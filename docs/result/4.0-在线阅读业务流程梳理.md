## 一、一句话架构

```
浏览器（Vue 3 + Element Plus）
   │  axios，带 Authorization: Bearer <token>
   ▼
nginx :91  ──/api/* 反向代理──▶  localhost:8081
   ▼
Spring Boot 4.0.8（内置 Tomcat）
   │  AuthInterceptor：校验 token → 把 loginUser 塞进 request attribute
   │  Controller → Service → Mapper
   ▼
MyBatis（resources/mapper/*.xml）
   ▼
MySQL 8.0（库名 library_system）
```

**两个容易忽略的结构性事实：**

1. **阅读页是一个独立的全屏路由**（`/read/:type/:id`），注册在 `MainLayout` **之外** —— 所以它没有侧边栏、没有顶栏，自己就是整个视口（`.reader { position: fixed; inset: 0 }`）。
2. **阅读页只有两种身份**：`type = book`（管理员上传的书籍）或 `type = file`（用户自己传的 txt）。两条线在同一个页面里，靠 `type` 分流到后端两组接口。

## 二、四张表的职责

### 总览

| 表 / 列 | 一句话职责 | 记录粒度 | 关键约束 |
|---|---|---|---|
| `book.readable` | "这本书能不能在线阅读"的**开关** | 一本书一个值 | `tinyint(1) NOT NULL DEFAULT 0` |
| `book_content` | **书籍**正文（长文本） | 一本书**一份** | `PRIMARY KEY (book_id)` → 天然一对一 |
| `reader_file` | **用户上传**的 txt | 一个文件一行 | `id BIGINT`；`KEY idx_user(user_id, create_time)` |
| `reader_progress` | 某人读到哪儿了 | **一人 × 一个目标 = 一行** | `UNIQUE uk_progress(user_id, target_type, target_id)` |

### 2.1 `book.readable` —— 开关列，不是一张表

```sql
ALTER TABLE book ADD COLUMN readable TINYINT(1) NOT NULL DEFAULT 0;
```

**为什么单独加一列，而不是"有正文就算可读"？**

因为"有正文"和"允许阅读"是两件事：

- 管理员可以先传正文、过几天再开放；
- 也可以临时关掉某本书的在线阅读，但**不想删正文**（删了要重传）。

所以拆成一个显式开关。默认 `0`（不可读）是安全默认值 —— 新加的书不会意外对读者开放。

> ⚠️ **一个容易踩的坑**：`UploadBookContent`（上传正文）**不会**自动把 `readable` 置 1。
> 管理员传完正文后，必须再去「电子书」弹窗里手动打开开关，读者才看得到「阅读」按钮。
> 如果你遇到"明明传了正文，列表里却没有阅读按钮"，先查这里。

### 2.2 `book_content` —— 书籍正文

```sql
CREATE TABLE book_content (
    book_id     INT      NOT NULL COMMENT '对应 book.id',
    content     LONGTEXT NOT NULL COMMENT '正文纯文本，换行统一用 \n',
    word_count  INT      NOT NULL DEFAULT 0 COMMENT '去掉空白后的字符数',
    encoding    VARCHAR(16) DEFAULT NULL COMMENT '检测到的原文本编码，只做诊断',
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (book_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

**设计要点：**

| 决策 | 原因 |
|---|---|
| 主键用 `book_id` 而不是自增 `id` | 一本书只可能有一份正文 → 主键本身就是"唯一约束"，不用额外查重 |
| 存整篇而不是一章一行 | 章节是**每次请求现切**的（见 §六），存整篇避免"章节表与正文不同步" |
| `LONGTEXT`（4GB 上限） | 一本正常小说 1~3MB；LONGTEXT 足够，不用纠结 |
| `encoding` 只做诊断 | 存的是"当初识别成什么"，**不参与解码**。正文在入库前已经转成 UTF-8 了 |
| 刻意**没有** `FOREIGN KEY` | 见 §八（外键与孤儿数据） |

正文入库前会统一把 `\r\n` 和 `\r` 都换成 `\n` —— 否则 Windows 换行会让章节正则里的 `[^\n]` 匹配出奇怪的结果。

### 2.3 `reader_file` —— 用户上传的 txt

```sql
CREATE TABLE reader_file (
    id            BIGINT       NOT NULL AUTO_INCREMENT,
    user_id       INT          NOT NULL,
    title         VARCHAR(200) NOT NULL COMMENT '默认取文件名（去掉扩展名）',
    content       LONGTEXT     NOT NULL,
    word_count    INT          NOT NULL DEFAULT 0,
    chapter_count INT          NOT NULL DEFAULT 0 COMMENT '切出来的章数，列表页要显示',
    encoding      VARCHAR(16)  DEFAULT NULL,
    create_time   DATETIME     DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    KEY idx_user (user_id, create_time)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

**和 `book_content` 的三处关键差异：**

| | `book_content` | `reader_file` |
|---|---|---|
| 主键 | `book_id`（外键式，一对一） | `id` **自增 BIGINT** |
| 为什么 | 一本书一份 | 一个用户可以传**很多份**，只能靠自增 id 区分 |
| 归属 | 无（书是公共的） | `user_id`，**所有读写都必须带上它** |

`id` 必须是 `BIGINT`：`book_content.book_id` 是 `INT`，而 `reader_progress.target_id` 是 `BIGINT`（要装得下两种 id）。所以 Java 里 `target_id` 用 `Long`，`bookId.longValue()` 转一下。

**`chapter_count` 是冗余字段，故意的** —— 它能在插入时算一次就存下来。否则「我的书库」列表页每行都要 `split()` 一次全文才能显示"几章"，一页 10 行就是 10 次全文切分，纯浪费。

**`idx_user (user_id, create_time)`** 是给列表页分页用的：`WHERE user_id = ? ORDER BY create_time DESC LIMIT ?, ?` 正好走这个联合索引。

### 2.4 `reader_progress` —— 读到哪儿了

```sql
CREATE TABLE reader_progress (
    id            BIGINT       NOT NULL AUTO_INCREMENT,
    user_id       INT          NOT NULL,
    target_type   TINYINT      NOT NULL COMMENT '1=书籍 2=用户文件',
    target_id     BIGINT       NOT NULL,
    chapter_index INT          NOT NULL DEFAULT 0,
    chapter_title VARCHAR(200) DEFAULT NULL,
    percent       DECIMAL(5,2) NOT NULL DEFAULT 0.00 COMMENT '章内滚动百分比 0~100',
    update_time   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_progress (user_id, target_type, target_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

**这张表是整个 4.0 里设计上最有取舍的一处。**

#### 为什么要 `target_type` + `target_id`，而不是两张表

书籍（`book.id` 是 `INT`）和用户文件（`reader_file.id` 是 `BIGINT`）是**两套独立的 id 空间**，`book` 里 5 号书和 `reader_file` 里 5 号文件完全是两个东西。

两种做法：

| 做法 | 代价 |
|---|---|
| 建 `book_progress` + `file_progress` 两张表 | 结构重复一遍，Service 里每个方法都要写两份 if/else |
| **一张表 + `target_type` 区分**（本项目选择） | `target_id` 必须用 `BIGINT` 装两种 id；查询时必须带上 `target_type` |

选第二种。代价就一条：**所有查询都不能只按 `target_id` 查**，必须 `(user_id, target_type, target_id)` 三件套一起。

#### 为什么唯一键是这三列

`UNIQUE (user_id, target_type, target_id)` 意味着：**同一个用户对同一个目标，永远只有一行**。

这直接带来两个后果：

1. **保存进度用的是 UPSERT**（`INSERT ... ON DUPLICATE KEY UPDATE`）—— 不用先查再决定 update 还是 insert。
2. **只能记住"最后读的那一章"的位置**，记不住"每一章各自读到哪"。

> 这是刻意的取舍。大多数人是顺着读的，记住最后位置就够了；
> 真要"每章各记一个位置"，唯一键要加 `chapter_index`（每章一行），
> 那"上次读到第几章"就不能从这行推了，得另算（取 `update_time` 最新的那条）。**目前没做。**

#### `percent` 的语义 —— 容易误解，重点看

```java
// services/Impl/ReaderServiceImpl.java 概念等价写法
int scrollable = el.scrollHeight - el.clientHeight;
percent = scrollable > 0 ? Math.min(100, el.scrollTop / scrollable * 100) : 0;
```

`percent` 是 **当前这一章内部的滚动百分比**，**不是**"全书读了百分之多少"。

所以它必须和 `chapter_index` 配着用才有意义 —— 单独一个 `percent = 42` 说明不了任何问题。

`DECIMAL(5,2)`（总共 5 位、2 位小数，最大 `999.99`）比 `FLOAT` 更适合存百分比：不会出现 `42.300000000000004` 这种浮点误差。

#### `chapter_title` 是快照

标题在保存进度时**复制一份**存进来，而不是每次 JOIN 回去取。

原因：正文可能被管理员替换，章节数会变。如果只存 `chapter_index`，正文换过之后这个 index 可能越界或指到别的章上。存一份标题快照，至少界面上还能显示"你上次读到《第三十八章 灯灭》"。

## 三、两条业务线

### 3.1 线 A：书籍在线阅读（管理员开放 → 读者阅读）

```
【管理员】
  图书列表 → 操作列「电子书」
    → BookContentDialog
        ├ 上传正文   → POST /reader/book/{id}/content
        ├ 预览阅读页 → 前端直接跳 /read/book/{id}
        └ 开关可读   → PUT /books/{id}/readable

【读者】
  图书列表 → 操作列「阅读」（只有 readable = 1 才出现）
    → /read/book/{id}
```

**权限判定只有一条**（`ReaderServiceImpl:56` 附近）：

```java
if (!Integer.valueOf(1).equals(book.getReadable())) {
    // 不可读 → meta 里返回 readable=false + denyReason，而不是抛异常
}
```

注意这里返回的是**正常响应 + `readable: false`**，不是 403 ✗
因为阅读页需要拿到书名和拒绝原因，好把"这本书暂时不能在线阅读"这句话显示出来。

### 3.2 线 B：用户上传的文件（自己传、自己读）

```
我的书库 → 「上传 txt」
  → POST /reader/file（multipart）
  → 返回新文件 id → 前端直接 router.push('/read/file/' + id)

我的书库 → 操作列「阅读」  → /read/file/{id}
        → 操作列「管理」  → 重命名 / 删除
```

**权限判定：只有一条，就是 `user_id`**

```sql
SELECT ... FROM reader_file WHERE id = #{id} AND user_id = #{userId}
```

拿不到 → 抛 "文件不存在"（**而不是 "没有权限"**）。这样别人无法通过错误信息探测"这个 id 是否存在"，是一个小但正确的安全习惯。

### 3.3 两条线的对照

| 维度 | 线 A：书籍 | 线 B：用户文件 |
|---|---|---|
| 谁能上传 | 仅管理员（`@RequireAdmin`） | 任何登录用户 |
| 存在哪张表 | `book_content` | `reader_file` |
| 权限判定 | `book.readable = 1` **且**正文存在 | `user_id = 当前登录人` |
| 有没有"开关" | **有**（`book.readable`） | **没有**（传了就能读） |
| 谁能看 | 所有登录用户 | 只有上传者自己 |
| 谁可删 | 管理员 | 上传者 |
| 目标类型值 | `target_type = 1` | `target_type = 2` |
| 后端接口前缀 | `/reader/book/**` | `/reader/file/**` |
| 前端 `type` 值 | `book` | `file` |

★ **两条线在 Service 层是分开的私有方法，不共用** —— 因为权限模型完全不同（一个看公共开关，一个看归属）。强行抽象成一个方法，后面会变成一堆 `if (type == book) ... else ...`。

## 四、六条关键链路（时序）

### 4.1 管理员上传书籍正文

```
① 前端 BookContentDialog → POST /reader/file... 不对，是 /reader/book/{id}/content
   Content-Type: multipart/form-data，字段名 file

② AuthInterceptor
   → 校验 token
   → @RequireAdmin 校验角色

③ ReaderServiceImpl.UploadBookContent(bookId, file)
   ├ 校验 book 是否存在
   ├ CheckTxt(file)
   │   ├ 后缀必须是 .txt
   │   └ 大小 ≤ 10MB（MAX_BYTES = 10L * 1024 * 1024）
   ├ byte[] bytes = file.getBytes()
   ├ Decoded d = TextDecodeUtils.decode(bytes)     ← 编码检测（§五）
   ├ text = d.text()  换行统一成 \n
   ├ wordCount = 去掉空白后的字符数
   └ bookContentMapper.Upsert(bookId, text, wordCount, d.charset())
       （book_id 是主键 → INSERT ... ON DUPLICATE KEY UPDATE，天然幂等，可反复覆盖）

④ 返回 {code:1}
```

⚠️ **这一步不会打开 `readable`**。上传成功 ≠ 可读。管理员要再点一次开关（`PUT /books/{id}/readable`）。

### 4.2 读者打开一本书（冷启动）

```
① 前端 router → /read/book/:id → ReaderView.vue 挂载
   onMounted → loadMeta()

② GET /reader/book/{id}/meta
   ├ 查 book（含 readable）
   ├ 不可读 → 返回 { readable:false, denyReason, title }  【不抛异常】
   ├ 查 book_content
   │   └ 没有正文 → { readable:false, hasContent:false, denyReason:'还没有正文' }
   ├ SplitChapters(text)  → List<ChapterItemVo>（标题 + 字数，不含正文）
   ├ 查 reader_progress
   │   └ 有 → lastChapter = min(chapterIndex, 章数-1)   ← 夹一下防越界
   │          lastPercent = percent
   └ 返回 { title, readable, chapterCount, wordCount, encoding,
            lastChapter, lastPercent, chapters[] }
   ★ 注意：返回里【没有正文】，正文要单独按章取

③ 前端 await loadChapter(lastChapter || 0)

④ GET /reader/book/{id}/chapter/{index}
   ├ GetReadableText(bookId)   ← 再校验一次可读性 + 取正文
   ├ ReadChapter(text, index)  ← 现切章节，返回这一章的 content
   └ 返回 { index, title, content, prevIndex, nextIndex, wordCount }
   ★ prevIndex / nextIndex 必须是 Integer（首章/末章的邻居为 null），
     用 int 的话首章会变成 -1，前端翻页按钮的判断就错了

⑤ 前端 await nextTick()  → RestoreScroll(lastPercent)   ← 恢复章内滚动位置

⑥ 渲染：<p v-for> 逐个段落，插值输出（绝不用 v-html）
```

### 4.3 用户上传自己的 txt

```
① 前端 beforeUpload：只检查"能不能传"（后缀 + 大小）
   ★ 绝不读文件内容 —— 前端一 readAsText，GBK 文件当场变乱码，
     后端就再也救不回来了。内容必须原样按字节传到后端。

② POST /reader/file  (multipart，可选 title 字段)

③ ReaderServiceImpl.UploadFile
   ├ CheckTxt → Decode → ResolveTitle（没传 title 就用文件名去扩展名）
   │   └ 标题超 200 字 → 截断到 200
   ├ SplitChapters 算 chapterCount
   └ readerFileMapper.Save(file)  ← useGeneratedKeys 回填 id

④ 返回 ReaderFileVo（含 id）
   → 前端拿到 id 直接 router.push('/read/file/' + id)，少一步点击
```

### 4.4 阅读中翻章

```
点「下一章」（或按 → 键、或目录里点某一章）
  ├ goChapter(nextIndex)
  │   ├ 判定动画方向：index < 当前 index ? 'prev' : 'next'
  │   ├ FlushProgress()      ← 先把【上一章】的进度立刻存掉
  │   └ loadChapter(index)
  │       ├ GET /reader/{type}/{id}/chapter/{index}
  │       ├ scrollTo({ top: 0 })    ← 新章从头开始
  │       └ 悬浮窗章节名做滑动切换动画（旧标题左移出、新标题从右进）
```

★ 顺序很重要：**先存旧章进度，再加载新章**。反过来会拿到新章的滚动位置去写旧章的记录。

### 4.5 保存阅读进度（三种时机，行为不同）

| 时机 | 用哪个函数 | 为什么 |
|---|---|---|
| 阅读中滚动 | `saveProgress()` | **800ms 防抖**，避免每滚一下发一次请求 |
| 切章 / 组件卸载 | `FlushProgress()` | **立刻发**，不等防抖 |
| 关标签 / 刷新 / 手机切后台 | `SaveOnUnload()` | **`fetch` + `keepalive`**，见下 |

**为什么关页时必须绕过 axios：**

- `axios` 底层是 `XMLHttpRequest`，页面卸载时浏览器会**取消**在途请求 → 进度静默丢失；
- `fetch(..., { keepalive: true })` 允许请求"带着页面卸载过程一起发出去"；
- `navigator.sendBeacon` 也能活过卸载，但它**只能发 `text/plain` / 表单**，发不了我们的 `PUT + application/json` → 用不了。

### 4.6 从阅读页返回

```
点「← 返回」
  ├ 只做 router.push（不在这个函数里存进度）
  └ 路由变化 → 组件卸载 → onBeforeUnmount
        ├ FlushProgress()     ← 立刻发，这里才是唯一的保存点
        └ 移除 keydown / pagehide 监听
```

★ **`goBack` 里不能也存一次** —— 两边都存会发两遍请求，而且第二遍的路由参数已经失效（见 §十一 坑 4）。

## 五、编码检测：为什么必须有这一步

### 问题

用户传的 txt 可能是 **UTF-8**，也可能是 **GBK / GB18030**（国内 Windows 记事本、老网站的常见编码）。JVM 里字符串是 UTF-16，要正确转成字符串，**必须先知道原文件是什么编码**。

猜错的后果很具体：GBK 的文件按 UTF-8 解，会得到

```
��һ�� Ǳ��      ← 这就是乱码
```

### 检测顺序

```
TextDecodeUtils.decode(byte[] bytes)
  ① 看 BOM
       EF BB BF     → UTF-8
       FF FE        → UTF-16LE
       FE FF        → UTF-16BE
       （BOM 存在时直接按它解，最可靠）
  ② 严格按 UTF-8 解一遍
       CodingErrorAction.REPORT  ← ★ 关键，见下
       成功 → "utf-8"
       抛异常 → 进 ③
  ③ 按 GB18030 解
       GB18030 是 GBK / GB2312 的超集，能覆盖国内绝大多数非 UTF-8 文本
       成功 → "gb18030"
  ④ 都失败 → 兜底按 UTF-8 解（不抛异常，宁可显示乱码也不让上传失败）
```

### ★ 最关键的那一行

```java
// 正确
decoder.onMalformedInput(CodingErrorAction.REPORT);

// 错误 —— 会让整个检测机制失效
decoder.onMalformedInput(CodingErrorAction.REPLACE);
```

用 `REPLACE` 的话，遇到非法字节它会**默默替换成 `�` 而不抛异常** → 第 ② 步永远不会失败 → GB18030 分支**永远执行不到** → 所有 GBK 文件全部变成乱码。

这个坑本项目真实踩过：一开始写的就是 `REPLACE`，结果 GBK 测试文件全部显示成 `��һ�� Ǳ��...`。改成 `REPORT` 后，同一批文件全部正常。

> 顺带一个同源的小 bug：BOM 判断写成了 `bytes.length > 3`，应该 `>= 3`。
> 否则"正好 3 字节的文件"（极端但可能）会被跳过 BOM 检测。

### 检测结果存哪

`encoding` 列。但它**只做诊断** —— 入库的 `content` 已经是 UTF-8 的 Java 字符串，后续所有读取都不再管 `encoding`。

排查时很有用：`SELECT encoding FROM reader_file` 一眼就能看出当初识别成什么。

## 六、章节切分：为什么每次都重新切

### 规则

```java
private static final Pattern CHAPTER =
    Pattern.compile("(?m)^[ \\t　]*(第[0-9０-９零一二三四五六七八九十百千万〇两]+[章节回卷篇集]"
                  + "|Chapter\\s+\\d+|序章|楔子|引子|尾声|后记|番外)[^\\n]{0,40}$");
```

逐条解释：

| 部分 | 作用 |
|---|---|
| `(?m)` | 多行模式，`^` / `$` 匹配每行的头尾 |
| `^[ \t　]*` | 允许标题行前面有空格（含**全角空格** `　`，中文 txt 里常见） |
| `第[数字]+[章节回卷篇集]` | 中文数字 + 单位（含**全角数字** `０-９` 和 `〇两`） |
| `Chapter\s+\d+` | 顺带支持英文章节 |
| `序章\|楔子\|引子\|尾声\|后记\|番外` | 特殊章节名 |
| `[^\n]{0,40}$` | 标题后面最多 40 个字，且**必须到行尾** |

最后那一段 `[^\n]{0,40}$` 是防止误切的关键：正文里出现"第一章"三个字（比如"他翻到第一章"）不会匹配，因为后面还有很长一段话不满足"到行尾且不超过 40 字"。

### 章首内容的归并

第一个章节标题**之前**如果有文字，会被归成独立一章，标题由程序生成：

```java
items.add(new ChapterItemVo(0, "前言", ...))
```

测试文本正是靠这个规则验证的：正文开头放几段话、不写"前言"两个字，阅读页里应该自动出现一章叫「前言」。

### 为什么**不**把章节落库

| 方案 | 问题 |
|---|---|
| 建 `book_chapter` 表，切一次存下来 | ① 正文会被替换 → 章节表要跟着重建，一旦漏了就不一致；② 切分规则以后想改（比如加"卷一"），已入库的旧数据全部失效，还得写迁移脚本 |
| **每次请求现切**（本项目选择） | 每次都要 `split()` 一遍全文 |

现切的成本：**2MB 的文本大约几十毫秒**，完全在可接受范围。而一致性问题的排查成本远高于这几十毫秒。

所以：**数据库里只存"整篇正文"，章节是运行时产物。**

代价是每次翻章都要重新切一遍全文（取第 N 章也是切完再取）。这是刻意的取舍。

## 七、阅读进度：最绕的一块

### 7.1 数据结构决定了能力边界

```
UNIQUE (user_id, target_type, target_id)
   → 一人 × 一目标 = 一行
   → 只能记"你最后读的那一章 + 那一章的滚动百分比"
   → 记不住"第 3 章你读到 60%、第 7 章你读到 20%"
```

想升级成"每章各自记位置"，唯一键要变成 `(user_id, target_type, target_id, chapter_index)`，同时还要另外维护"上次读到第几章"。**目前没做**。

### 7.2 一次完整的"读 → 存 → 再读"

```
【第一次阅读】
  meta → lastChapter = 0, lastPercent = 0
  → 打开第 0 章，滚到 42%
  → 关掉页面 → FlushProgress
      PUT /reader/{type}/{id}/progress
      { chapterIndex: 0, chapterTitle: "前言", percent: 42.00 }
      → UPSERT 进 reader_progress

【第二次打开】
  meta → lastChapter = 0, lastPercent = 42.00
  → 打开第 0 章
  → await nextTick()          ← 必须，见下
  → RestoreScroll(42)         → scrollTop = 42% × (scrollHeight - clientHeight)
  → 正好回到上次的位置
```

### 7.3 ★ `nextTick` 那一步为什么不能省

```js
// 错：章节内容刚赋值、DOM 还没更新，height 算出来是 0，滚不动
chapter.value = data
RestoreScroll(percent)

// 对：等 DOM 更新完再算
await loadChapter(index)
await nextTick()
RestoreScroll(percent)
```

`scrollHeight` 取决于正文有没有真的渲染出来。这行是"恢复位置"这类功能最经典的坑。

### 7.4 后端也要夹一下

```java
vo.setLastChapter(Math.min(progress.getChapterIndex(), items.size() - 1));
```

正文被替换过之后章节数可能变少。不夹的话，前端会去请求一个不存在的章节号 → 后端返回"章节不存在" → 用户体验成"明明有进度却打不开"。

### 7.5 级联清理

| 什么时候 | 清什么 | 代码位置 |
|---|---|---|
| 删除书籍正文 | **所有人**对这本书的进度 | `DeleteBookContent` → `DeleteByTarget(TARGET_BOOK, ...)` |
| 删除用户文件 | **所有人**对这个文件的进度 | `DeleteFile` → `DeleteByTarget(TARGET_FILE, ...)` |
| 删除用户 | **这个人**的全部进度 | `UserServiceImpl.ClearUserData` → `DeleteByUser(userId)` |

★ 前两个是"删目标 → 清所有相关进度"（故意不带 `user_id`）；
第三个是"删用户 → 清他自己的所有进度"（带 `user_id`）。两个不同的清理维度，别混。

## 八、权限与安全

### 8.1 三层防护

| 层 | 做什么 | 在哪 |
|---|---|---|
| 登录拦截 | 除 `/auth/login`、`/auth/register` 外全部要求 token | `AuthInterceptor` + `WebConfig` |
| 角色拦截 | `@RequireAdmin` 标注的方法仅管理员 | `AuthInterceptor` 读注解 |
| 数据归属 | 每条 SQL 都带 `user_id` | 各 Mapper 的 `WHERE` |

**HTTP 状态码的语义要分清：**

| 码 | 含义 | `code` 字段 |
|---|---|---|
| 200 | 业务处理完了（可能成功也可能业务失败） | `1` 成功 / `0` 业务失败 |
| 401 | **没登录**（或者 token 过期） | — |
| 403 | **登录了，但角色不对**（普通用户访问管理员接口） | — |

`401` 和 `403` 的区别是"你是谁不知道"和"我知道你是谁，但你不能干这个"。

### 8.2 IDOR（越权访问）防线

所有"按 id 操作"的接口，SQL 里**必须**同时带 `user_id`：

```sql
-- 对：改不到别人的文件
UPDATE reader_file SET title = #{title} WHERE id = #{id} AND user_id = #{userId}

-- 错：只要猜到 id 就能改别人的
UPDATE reader_file SET title = #{title} WHERE id = #{id}
```

`GetOwnFile(fileId, loginUser)` 这个私有方法把所有"取文件"的路径统一成一句话：**先校验归属，再干活**。所有需要文件实体的地方都走它。

### 8.3 XSS 防线

正文是用户上传的纯文本，里面可以写 `<script>`。

```html
<!-- 对：插值，Vue 会转义 -->
<p v-for="text in paragraphs">{{ text }}</p>

<!-- 错：v-html 会把 <script> 当代码执行 -->
<p v-html="content"></p>
```

**整个阅读页没有一处使用 `v-html`。** 这是硬约束，改这块代码时不要破坏它。

### 8.4 外键与孤儿数据

**本项目所有 4.0 的表都没有建外键。** 后果是删父级数据**不会**级联删除子数据。

已确认会留孤儿的三张表：

| 表 | 场景 | 现在怎么处理 |
|---|---|---|
| `reader_file` | 用户被删 → 他的文件还在 | ✅ `ClearUserData` 手动清 |
| `reader_progress` | 用户被删 → 他的进度还在 | ✅ 同上 |
| `notice_read` | 用户被删 → 他的已读记录还在 | ✅ 同上 |
| `borrow_record` | 用户被删 → 借阅历史还在 | ❌ **故意保留**（历史要留档） |

`ClearUserData` 在**两个入口**都调了：`DeleteUser`（管理员删人）和 `LogoutUser`（用户自己注销），且都加了 `@Transactional` —— 保证"清数据"和"删用户"要么全成、要么全不成。

> 留档的代价：`borrow_record` 里保留的 `user_id` 会指向已删除的用户。
> 前端借阅列表如果要 JOIN 出用户名，会显示空白。要处理的话，方案是"存用户名快照"或"显示『已注销用户』"。

## 十一、踩过的坑（8 条）

按"疼"的程度排，每条都是真实发生过的。

### 坑 1：`CodingErrorAction.REPLACE` 让编码检测形同虚设

`REPLACE` 不抛异常 → 永远走不到 GB18030 分支 → 所有 GBK 文件乱码。
**修法**：改成 `REPORT`（解码器遇到非法字节要抛，才能进入下一个候选编码）。

### 坑 2：`onBeforeUnmount` 里 `saveProgress()` + `clearTimeout` 互相抵消

```js
onBeforeUnmount(() => {
  saveProgress()            // 内部 setTimeout(..., 800)
  clearTimeout(saveTimer)   // 立刻把刚设的定时器取消 → 一次都没发出去
})
```

**症状**：离开阅读页时进度完全没保存。
**修法**：拆出不防抖的 `FlushProgress()`，卸载时用它。

### 坑 3：`percent` 存了但从来没被读回来

后端 `ReaderMetaVo` 只有 `lastChapter`，没有 `lastPercent`；前端 `loadChapter` 进来就 `scrollTo({top: 0})`。
**症状**：进度存得很勤，但永远回到章首。
**修法**：meta 增加 `lastPercent`，前端 `nextTick` 后 `RestoreScroll`。

### 坑 4：`computed(() => route.params.id)` 在卸载时变成 `undefined`

```js
// 错
const targetId = computed(() => route.params.id)
// 返回时：goBack → 存一次（参数还对）→ router.push('/books')
//        → 路由变了，params.id = undefined
//        → onBeforeUnmount 再存一次 → PUT /reader/book/undefined/progress
//        → 后端 @PathVariable Integer 绑定失败 → 500「服务器异常」
```

**症状**：从阅读页返回时弹"服务器异常"，但实际数据都对（真保存早就成功了，这是**假请求**）。
**修法**：进页面时快照 `const targetId = ref(route.params.id)`；`goBack` 不再重复保存；三个保存函数加 `targetId` 守卫。

### 坑 5：`axios` 的请求在页面卸载时被取消

**症状**：关标签页时最后一次进度丢失。
**修法**：`fetch(..., { keepalive: true })`。不能用 `sendBeacon`（它发不了 `PUT + JSON`）。

### 坑 6：`text-indent` 只作用于第一行

整章塞进一个 `<p>` 里，`text-indent: 2em` 只会缩进开头的第一行。
**修法**：按 `\n` 切段，每段一个 `<p>`。改完 `white-space: pre-wrap` 也要去掉。

### 坑 7：主题切换"只换悬浮窗、不换页面"

排查后确认正文区没有写死的背景色遮挡。最终放弃"切 class + CSS 规则解析"的路线，改成**行内 CSS 变量**（`:style="themeStyle"`）—— 少一层解析，就不可能"没匹配上"。

### 坑 8：多表 `DELETE ... USING JOIN` 在 MySQL 上报错

```sql
-- ✗ 报错
DELETE r FROM notice_read r LEFT JOIN sys_user u ON u.id = r.user_id WHERE u.id IS NULL

-- ✓ 用这个
DELETE FROM notice_read WHERE user_id NOT IN (SELECT id FROM sys_user)
```

> 附带教训：排查时我把 stderr 用 `2>$null` 屏蔽了，结果**自己的报错也被吞掉**，白折腾一轮。
> 生产代码里用的是 `WHERE user_id = #{userId}` 最简形式，没这个问题。
