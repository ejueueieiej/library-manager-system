## 一、写代码时遵循的约定

| 项 | 约定 | 原因 |
|---|---|---|
| 代码注释 | 只写「为什么」，不写「是什么」；一句话能说清就不写 | 代码要能一口气读下去 |
| 多参数 Mapper 方法 | 一律加 `@Param` | 跟你 `BookMapper` 的风格一致 |
| id 类型 | 用 `Integer` | 库表是 `BIGINT`，但项目里 `LoginUser` / `sysUser` / `Book` 的 id 统一是 `Integer` |
| DTO 默认值 | 分页字段必须在字段上给默认值 | 防 `(pageNum-1)*pageSize` 拆箱 NPE |
| 分页 total | 必须和 list 共用同一段 `<sql>` 条件 | 2.0 的 `GetUsers` 就错在这里：搜「张三」列表 1 行、页脚显示共 3 条 |
| 统一返回 | `new Result().success(msg, data)` | 跟现有代码一致 |
| 权限 | 管理员方法打 `@RequireAdmin` | `WebConfig` 不用动，拦截器默认全拦、只放行 `/auth/login`、`/auth/register` |

**③ `GetMySummary` 一条 SQL 出三个数**，不用发三条查询：

```sql
SELECT COUNT(CASE WHEN status = 1 THEN 1 END)                       AS borrowing_count,
```

#### 🔴 修正：上面 ① 的口径是错的（实测抓到，已改）

**① 的结论「按日历天算」已被推翻。** 它和 SQL 的逾期判定口径不一致：

```sql
-- 筛选、统计、排序用的都是这个（时刻比较）
status = 1 AND due_time < NOW()
```

用真实测试数据（`due_time = 今天 22:22`、请求时 `22:31`）一问正在跑的后端就露了：

| 来源 | 口径 | 对同一条记录的结论 |
|---|---|---|
| `summary.overdueCount` | SQL `due_time < NOW()` | **1（算逾期）** |
| `?overdue=1` 筛选 | SQL `due_time < NOW()` | **筛得出来** |
| `overdueDays` | 日历天差 | **0（不算逾期）** |

表现就是：**这条记录出现在「已逾期」筛选里，却不标红、不显示天数** ——
也就是"为什么看不到小红点"的直接原因。

**修正后的唯一口径**：判定用**时刻**（`due_time < now`），天数**不满一天也计 1 天**：

```java
private int OverdueDays(LocalDateTime dueTime, LocalDateTime end) {
    if (dueTime == null || !dueTime.isBefore(end)) {
        return 0;
    }
    long days = ChronoUnit.DAYS.between(dueTime.toLocalDate(), end.toLocalDate());
    return days > 0 ? (int) days : 1;   // ★ 不满一天也算逾期 1 天
}
```

**续借的逾期判断也回调成时刻比较**：上一轮我把它改成按日期比，
那是"为了让两边一致而改错了另外一边"。现在四处统一跟着 SQL 走：
`summary.overdueCount` / `?overdue=1` 筛选 / `overdueDays` / 续借拦截。

> 教训：**同一件事（"逾期了吗"）在 SQL 和 Java 里各写了一遍，就必须把口径钉死。**
> 更省事的做法是只留一处 —— 比如让 SQL 直接算 `overdueDays` 返回，
> Java 就永远不会和它打架。这版先用"两处同口径 + 注释互相指认"，
> 等接口 8 写完可以考虑合并成一处。

**★ `GetAllBorrowCount` 必须带上 JOIN —— 和接口 2 正好相反**

接口 2 的 count 不需要 JOIN（它的条件只引用 `r.*`）。接口 6 的**必须带**：

```xml
<select id="GetAllBorrowCount" resultType="java.lang.Integer">
    SELECT COUNT(*)
    FROM borrow_record r
             LEFT JOIN book b ON b.id = r.book_id       <!-- ★ 不能省 -->
             LEFT JOIN sys_user u ON u.id = r.user_id   <!-- ★ 不能省 -->
    <include refid="allBorrowWhere"/>
</select>
```

因为管理员的筛选条件引用了**关联表的列**：

```xml
<if test="dto.username != null and dto.username != ''">
    AND u.username LIKE CONCAT('%', #{dto.username}, '%')
</if>
<if test="dto.bookName != null and dto.bookName != ''">
    AND b.name LIKE CONCAT('%', #{dto.bookName}, '%')
</if>
```

少了 JOIN，一按用户名搜索就是 `Unknown column 'u.username' in 'where clause'` ——
**而且编译期完全看不出来，只有真的带着 username 参数请求一次才会暴露。**

所以规律不是"count 不用 JOIN"，而是：
**count 的 JOIN 需求，取决于 `<where>` 片段引用了哪些表的列。**

**接口 7 撤销和接口 4 归还是同一个模式**，连幂等门都一样：

```xml
<update id="CancelBorrow">
    UPDATE borrow_record SET status = 3 WHERE id = #{id} AND status = 1
</update>
```

都是「带条件翻转记录 → 成功了才 `IncreaseAvailable`」。
所以"先还后撤"这两次操作里，第二次必然拿到 0 行 → **库存绝不会被 +2**。

**接口 6 复用了接口 2 的三样东西**：`borrowOrder` 排序片段、`FillComputed`（逾期天数 + 可否续借）、
`borrowPageResult` —— 所以它自己只多了 `allBorrowWhere` 一个片段和三条语句。

```java
// 1.0 已有的写法：用库存差值反推
if (old.getTotalNum().intValue() - old.getAvailableNum().intValue() > 0) {
    throw new BusinessException("该图书已被借出，不能删除");
}
```

| 判据 | 表达式 | 性质 |
|---|---|---|
| 库存差值（现在的） | `total_num - available_num > 0` | **派生值** —— 依赖 `available_num` 一直算得对 |

**结论：现在的写法够用**，要更稳就换成一行的账本判据。**暂未更换**，等确认。

## 五、需要留意、但不需要写进代码的坑

- **`/notices/unread-count` 与 `/notices/{id}` 路径相似**：Spring 6 的路径匹配里字面量段优先于 `{id}` 模板，所以能正确命中。真撞上 500（`Failed to convert String to Long`）就把路径换成 `/notices/unread/count`，前端改一行。
- **列表的 `notice_read` JOIN 条件必须写在 `ON` 后面**：写进 `WHERE` 会让 `LEFT JOIN` 退化成 `INNER JOIN`，症状是"读过的通知都在，没读过的反而看不见"。
- **MyBatis XML 里 `<` 是非法字符**：`due_time < NOW()`、`available_num < total_num` 必须写成 `&lt;`（`>` 不用转义）。借阅模块到处都是这种比较。
- **「批量删除」按钮点了会 500**（已实测确认）：前端调的 `DELETE /books/batch` 后端不存在，
  而它会被 `@DeleteMapping("/books/{id}")` 匹配到（`id = "batch"`）→
  `Integer` 转换失败抛 `MethodArgumentTypeMismatchException` →
  被 `GlobalExceptionHandler` 的兜底 `Exception` 处理器转成 **500「服务器异常，请联系管理员」**。
  实测：`DELETE /books/abc` 和 `DELETE /books/batch?ids=99999` 都返回 500，且没有误删任何数据。
  处理方式二选一：补上 `DELETE /books/batch`（顺便给批量删除也加未归还校验），
  或者把前端那个按钮去掉 —— 它从 1.0 起就是死的。

## 六、模块二的规则变更（2026-10-16）

规则由「用户可自助还书」改为「**还书必须由管理员确认**」。
你给的理由是"用户自己在网站上操作，有图书丢失的风险" —— 结论正确，
而且本质比这个表述更严重：

> **自助还书会销毁"这本书在谁手上"的唯一凭证。**
> 用户在家点一下，`available_num` 就 +1、`return_time` 被写上、记录变成"已归还"，
> 而书还在他手上。**从此系统里再也查不出这本书在谁那儿，且不可逆。**

### 对称检查：借书方向要不要一起收？

借书的"假事实"也是用户点出来的（点了借书却没来取，书被虚拟占着），
但两者**严重程度不对称**：

| | 用户误操作后 | 库存 | 追责凭证 |
|---|---|---|---|
| **自助还书** | 虚增 → 别人来借扑空 | ❌ **被销毁** |
| **自助借书** | 虚减 → 别人借不到 | ✅ 还在（记录是"借出中"，借阅人明确） |

所以只收还书，保留自助借书，并给"没来取书"补一个**撤销借阅**出口。

### 最终确认的五条规则

| 决策 | 结果 |
|---|---|
| 借书 | 用户**自助**（保留） |
| **还书** | **仅管理员**，可填实际归还日期（默认今天） |
| **撤销借阅** | **仅管理员**，新增接口 7；不删记录，置 `status = 3` |

| **删除记录** | **仅管理员**，新增接口 8（备用通道）；**借出中的删不掉** |

### 补充：管理员删除通道（你的要求「以备用」）

在接口 7 之外又加了 **接口 8 `DELETE /borrows/{id}`**，但加了一道硬约束：

```
✅ status = 2 已归还  → 可以删
✅ status = 3 已取消  → 可以删
❌ status = 1 借出中  → 拒绝
```

**为什么借出中的不能删**：那条记录是"这本书在谁手上"的唯一凭证。
删了它，`available_num` 会**永远少一本**（书在外面，却没有任何记录说明它去了哪），
这本书在系统里"人间蒸发" —— **正是"用户不能自助还书"要防的那个风险，
只是换成了由管理员来触发**。

已归还 / 已取消的记录库存早就回滚过了，删它们不动库存、不破坏一致性。

约束做了**两层**（防的是以后有人改坏其中一层）：

| 层 | 位置 | 作用 |
|---|---|---|
| Service | `if (record.getStatus() == 1) throw ...` | 给出可读的错误提示 |
| SQL | `WHERE id = ? AND status != 1` | ★ 最后一道闸：万一 Service 被改坏，数据库也不让删 |

要删一条借出中的记录 → 先「撤销借阅」再「删除」，**两步都是诚实的事实**，
不存在绕过库存逻辑的旁路。

**这次改动零返工** —— 借阅模块的 POJO / Mapper / Service / Controller 一个都还没建。

### 变更后仍需注意的两点

1. **`returnTime` 必须用 `String` 接，不能声明成 `LocalDate`**：格式不对时 Spring 会抛
   `MethodArgumentTypeMismatchException`，被全局处理器兜成 500「服务器异常」，
   管理员只会看到"服务器异常"，完全不知道是自己日期格式打错了。
2. **`overdueDays` 已归还的记录必须用 `return_time` 算**，不能用"今天" ——
   否则 8 月按期归还的记录到 12 月会显示"逾期 120 天"。
