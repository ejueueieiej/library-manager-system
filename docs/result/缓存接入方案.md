## 二、P1：图书详情切"逻辑过期"

现状：`GetBookById` 走 `queryWithPassThrough`。`queryWithLogicalExpire` 已实现、有单测，但没人调用。

**如果只是交作业，保持现状完全够用。** 做这一步的理由只有一个：答辩时能演示"过期瞬间 50 并发只回源 1 次"。

### 接入两步

```java
// 1) Service 里换方法
Book book = cacheUtil.queryWithLogicalExpire(
        CacheUtil.CACHE_BOOK_KEY, id, Book.class,
        bookMapper::GetBookById, CacheUtil.CACHE_BOOK_TIME, TimeUnit.MINUTES);
```

```java
// 2) 启动预热：不做的话第一批请求全是"未命中"，会直接打库
@Component
public class CacheWarmUp implements CommandLineRunner {
    @Override
    public void run(String... args) {
        // 只预热上架的书，数量按需要取
        for (Book b : bookMapper.GetOnShelfBooks(200)) {
            cacheUtil.setWithLogicalExpire(CacheUtil.CACHE_BOOK_KEY + b.getId(),
                    b, CacheUtil.CACHE_BOOK_TIME, TimeUnit.MINUTES);
        }
    }
}
```

### 注意

- **切换前清一次 `Cache:Book:*`**：同一个 key 混着两种格式（普通 JSON vs `{"data":...,"expireTime":...}`），读的时候必然踩反序列化。
- 切过去之后，**不要再同时用 `queryWithPassThrough` 写同一个 key**，二选一。
- 逻辑过期的 key **物理永不过期**，全靠写操作删 key + 未命中回源兜底——这两条你都已经有了。

## 三、P2：用户信息缓存（收益最大）

### 为什么值得做

`AuthInterceptor` 每个请求都要 `loginMapper.GetByUsername` 查一次 `sys_user`。
实测：**100 个请求 = 100 条用户表 SQL**，比图书查询还多，是当前 DB 压力的大头。

### 红线：别把密码哈希写进 Redis

`sysUser` 里有 `password`（BCrypt 哈希）。直接缓存等于把一份可离线爆破的密码库放进 Redis。
最省事的做法是缓存前把它抹掉：

```java
public static final String CACHE_USER_KEY = DEFAULT_CACHE_KEY + "User:";

sysUser user = cacheUtil.queryWithPassThrough(
        CacheUtil.CACHE_USER_KEY, username, sysUser.class,
        name -> {
            sysUser u = loginMapper.GetByUsername(name);
            if (u != null) {
                u.setPassword(null);     // ← 关键：不进缓存
            }
            return u;
        }, 60L, TimeUnit.SECONDS);
```

### TTL 必须短

**30~60 秒**。因为要兼顾"账号被禁用/删除后多久生效"——TTL 越长，禁用了还能继续用的时间越长。

### 失效点（6 个）

`UpdateUser`、`UpdateStatus`（禁用）、`ResetPassword`、`DeleteUser`、`LogoutUser`、`AddUser`（如果新增时可能撞名）：
```java
cacheUtil.deleteKey(CacheUtil.CACHE_USER_KEY + username);
```

### 不做的理由也成立

不做就是数据库多几次查询；做了就要保证"禁用及时生效"。**这门课不做不算短板，做了要能讲清楚这个权衡。**

## 四、明确不做

| 项 | 理由 |
|---|---|
| 通知列表缓存 | 管理员低频 + 6 个筛选维度 + 失效要版本号，收益和复杂度完全不匹配 |
| 图书分页缓存 | 任何一本书改动都会让所有分页脏掉，命中率还低 |
| 用户管理列表 | QPS 低，缓存只会增加 bug 面 |
| 布隆过滤器 | 知道"能挡枚举穿透"就够，别实现 |
| 事务 `afterCommit` / 锁 UUID + Lua / 线程池 `@PreDestroy` | 知道有这回事即可 |

## 五、判断标准（以后加新缓存前问自己）

1. **QPS 高不高？**（由流量决定，不由接口的权限等级决定）
2. **写频率低不低？**
3. **失效能不能一两条 `DEL` 搞定？**
4. **key 维度多不多？**（多条件 + 分页 = 命中率灾难）
5. **缓存错了会不会让业务判断出错？**（库存、权限 → 不进缓存）

五条里中三条"否"，就别加。

## 六、仍然存在的风险（知道就行）

1. **枚举穿透**：空值缓存挡不住"换着 id 打"。最便宜的缓解是 `id <= 0` 直接拒绝，治本要布隆过滤器。
2. **锁可能误删**：`islock` 的 value 是空串、`unlock` 直接 `delete`；重建超过 10 秒锁 TTL 时可能删掉别人的锁。
3. **线程池未关闭**：`CACHE_REBUILD_EXECUTOR` 是非守护线程，应用关闭时最好 `@PreDestroy` 里 `shutdown()`。
4. **序列化表示**：`BigDecimal 32.00` 会变成 `32`、日期在 Redis 里是毫秒时间戳。命中缓存前后的响应体可能不完全一致（不影响业务）。
5. **改实体字段后的旧缓存**：缓存里多出来的字段可能反序列化失败。`queryWithPassThrough` 目前没有 try/catch 兜底。
6. **事务内删缓存**：`BorrowBook` / `ReturnBook` / `CancelBorrow` / `DeleteNotice` 是在事务方法体里删的，理论上存在毫秒级窗口；课程项目可接受。
