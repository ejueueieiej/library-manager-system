## 一、为什么要有这个接口

v2.0 的用户只能由管理员在「用户管理」里创建。但真实场景里，读者应该能自己注册：

- 管理员不必挨个代建账号
- 读者自助注册后立即可用（默认「读者」角色，只能查书、看详情）
- 需要更高权限（管理员）时，仍由管理员在「用户管理」里调整 —— **注册接口永远不给管理员权限**

## 三、接口详情

### 1. 用户自助注册

| 项 | 值 |
|---|---|
| 请求方法 | `POST` |
| 后端路径 | `/auth/register` |
| 前端请求 | `/api/auth/register` |
| 需要登录 | ❌ **不需要**（和 `/auth/login` 一样是公开接口） |

#### 请求体

| 字段 | 类型 | 必填 | 校验规则 | 说明 |
|---|---|---|---|---|
| `username` | String | ✅ | 3~50 字符，**全库唯一**，只允许字母/数字/下划线 | 登录名 |
| `password` | String | ✅ | 6~20 字符 | **明文传过来，后端 BCrypt 加密后存** |
| `realName` | String | ✅ | ≤50 | 真实姓名 |
| `phone` | String | ❌ | ≤20，格式 `1[3-9]\d{9}` | 手机号 |
| `email` | String | ❌ | ≤100，基本邮箱格式 | 邮箱 |

```json
{
  "username": "wangwu",
  "password": "123456",
  "realName": "王五",
  "phone": "13800000004",
  "email": "wangwu@example.com"
}
```

> ⚠️ **请求体里【没有】`role`、`status`、`avatar`、`id`**
>
> - `role` —— 后端**强制设成 `USER`**。前端页面也没有角色选择。
>   如果允许前端传 `role: "ADMIN"`，那谁都能给自己发管理员权限，整个权限体系当场作废。
> - `status` —— 后端**强制设成 `1`（正常）**。
>   （不要让 v2.0 那个"魔法值 `2` 表示全部"溜进来，`sys_user.status` 只有 `0` 和 `1`）

#### 返回

**成功**（HTTP 200）：

```json
{ "code": 1, "msg": "注册成功", "data": null }
```

> **设计决策：注册后不自动登录。**
> 前端收到成功后跳转到登录页，并把用户名带过去（`/login?username=wangwu`）方便用户少打一遍。
> 理由：注册和登录是两件事，自动登录会让"密码到底存对没有"这个问题被掩盖；
> 而且后端不用在这里重复签发 token 的逻辑，实现更简单。
>
> 如果以后想做「注册即登录」，把这个接口的 `data` 改成和 `/auth/login` 一样的
> `{ token, user }` 结构即可 —— 前端已经把两种情况的处理都留好了位置。

#### 错误返回（都是 HTTP 200 + `code:0`，沿用 v2.0 的约定）

| 场景 | msg |
|---|---|
| 用户名为空 | `用户名不能为空` |
| 用户名长度不对 | `用户名长度必须 3~50 个字符` |
| 用户名格式不对 | `用户名只能包含字母、数字、下划线` |
| **用户名已存在** | `用户名已存在` |
| 密码为空 / 太短 | `密码长度必须在 6 到 20 之间` |
| 姓名为空 | `姓名不能为空` |
| 手机号格式不对 | `手机号格式不正确` |
| 邮箱格式不对 | `邮箱格式不正确` |

> ⚠️ **不要**在错误里区分"用户名已存在"和"用户名可用"之外的敏感信息。
> 注册接口天然存在**用户名枚举**问题（拿一堆名字试，靠报错判断哪些已注册）。
> 这是自助注册无法避免的取舍 —— 但**绝不能**把邮箱、手机号是否已注册也暴露出来。

## 四、★ 后端实现要点（5 条，第 1 条最容易漏）

### 1. 🔴 必须把 `/auth/register` 加进拦截器白名单

否则这个接口永远返回 **401「未登录或登录已过期」** —— 因为没注册的人当然没有 token，
而 v2.0 的拦截器默认拦截 `/**`：

```java
// WebConfig.java
registry.addInterceptor(authInterceptor)
        .addPathPatterns("/**")
        // 登录和注册是【仅有的两个】不需要 token 的接口
        .excludePathPatterns("/auth/login", "/auth/register");   // ← 加上 /auth/register
```

> 这就是 v2.0 那个"放行路径写错就死锁"的坑的翻版：
> **忘了放行 → 没人能注册 → 但表现是"未登录"，很容易往鉴权方向查，其实是白名单漏了。**

### 2. 密码必须 BCrypt 加密，绝不能存明文

```java
String hash = BCrypt.hashpw(dto.getPassword(), BCrypt.gensalt());
```

### 3. 角色和状态由后端定死

```java
// ✅ 正确：后端说了算
user.setRole("USER");
user.setStatus(1);

// ❌ 错误：把前端传的 role 直接用 —— 这是提权漏洞
// user.setRole(dto.getRole());
```

### 4. 用户名唯一性

`sys_user` 表上已经有 `UNIQUE KEY uk_user_username`，但**建议先查一次**给出友好提示：

```java
if (userMapper.CountByUsername(username) > 0) {
    throw new BusinessException("用户名已存在");
}
```

> ⚠️ 如果直接撞唯一索引，会抛 `DuplicateKeyException`，而现在的
> `GlobalExceptionHandler.handleDuplicateKeyException()` 是**写死**返回「该 ISBN 已存在」的 ——
> 用户注册重复时会看到"ISBN 已存在"，莫名其妙。
> 要么用上面的预查挡住，要么顺手把这个 handler 改通用一点。

### 5. 校验规则要和前端保持一致

前端的校验在 [RegisterView.vue](../../library-web/src/views/register/RegisterView.vue) 里已经写好了，
后端**必须再校验一遍** —— 前端校验只是体验，绕过它太容易了（Postman 直接打接口）。

## 五、后端需要新增/改动的文件（清单）

| 文件 | 动作 | 说明 |
|---|---|---|
| `controller/Impl/RegisterController.java` | 🆕 | 或者把方法加到现有的 `LoginControllerImpl` 里（更省事） |
| `service/RegisterService.java` + `Impl` | 🆕 | 或者复用 `UserService.AddUser()` 的思路 |
| `pojo/dto/RegisterDto.java` | 🆕 | 5 个字段：username / password / realName / phone / email |
| `mapper/UserMapper.java` | 🔧 | 已有 `GetUserByUsername`、`Insert`，**基本可直接复用** |
| `config/WebConfig.java` | 🔧 | ★ 加 `/auth/register` 到 `excludePathPatterns` |

### 最省事的做法（推荐）

不需要新建 Service / Controller，**直接在现有的类里加一个方法**：

```java
// LoginControllerImpl.java 里加
@PostMapping("/auth/register")
public Result Register(@RequestBody RegisterDto dto) {
    loginService.Register(dto);
    return new Result().success("注册成功", null);
}
```

Service 里 90% 的逻辑和 `UserServiceImpl.AddUser()` 一样（校验 + 查重 + BCrypt + 插入），
唯一的区别是**角色写死 USER**、**不接收 role 字段**。

> 💡 顺带能修掉一个旧账：`UserServiceImpl.AddUser()` 现在用的是 `UserSelectDto`
> （查询用的 DTO，`status` 默认值是魔法值 `2`），插入时会把 `status=2` 写进库。
> 新建 `RegisterDto` / `UserSaveDto` 正好可以把这件事理顺。

## 七、联调自测清单

**注册接口**
- [ ] 不带 `Authorization` 头调 `POST /auth/register` → **200 注册成功**（不是 401！这条专门验白名单）
- [ ] 注册后用新账号能成功登录 → `POST /auth/login` 返回 token
- [ ] 查数据库，新用户的 `password` 是 `$2a$10$...` 开头（**不是明文 `123456`**）
- [ ] 查数据库，新用户的 `role = 'USER'`、`status = 1`
- [ ] 用已存在的用户名注册 → `用户名已存在`
- [ ] 密码传 5 位 → `密码长度必须在 6 到 20 之间`
- [ ] 密码传 21 位 → 同上
- [ ] 请求体里**故意加** `"role": "ADMIN"` → 注册出来的用户**仍然是 `USER`**（★ 提权测试，必做）
- [ ] 请求体里**故意加** `"status": 0` → 注册出来的用户**仍然是 `1`**

**前端**
- [ ] 登录页底部有「注册新用户」，点击跳到 `/register`
- [ ] 注册页能正常填写、校验（两次密码不一致会拦下）
- [ ] 注册成功后跳回登录页，**用户名已自动填好**
- [ ] 已登录状态下直接访问 `/register` → 被弹回 `/books`
- [ ] 注册页的「返回登录」能回到登录页
