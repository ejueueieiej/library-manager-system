## 〇、通用约定（先看这一节，后面所有接口都遵守）

### 0.1 两个路径不要搞混

| 概念 | 值 | 说明 |
|---|---|---|
| **后端接口路径** | `/books` | 你 Spring Boot 里 `@RequestMapping("/books")` 写的路径，用 Apifox 直连 `localhost:8081` 调试时用这个 |
| **前端请求路径** | `/api/books` | 前端统一加 `/api` 前缀；**开发环境**由 Vite 代理、**生产环境**由 nginx 反代，都会把 `/api` 剥掉再转发给 8081 |

这样做的好处：浏览器眼里所有请求都是同源，**永远不会有跨域（CORS）问题**，后端也不用配 `@CrossOrigin`。

```
浏览器  --/api/books-->  Vite(5173) 或 nginx(80)  --/books-->  Tomcat(8081)
```

### 0.2 统一返回体

**所有**接口（包括报错）都返回这个结构，HTTP 状态码一律 `200`：

```json
{
  "code": 1,
  "msg": "success",
  "data": null
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | Integer | **1 = 成功，0 = 失败**（业务失败，如「ISBN 已存在」） |
| `msg` | String | 提示语，前端直接弹窗显示 |
| `data` | 泛型 T | 业务数据；没有数据时为 `null` |

**特殊情况**：只有这三种才用非 200 的 HTTP 状态码

| HTTP | 场景 | 返回体 |
|---|---|---|
| `200` | 一切正常，**包括业务失败** | `{code:0, msg:"该 ISBN 已存在", data:null}` |
| `401` | 未登录 / token 失效（**2.0 才有**） | `{code:0, msg:"未登录", data:null}` |
| `500` | 服务器内部异常（空指针等） | `{code:0, msg:"服务器异常，请联系管理员", data:null}` |

> 为什么业务失败也用 200？因为前端的 axios 拦截器只写一次判断：`if (res.code === 1)` 成功，否则弹 `msg`。简单、不易漏。

### 0.3 分页约定

**请求**（所有分页接口都一样）：

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `pageNum` | Integer | 否 | 1 | 第几页，**从 1 开始**（不是 0） |
| `pageSize` | Integer | 否 | 10 | 每页几条 |

**响应**：`data` 固定为 `{ total, list }`

```json
{
  "code": 1,
  "msg": "success",
  "data": {
    "total": 8,
    "list": [ ]
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `total` | Long | 满足条件的**总记录数**（用来算总页数） |
| `list` | Array | 当前页的数据列表 |

### 0.4 数据格式约定

| 类型 | 格式 | 示例 |
|---|---|---|
| 日期 | `yyyy-MM-dd` | `"2016-09-01"` |
| 日期时间 | `yyyy-MM-dd HH:mm:ss` | `"2026-10-12 20:30:00"` |
| 金额 | 数字（两位小数） | `149.00` |
| 请求体 | `Content-Type: application/json` | |
| 查询参数 | URL 上的 query string | `/books?pageNum=1&name=Java` |

### 0.5 接口总览（按开发顺序，从易到难）

| # | 功能 | 方法 | 后端路径 | 难度 | 建议 |
|---|---|---|---|---|---|
| 1 | 查询全部分类 | GET | `/categories` | ⭐ | **先做这个**，无参数无分页，用来打通前后端链路 |

| 4 | 新增图书 | POST | `/books` | ⭐⭐ | 练 JSON 请求体 + 参数校验 + 唯一性校验 |
| 5 | 修改图书 | PUT | `/books/{id}` | ⭐⭐ | 练更新 + 存在性校验 |
| 6 | 删除图书 | DELETE | `/books/{id}` | ⭐ | 练物理删除 + 影响行数判断 |
| 7 | 批量删除 | DELETE | `/books/batch` | ⭐⭐ | 进阶，前端多选删除 |

**用途**：图书列表页的主查询。支持书名模糊、作者模糊、分类精确、状态精确，四个条件可以任意组合（都不传就是查全部）。

| 项 | 值 |
|---|---|
| 请求方法 | `GET` |
| 后端路径 | `/books` |
| 前端请求 | `/api/books` |

**前端向后端请求的数据**（URL query 参数，全部可选）：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `pageNum` | Integer | 否 | 第几页，默认 1 |
| `pageSize` | Integer | 否 | 每页几条，默认 10 |
| `name` | String | 否 | 书名，**模糊查询**（`LIKE %值%`） |

```json
        "author": "霍春阳",
```

**⚠️ 三个必须注意的点**：

1. **必须带 `categoryName`**：前端列表要显示分类名称，不是 id。用 `LEFT JOIN book_category` 查出来，别让前端自己再查一次。
2. **`LEFT JOIN` 别写成 `INNER JOIN`**：万一某本书的 `category_id` 在分类表里找不到（脏数据），`INNER JOIN` 会让这本书直接从列表里静默消失，这种 bug 极难排查；`LEFT JOIN` 至少还能看见它。
3. **排序**：建议 `ORDER BY b.create_time DESC, b.id DESC`（新加的排最前），否则分页顺序不稳定，翻页会看到重复数据。

### 4. 新增图书

| 项 | 值 |
|---|---|
| 请求方法 | `POST` |
| 后端路径 | `/books` |
| 前端请求 | `/api/books` |
| 请求头 | `Content-Type: application/json` |

**前端向后端请求的数据**（JSON 请求体）：

| 字段 | 类型 | 必填 | 校验规则 | 说明 |
|---|---|---|---|---|
| `isbn` | String | ✅ | 非空，≤20 字符 | 书号，全库不重复（未删除的里面） |
| `name` | String | ✅ | 非空，≤100 字符 | 书名 |
| `author` | String | ✅ | 非空，≤50 字符 | 作者 |
| `publisher` | String | ❌ | ≤100 字符 | 出版社 |
| `publishDate` | String | ❌ | `yyyy-MM-dd` | 出版日期 |
| `categoryId` | Integer | ✅ | 必须存在于 `book_category` | 分类 id |
| `price` | Number | ❌ | ≥ 0，两位小数 | 定价，不传默认 0 |
| `totalNum` | Integer | ✅ | ≥ 1 | 总册数 |
| `coverUrl` | String | ❌ | ≤255 字符 | 封面图地址 |
| `intro` | String | ❌ | 无限制 | 简介 |
| `status` | Integer | ❌ | 1 或 0 | 状态，不传默认 1（在架） |
| ~~`availableNum`~~ | — | ❌ | — | **前端不传**！后端自动 `availableNum = totalNum` |

**请求示例**：

```json
{
  "isbn": "9787111128069",
  "name": "重构：改善既有代码的设计",
  "author": "Martin Fowler",
  "publisher": "人民邮电出版社",
  "publishDate": "2019-04-01",
  "categoryId": 2,
  "price": 118.00,
  "totalNum": 3,
  "intro": "软件工程领域的经典著作，讲解如何安全地改善代码结构。",
  "status": 1
}
```

**你希望我返回的数据**：

```json
{ "code": 1, "msg": "新增成功", "data": null }
```

> `data` 可以返回新书的 id，但前端用不上（新增后会重新查列表），返回 `null` 最省事。

**可能的错误返回**：

| 场景 | 返回 |
|---|---|
| ISBN 已存在 | `{ "code": 0, "msg": "该 ISBN 已存在", "data": null }` |
| 分类不存在 | `{ "code": 0, "msg": "分类不存在", "data": null }` |
| 必填字段为空 | `{ "code": 0, "msg": "书名不能为空", "data": null }` |
| 总册数 < 1 | `{ "code": 0, "msg": "总册数至少为 1", "data": null }` |

**⚠️ 后端要做的校验（按顺序）**：

1. 参数校验（`@Valid` + `@NotBlank` / `@NotNull` / `@Min`）——由全局异常处理器统一转成 `code:0`
2. **ISBN 唯一性**：数据库已经加了唯一索引 `uk_book_isbn`，所以有**两种写法**：
   - **写法 A（推荐，能给出友好提示）**：先查一次 `SELECT COUNT(*) FROM book WHERE isbn = ?`，大于 0 就抛 `BusinessException("该 ISBN 已存在")`
   - **写法 B（更省事，靠数据库兜底）**：直接 insert，在全局异常处理器里捕获 `DuplicateKeyException`，也返回「该 ISBN 已存在」
   - 建议 **A + B 都写**：A 负责给用户看的友好提示，B 负责挡住并发情况下的漏网之鱼
3. **分类存在性**：`SELECT COUNT(*) FROM book_category WHERE id = ?`
4. `availableNum` 由后端赋值 = `totalNum`，**不要相信前端传的值**
5. `create_time` / `update_time` 交给 MySQL 默认值，Java 里不用管

### 5. 修改图书

| 项 | 值 |
|---|---|
| 请求方法 | `PUT` |
| 后端路径 | `/books/{id}` |
| 前端请求 | `/api/books/9` |

**前端向后端请求的数据**：路径参数 `id` + 请求体（字段与新增**完全一样**，也是那份 `BookSaveDTO`）

```json
{
  "isbn": "9787111128069",
  "name": "重构：改善既有代码的设计（第2版）",
  "author": "Martin Fowler",
  "publisher": "人民邮电出版社",
  "publishDate": "2019-04-01",
  "categoryId": 2,
  "price": 128.00,
  "totalNum": 5,
  "intro": "软件工程领域的经典著作。",
  "status": 1
}
```

**你希望我返回的数据**：

```json
{ "code": 1, "msg": "修改成功", "data": null }
```

**⚠️ `availableNum` 的坑（这是本接口最容易写错的地方）**

前端**不传** `availableNum`，后端要按「**已借出的册数不变**」来算：

```
已借出数 = 旧.totalNum - 旧.availableNum
新.availableNum = 新.totalNum - 已借出数
```

举例：原来 3 册、借出 1 册（可用 2），管理员把总册数改成 5 → 新可用数 = 5 - 1 = **4**。
如果直接 `availableNum = totalNum`，就会把「已借出」的那本书凭空变出来。1.0 阶段还没借阅功能，两种写法看不出差别，但 2.0 加上借阅后这就是**数据事故**。

**可能的错误返回**：`图书不存在` / `该 ISBN 已存在` / `分类不存在`

> **注意：改自己的 ISBN 不算冲突**。做唯一性预查时必须把自己排除掉，否则「只改价格、没动 ISBN」也会直接报「ISBN 已存在」，这是个必踩的坑：
>
> ```sql
> SELECT COUNT(*) FROM book WHERE isbn = #{isbn} AND id != #{id}
> ```

### 6. 删除图书（物理删除）

| 项 | 值 |
|---|---|
| 请求方法 | `DELETE` |
| 后端路径 | `/books/{id}` |
| 前端请求 | `/api/books/9` |

**前端向后端请求的数据**：路径参数 `id`（前端会先弹一个 `ElMessageBox.confirm` 二次确认）

**你希望我返回的数据**：

```json
{ "code": 1, "msg": "删除成功", "data": null }
```

**⚠️ 本项目用的是物理删除**（你确认过的方案），数据真的从表里消失：

```sql
DELETE FROM book WHERE id = #{id}
```

- 好处：表不会越用越大，而且 ISBN 能加**唯一索引**（逻辑删除时加不了），「书号不能重复」由数据库兜底最可靠
- 代价：删错了只能靠备份恢复，所以**前端必须保留二次确认弹窗**（已经写好了）
- 影响行数为 0（id 不存在）时返回 → `{ "code": 0, "msg": "图书不存在", "data": null }`
- ⚠️ **等 2.0 加了借阅记录表，这里要回来加一道校验**：先查这本书有没有「未归还」的借阅记录，有就拒绝删除并提示「该图书还有未归还的借阅，不能删除」，否则借阅记录会变成查不到书的孤儿数据

### 7. 批量删除（进阶）

| 项 | 值 |
|---|---|
| 请求方法 | `DELETE` |
| 后端路径 | `/books/batch` |
| 前端请求 | `/api/books/batch?ids=3,4,5` |

**前端向后端请求的数据**：query 参数 `ids`，**逗号分隔的 id 字符串**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `ids` | String | ✅ | 例如 `"3,4,5"` |

> 为什么用 `?ids=1,2,3` 而不是请求体？因为部分浏览器/网关对 `DELETE` 带 body 支持不一致，用 query 最稳。

**你希望我返回的数据**：

```json
{ "code": 1, "msg": "成功删除 3 本图书", "data": null }
```

**后端要点**：用 `@RequestParam List<Long> ids` 接收（Spring 会自动把逗号分隔的字符串转成 List），Mapper 里用 `<foreach>` 拼 `IN`：

```xml
<delete id="deleteBatch">
    DELETE FROM book WHERE id IN
    <foreach collection="ids" item="id" open="(" separator="," close=")">
        #{id}
    </foreach>
</delete>
```

```json
}
```

⚠️ **必须返回相对地址**（以 `/uploads` 开头），不要返回 `http://localhost:8081/uploads/xxx.jpg` 这种写死主机名的完整地址：

- 开发环境前端在 5173、生产环境在 nginx 的 80 端口，主机名一写死就会串味
- 相对地址由 Vite 代理 / nginx 反代统一转发，两种环境都不用改代码

**后端实现要点（5 步）**：

1. **Controller**：`@PostMapping("/files/upload")`，参数 `@RequestParam("file") MultipartFile file`
2. **校验**：文件非空、后缀在白名单内、大小 ≤ 5MB（**前端校验是防手滑，后端校验才是防攻击，两个都要**）
3. **存储**：存到项目外的固定目录，文件名用 `UUID + 后缀`，按日期分目录
   ```java
   String original = file.getOriginalFilename();          // 可能为 null，要判空
   String ext = original.substring(original.lastIndexOf("."));
   String datePath = LocalDate.now().format(DateTimeFormatter.ofPattern("yyyy/MM"));
   String fileName = UUID.randomUUID().toString().replace("-", "") + ext;
   File dir = new File("D:/library-uploads/" + datePath);
   dir.mkdirs();
   file.transferTo(new File(dir, fileName));
   return Result.success(Map.of("url", "/uploads/" + datePath + "/" + fileName));
   ```
   > **绝对不要用原始文件名**：中文乱码、重名覆盖、`../` 路径穿越，三个坑一次踩全。
4. **让浏览器能访问到这些图片**：加一个静态资源映射配置类
   ```java
   @Configuration
   public class WebConfig implements WebMvcConfigurer {
       @Override
       public void addResourceHandlers(ResourceHandlerRegistry registry) {
           registry.addResourceHandler("/uploads/**")
                   .addResourceLocations("file:D:/library-uploads/");
       }
   }
   ```
5. **`application.yml` 放开上传大小限制**（Spring Boot 默认单文件只有 1MB，传张封面图就爆了）：
   ```yaml
   spring:
     servlet:
       multipart:
         max-file-size: 5MB
         max-request-size: 10MB
   ```

⚠️ **上传目录不要放在项目里**（比如 `src/main/resources/static`）：`mvn clean` 打包会把它清掉。放项目外的固定目录最省心。

**可能的错误返回**：

| 场景 | 返回 |
|---|---|
| 文件为空 | `{ "code": 0, "msg": "请选择要上传的文件", "data": null }` |
| 格式不允许 | `{ "code": 0, "msg": "只支持 jpg / png / webp / gif 格式", "data": null }` |
| 超过 5MB | `{ "code": 0, "msg": "图片不能超过 5MB", "data": null }` |
| 被 Spring 提前拦下 | 在全局异常处理器里捕获 `MaxUploadSizeExceededException` → `Result.error("图片不能超过 5MB")` |

> 2.0 做了登录之后，这个接口要补上「必须登录才能上传」的校验。

| 属性 | 类型 | 校验注解 | 说明 |
|---|---|---|---|
| `isbn` | String | `@NotBlank(message="ISBN不能为空")` `@Size(max=20)` | 书号 |
| `name` | String | `@NotBlank(message="书名不能为空")` `@Size(max=100)` | 书名 |
| `author` | String | `@NotBlank(message="作者不能为空")` `@Size(max=50)` | 作者 |
| `publisher` | String | `@Size(max=100)` | 出版社 |
| `publishDate` | LocalDate | `@JsonFormat(pattern="yyyy-MM-dd")` | 出版日期 |
| `categoryId` | Integer | `@NotNull(message="请选择分类")` | 分类 id |
| `price` | BigDecimal | `@DecimalMin(value="0", message="定价不能为负")` | 定价 |

| `intro` | String | 无 | 简介 |
| `status` | Integer | 无（默认 1） | 状态 |

> **故意不放 `availableNum`**：它由后端算，前端传了也不认（见 5. 修改图书的说明）。
> 用 `@Valid @RequestBody BookSaveDTO dto` 接收，校验失败会被 `MethodArgumentNotValidException` 接住，在全局异常处理器里转成 `Result.error(第一条错误信息)`。

### 2.8 `BusinessException` + `GlobalExceptionHandler`

`BusinessException extends RuntimeException`，只带一个 `message` 字段（如「该 ISBN 已存在」）。

`GlobalExceptionHandler` 用 `@RestControllerAdvice`，至少处理三类：

| 异常 | 处理 | 返回 |
|---|---|---|
| `BusinessException` | 业务异常（自己抛的） | `Result.error(e.getMessage())`，HTTP 200 |
| `MethodArgumentNotValidException` | `@Valid` 校验失败 | `Result.error(第一个字段的错误提示)`，HTTP 200 |
| `Exception` | 兜底 | 打日志 + `Result.error("服务器异常")`，HTTP 200 |

> ⚠️ **业务失败一定要返回 HTTP 200**，只有真正的未登录（2.0）和服务器崩溃才用 401/500，否则前端拦截器会走错分支。

### 2.9 Mapper 接口

```java
@Mapper
public interface BookMapper {
    List<BookVO> list(BookQueryDTO query);            // 分页+多条件（PageHelper 自动加 limit）
    BookVO getById(Long id);                          // 详情（带 categoryName）
    int countByIsbn(@Param("isbn") String isbn, @Param("excludeId") Long excludeId);  // ISBN 唯一性预查
    int insert(Book book);                            // 新增
    int update(Book book);                            // 修改
    int deleteById(@Param("id") Long id);             // 物理删除单条  DELETE FROM book WHERE id = ?
    int deleteBatch(@Param("ids") List<Long> ids);    // 批量物理删除（XML 里用 <foreach>）
    int updateStatus(@Param("id") Long id, @Param("status") Integer status); // 上下架
}
```

> `countByIsbn` 的 `excludeId` 在**新增时传 null**，XML 里用 `<if test="excludeId != null"> AND id != #{excludeId} </if>` 判断即可，一个方法同时服务新增和修改。

### 3.3 PageHelper 的正确用法

```java
@Override
public PageResult<BookVO> page(BookQueryDTO query) {
    PageHelper.startPage(query.getPageNum(), query.getPageSize());  // 必须紧挨着查询语句
    List<BookVO> list = bookMapper.list(query);                     // 这一行才会被分页
    PageInfo<BookVO> info = new PageInfo<>(list);
    return new PageResult<>(info.getTotal(), info.getList());
}
```

⚠️ `PageHelper.startPage()` 后面**必须紧跟**那条要被分页的查询，中间不能插入别的查询，否则分页会作用到错误的对象上。

### 3.4 Mapper XML 的动态 SQL（列表查询参考）

```xml
<select id="list" resultType="org.libaray_manager_system.pojo.vo.BookVO">
    SELECT b.*, c.name AS category_name
    FROM book b
    LEFT JOIN book_category c ON b.category_id = c.id
    <where>
        <!-- 物理删除，所以这里没有 deleted = 0 这个条件 -->
        <if test="name != null and name != ''">
            AND b.name LIKE CONCAT('%', #{name}, '%')
        </if>
        <if test="author != null and author != ''">
            AND b.author LIKE CONCAT('%', #{author}, '%')
        </if>
        <if test="categoryId != null">
            AND b.category_id = #{categoryId}
        </if>
        <if test="status != null">
            AND b.status = #{status}
        </if>
    </where>
    ORDER BY b.create_time DESC, b.id DESC
</select>
```

> `<where>` 标签很聪明：它会自动吃掉第一个多余的 `AND`，而且**一个条件都没有时它什么都不拼**（不会留下孤零零的 `WHERE`）——所以"四个条件全不传 = 查全部"是天然成立的。

### 3.5 联调自测清单（写完接口按这个过一遍）
