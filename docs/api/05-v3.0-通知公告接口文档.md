## 一、这个模块解决什么问题

管理员需要一个**广播**渠道：闭馆安排、新书上架、活动预告、借阅规则调整。读者需要一个地方能看到它们。

"能发能看"只是及格线，真正决定表结构的是下面两个需求：

| 需求 | 落到哪里 |
|---|---|
| 重要通知不能被后来的消息挤下去 | `notice.is_top` + `ORDER BY is_top DESC, publish_time DESC` |
| 读者要知道"哪几条我还没看过" | `notice_read` 表 + 导航栏上的未读红点 |

**权限边界（2.0 定的规矩，这里照搬）：**

| 能力 | 谁有 |
|---|---|
| 发布 / 编辑 / 删除 / 置顶 | **仅管理员**（方法上打 `@RequireAdmin`） |
| 看列表、看详情、拿未读数 | 所有**已登录**用户（不加注解） |

> ⚠️ 前端会把"发布通知""删除"这些按钮对普通读者**隐藏**，但那只是体验。
> 真正拦人的是后端方法上那个 `@RequireAdmin` —— 用 Apifox 直接打接口是绕不过去的。

## 二、接口清单（7 个）

**建议按这个顺序开发**，理由是「从能立刻看到数据，到需要处理级联」：

|---|---|---|---|---|---|---|
| 1 | 通知分页列表 | `GET` | `/notices` | ✅ | ❌ | ⭐ |
| 2 | 通知详情（顺带标记已读） | `GET` | `/notices/{id}` | ✅ | ❌ | ⭐⭐ |
| 3 | 我的未读数量 | `GET` | `/notices/unread-count` | ✅ | ❌ | ⭐ |
| 4 | 发布通知 | `POST` | `/notices` | ✅ | ✅ | ⭐⭐ |
| 5 | 编辑通知 | `PUT` | `/notices/{id}` | ✅ | ✅ | ⭐⭐ |

> 比憋到最后再回归要舒服得多。

## 三、接口详情

### 接口 1 · 通知分页列表

| 项 | 值 |
|---|---|
| 请求方法 | `GET` |
| 后端路径 | `/notices` |
| 前端请求 | `/api/notices` |
| 需要登录 | ✅ |
| 需要管理员 | ❌ |

#### 前端发过来的数据（query 参数，**全部可选**）

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `pageNum` | Integer | `1` | 页码 |
| `pageSize` | Integer | `10` | 每页条数 |
| `keyword` | String | 空 | **标题或正文**模糊匹配（二选一命中即可） |
| `type` | Integer | 空 | 1公告 / 2通知 / 3活动 |
| `onlyTop` | Integer | 空 | 传 `1` 表示**只看置顶** |
| `status` | Integer | 空 | ★**只对管理员生效**：1已发布 / 0已下架。普通读者无论传什么，后端都强制当 `1` |

```
GET /api/notices?pageNum=1&pageSize=10&keyword=国庆&type=1&onlyTop=1
```

> ⚠️ **`status` 这行"只对管理员生效"不是可选项，是安全要求。**
> 如果不做这个强制，普通读者只要把 URL 改成 `?status=0`，就能看到管理员**已经下架**的通知。
> 正确写法就一行（见第五节要点 4）。
>
> 顺带说清楚：为什么还要给管理员留 `status` 这个筛选？
> 因为管理员需要"只看已下架的"，把之前撤下来的通知翻出来改一改再发布。

#### 你希望我返回的数据

```json
{
  "code": 1,
  "msg": "success",
  "data": {
    "total": 4,
    "list": [
      {
        "id": 1,
        "title": "图书馆国庆假期开放安排",
        "summary": "10 月 1 日至 3 日全馆闭馆，10 月 4 日起恢复正常开放。",
        "type": 1,
        "isTop": 1,
        "status": 1,
        "publisherName": "系统管理员",
        "publishTime": "2026-09-28 09:00:00",
        "isRead": 0
      },
      {
        "id": 4,
        "title": "读书月活动预告：好书共读计划",
        "summary": "本月将举办\"好书共读\"活动，参与者可优先借阅指定书目……",
        "type": 3,
        "isTop": 0,
        "status": 1,
        "publisherName": "系统管理员",
        "publishTime": "2026-10-11 16:40:00",
        "isRead": 1
      }
    ]
  }
}
```

**`data` 里每个字段的含义（也就是 `NoticeVo` 该有哪些属性）：**

| 字段 | 类型 | 从哪来 | 说明 |
|---|---|---|---|
| `total` | Integer | `COUNT(*)` | 总条数，**必须和 list 用同一套 where 条件**（见要点 6） |
| `list` | Array | 查询结果 | 见下 |
| `id` | Long | `notice.id` | |
| `title` | String | `notice.title` | |
| `summary` | String | `LEFT(notice.content, 60)` | **列表只给摘要，不给全文**（见要点 5） |
| `type` | Integer | `notice.type` | 1/2/3；**中文文案由前端映射**，后端不用管（见第六节） |
| `isTop` | Integer | `notice.is_top` | 1置顶 / 0普通 |
| `status` | Integer | `notice.status` | 1已发布 / 0已下架（管理员列表上要显示"已下架"标记） |
| `publisherName` | String | `sys_user.real_name`，为空时退回 `username` | 发布人 |
| `publishTime` | String | `notice.publish_time` | 格式 `yyyy-MM-dd HH:mm:ss` |
| `isRead` | Integer | `notice_read` 里有没有这一行 | 1已读 / 0未读；**管理员恒为 1** |

> **`isRead` 是给谁用的？** 给普通读者的列表 —— 有它才能在标题左边点一个小圆点表示"没看过"。
> 管理员看通知是"审阅自己发的东西"，不需要已读概念，所以后端对管理员直接返回 1。

**错误返回**：没有。查不到就是 `total: 0` + `list: []`，前端显示空状态。

### 接口 2 · 通知详情（顺带标记已读）

| 项 | 值 |
|---|---|
| 请求方法 | `GET` |
| 后端路径 | `/notices/{id}` |
| 前端请求 | `/api/notices/1` |
| 需要登录 | ✅ |
| 需要管理员 | ❌ |

#### 前端发过来的数据

一个路径参数 `id`（Long）。**没有请求体**。

#### ★ 这个接口有一个副作用：标记已读

普通读者打开详情时，后端**顺手往 `notice_read` 插一行**：

```sql
INSERT IGNORE INTO notice_read (notice_id, user_id) VALUES (#{noticeId}, #{userId});
```

`INSERT IGNORE` 靠的是建表时那个 `uk_notice_user` 唯一索引 ——
同一篇通知反复打开只会有一行，**天然幂等**，不用先查再插。

| 访问者 | 要不要插已读 |
|---|---|
| 普通读者（USER） | ✅ 插 |
| 管理员（ADMIN） | ❌ **不插**（管理员不参与已读统计，插了反而会让他自己的未读数永远算不清） |

> **为什么把"标记已读"塞进详情接口，而不单独开一个 `PATCH /notices/{id}/read`？**
> 因为这两个动作在业务上永远同时发生 —— 不可能"我看了详情但没读"。
> 拆成两个接口，前端就多一次可能失败的请求，还得处理"详情拿到了但已读没标上"的中间态。
> 合在一起，一次请求一个事务，最简单。

#### 你希望我返回的数据

```json
{
  "code": 1,
  "msg": "success",
  "data": {
    "id": 1,
    "title": "图书馆国庆假期开放安排",
    "content": "10 月 1 日至 3 日全馆闭馆，10 月 4 日起恢复正常开放。\n闭馆期间自助还书机暂停使用，到期图书请提前归还或办理续借。\n由此带来不便，敬请谅解。",
    "type": 1,
    "isTop": 1,
    "status": 1,
    "publisherName": "系统管理员",
    "publishTime": "2026-09-28 09:00:00",
    "updateTime": "2026-09-28 09:00:00",
    "isRead": 1
  }
}
```

**`NoticeDetailVo` 属性表**（比列表多 `content` / `updateTime`，少 `summary`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | Long | |
| `title` | String | |
| `content` | String | **完整正文**，含换行符；前端按 `\n` 分段渲染 |
| `type` | Integer | 1/2/3 |
| `isTop` | Integer | 1/0 |
| `status` | Integer | 1已发布 / 0已下架 |
| `publisherName` | String | 发布人姓名 |
| `publishTime` | String | 首次发布时间 |
| `updateTime` | String | 最后修改时间（前端显示"最后编辑于…"，没编辑过就和 publishTime 相同） |
| `isRead` | Integer | 普通读者恒为 1（这次的请求刚把它标成已读）；管理员恒为 0（不记已读） |

> 字段名和表列的对应关系：`real_name` → `realName`、`is_top` → `isTop`、`publish_time` → `publishTime`。
> 这个自动映射**你已经在用了**（`UserMapper.xml` 里 `SELECT *` 直接映射 `UserVo` 就是靠它），
> 本项目 `application.yml` 里 MyBatis 的下划线转驼峰是开着的，不用额外配置。

#### 错误返回（都是 HTTP 200 + `code:0`）

| 场景 | `msg` |
|---|---|
| id 不存在 | `通知不存在` |
| 通知已下架，且访问者是**普通读者** | `通知不存在或已下架` |

> **管理员访问已下架通知要能正常打开** —— 他得进来编辑、重新发布。
> 所以"已下架"这道判断**只对普通读者生效**。

### 接口 3 · 我的未读数量

| 项 | 值 |
|---|---|
| 请求方法 | `GET` |
| 后端路径 | `/notices/unread-count` |
| 前端请求 | `/api/notices/unread-count` |
| 需要登录 | ✅ |
| 需要管理员 | ❌ |

#### 前端发过来的数据

**什么都没有**。是谁在问，由 token 决定 ——
**绝对不要做成 `GET /notices/unread-count?userId=2`**，那又是水平越权。

#### 你希望我返回的数据

`data` 就是**一个裸数字**（不包对象，省一个类）：

```json
{ "code": 1, "msg": "success", "data": 2 }
```

含义：`status = 1` 的通知里，**还没有**出现在我 `notice_read` 里的条数。

| 访问者 | 返回值 |
|---|---|
| 普通读者 | 真实未读数 |
| 管理员 | **恒为 0**（他不记已读，未读数没有意义） |

#### ★★ 路径冲突警告（这条最容易踩）

`/notices/unread-count` 和 `/notices/{id}` **长得一模一样**。
如果 Spring 把 `unread-count` 当成 `{id}` 去转 Long，你会看到：

```
HTTP 500  Failed to convert value of type 'java.lang.String' to required type 'java.lang.Long'
         （或者 MethodArgumentTypeMismatchException）
```

**好消息：按 Spring 的路径匹配规则，这个写法是安全的。**
Spring 6（Boot 4 用的就是它）在多个模式都能匹配时，选**更具体**的那个：
字面量路径段 `unread-count` 比模板变量 `{id}` 更具体 → 优先命中 `unread-count`。

**但如果你真的撞上了 500**，别怀疑人生，直接把路径改成这个，前端也改一行：

| | 后端路径 | 前端 `notice.js` |
|---|---|---|
| 现在 | `/notices/unread-count` | `request.get('/notices/unread-count')` |
| 备选 | `/notices/unread/count` | `request.get('/notices/unread/count')` |

### 接口 4 · 发布通知

| 项 | 值 |
|---|---|
| 请求方法 | `POST` |
| 后端路径 | `/notices` |
| 前端请求 | `/api/notices` |
| 需要登录 | ✅ |
| 需要管理员 | ✅ **方法上要打 `@RequireAdmin`** |

#### 前端发过来的数据（JSON 请求体）

| 字段 | 类型 | 必填 | 校验规则 | 说明 |
|---|---|---|---|---|
| `title` | String | ✅ | 非空，≤100 字 | 标题 |
| `content` | String | ✅ | 非空 | 正文，可以带换行 |
| `type` | Integer | ✅ | 只能是 1 / 2 / 3 | 1公告 2通知 3活动 |
| `isTop` | Integer | ❌ | 只能 0 / 1 | 不传按 `0` |
| `status` | Integer | ❌ | 只能 0 / 1 | 不传按 `1`（立即发布）；传 `0` 就是先存着不公开 |

```json
{
  "title": "关于图书馆冬季开放时间调整的通知",
  "content": "自 11 月 1 日起，开馆时间调整为 08:30，闭馆时间调整为 21:00。\n周末照常开放。",
  "type": 2,
  "isTop": 0,
  "status": 1
}
```

> ⚠️ **请求体里【没有】这几个字段，一个都不能收：**
>
> | 不能收的字段 | 为什么 | 后端该怎么做 |
> |---|---|---|
> | `publisherId` | 谁能发通知由 token 决定。收了它，任何管理员都能**冒名**别人发通知 | `loginUser.getId()` |
> | `publishTime` | 发布时间是"服务器现在几点"，不是前端说了算 | `new Date()` / SQL 里的 `NOW()` |
> | `createTime` / `updateTime` | 数据库自动维护 | 交给 `DEFAULT CURRENT_TIMESTAMP` |
> | `id` | 新增不该带 id | 自增 |
>
> 这条和 2.1 注册文档里「请求体里没有 `role`」是同一类问题：
> **凡是"身份"和"时间"这类事实性字段，一律后端说了算。**

#### 你希望我返回的数据

```json
{ "code": 1, "msg": "发布成功", "data": { "id": 5 } }
```

`data` 里回一个新通知的 id，方便前端知道刚发的是哪条。
**如果你嫌麻烦返回 `null` 也完全可以** —— 前端只用 `msg`，不会读这个 `id`。

#### 错误返回

| 场景 | `msg` |
|---|---|
| 标题为空 | `标题不能为空` |
| 标题超长 | `标题长度不能超过 100 个字符` |
| 正文为空 | `正文不能为空` |
| 类型不在 1/2/3 | `通知类型不正确` |
| isTop / status 不是 0 或 1 | `置顶标记只能是 0 或 1` / `状态只能是 0 或 1` |

### 接口 5 · 编辑通知

| 项 | 值 |
|---|---|
| 请求方法 | `PUT` |
| 后端路径 | `/notices/{id}` |
| 前端请求 | `/api/notices/5` |
| 需要登录 | ✅ |
| 需要管理员 | ✅ |

#### 前端发过来的数据

路径参数 `id`，请求体和**接口 4 完全一样**（`title` / `content` / `type` / `isTop` / `status`）。

```json
{
  "title": "关于图书馆冬季开放时间调整的通知（已更新）",
  "content": "自 11 月 1 日起，开馆时间调整为 08:30……（补充：法定节假日另行通知）",
  "type": 2,
  "isTop": 1,
  "status": 1
}
```

> ⚠️ **编辑时这三个字段不能动（后端要主动忽略，而不是"前端不传"）：**
>
> | 字段 | 为什么不动 |
> |---|---|
> | `publisher_id` | 改通知的人不一定是当初发的人。让"发布人"跟着变，历史就乱了 |
> | `publish_time` | 它表示"这条是什么时候发出去的"。编辑属于小修小补，不该刷新它 |
> | `create_time` | 数据库维护 |
>
> **编辑也【不清空】已读记录**，理由：一条通知读过了就是读过了，
> 管理员随手改个错别字，不该让所有人的红点重新亮起来。
> 如果你确实想让全体重新注意，正确做法是**删掉重发**（或者以后专门加个"重新发布"按钮，顺手清 `notice_read`）。

#### 你希望我返回的数据

```json
{ "code": 1, "msg": "修改成功", "data": null }
```

#### 错误返回

| 场景 | `msg` |
|---|---|
| id 不存在 | `通知不存在` |
| 其他 | 同接口 4 的校验提示 |

### 接口 6 · 置顶 / 取消置顶

| 项 | 值 |
|---|---|
| 请求方法 | `PATCH` |
| 后端路径 | `/notices/{id}/top` |
| 前端请求 | `/api/notices/1/top?isTop=1` |
| 需要登录 | ✅ |
| 需要管理员 | ✅ |

#### 前端发过来的数据

| 位置 | 名称 | 类型 | 说明 |
|---|---|---|---|
| 路径 | `id` | Long | 通知 id |
| query | `isTop` | Integer | `1` 置顶 / `0` 取消置顶 |

> **为什么用 query 而不是请求体？** 因为这是"改一个开关"，
> 和 1.0 已有的 `PATCH /books/{id}/status?status=0`、2.0 的 `PATCH /users/{id}/status?status=1`
> **保持同一个套路** —— 三个接口一个写法，前端和你的记忆都省事。

#### 你希望我返回的数据

```json
{ "code": 1, "msg": "已置顶", "data": null }
```

取消时 `msg` 是 `已取消置顶`。

#### 错误返回

| 场景 | `msg` |
|---|---|
| `isTop` 不是 0/1 | `置顶标记只能是 0 或 1` |
| id 不存在 | `通知不存在` |

> 🔴 **别照抄 `UserController.UpdateStatus` 的写法。**
> 那里写的是：
> ```java
> Integer result = userService.UpdateStatus(id, status, loginUser);
> if (result == 0) { return new Result().error("已禁用"); }   // ← 这里有问题
> return new Result().success("已启用");
> ```
> 它把「**受影响行数**」当成了「**新状态值**」来用。后果是：
> `UPDATE` 改动 0 行（比如目标状态和当前一样，MySQL 会返回 0）时会走 `error()`，
> 而 `error()` 返回的是 `code: 0` —— **前端拦截器看到 `code != 1` 会当成失败弹红字，
> 并把开关回滚**。前端期待的是"无论置顶还是取消，都返回 `code: 1` + 对应文案"。
>
> 这个接口（以及 6 号借阅接口）请写成：
> ```java
> noticeService.UpdateTop(id, isTop);
> return new Result().success(isTop == 1 ? "已置顶" : "已取消置顶", null);
> ```

### 接口 7 · 删除通知

| 项 | 值 |
|---|---|
| 请求方法 | `DELETE` |
| 后端路径 | `/notices/{id}` |
| 前端请求 | `/api/notices/5` |
| 需要登录 | ✅ |
| 需要管理员 | ✅ |

#### 前端发过来的数据

只有路径参数 `id`。**没有请求体**。

> 本期**不做批量删除**。1.0 图书那个"批量删除"按钮在 2.0 时因为后端没有
> `DELETE /books/batch` 而一直是个摆设 —— 这个坑没必要在通知上再挖一遍。
> 真要批量删，等 `DELETE /books/batch` 补上了，照抄即可。

#### ★ 这是唯一需要"级联"的接口

通知删掉之后，`notice_read` 里指向它的行就成了**孤儿**（永远查不到、也不会被清理）。
所以删除必须**两步一起做**，并且加事务：

```sql
DELETE FROM notice_read WHERE notice_id = #{id};
DELETE FROM notice WHERE id = #{id};
```

```java
@Transactional   // ★ 两步要么都成，要么都不做；删了一半是最难受的状态
public void DeleteNotice(Long id) { ... }
```

> 🔴 **不加 `@Transactional` 会怎样？** 第一条删成功、第二条因为某种原因失败（比如外键、连接抖动），
> 结果通知还在、已读记录没了 —— 所有读者这条通知全变未读，红点莫名其妙冒出来。
> 事务就是为这种"两个动作必须同生共死"的场景存在的。

#### 你希望我返回的数据

```json
{ "code": 1, "msg": "删除成功", "data": null }
```

| 场景 | `msg` |
|---|---|
| id 不存在 | `通知不存在` |

## 五、★ 后端实现要点（7 条，第 1、2 条最容易出事）

### 1. 🔴 列表的 JOIN 条件**必须写在 `ON` 后面，不能写在 `WHERE` 里**

这是本模块最大的坑。列表要同时拿到「发布人姓名」和「我读没读过」：

```sql
SELECT n.id,
       n.title,
       LEFT(n.content, 60)                                  AS summary,
       n.type,
       n.is_top,
       n.status,
       COALESCE(u.real_name, u.username)                    AS publisher_name,
       n.publish_time,
       CASE WHEN r.id IS NULL THEN 0 ELSE 1 END             AS is_read
FROM notice n
         LEFT JOIN sys_user    u ON u.id = n.publisher_id
         -- ★★ 下面这个条件只能写在这里（ON），不能挪到 WHERE
         LEFT JOIN notice_read r ON r.notice_id = n.id AND r.user_id = #{userId}
<where>
    <if test="dto.status != null">AND n.status = #{dto.status}</if>
    <if test="dto.type   != null">AND n.type   = #{dto.type}</if>
    <if test="dto.onlyTop != null and dto.onlyTop == 1">AND n.is_top = 1</if>
    <if test="dto.keyword != null and dto.keyword != ''">
        AND (n.title LIKE CONCAT('%', #{dto.keyword}, '%')
             OR n.content LIKE CONCAT('%', #{dto.keyword}, '%'))
    </if>
</where>
ORDER BY n.is_top DESC, n.publish_time DESC
LIMIT #{startIndex}, #{dto.pageSize}
```

**为什么？** 把 `r.user_id = #{userId}` 写到 `WHERE` 里，`LEFT JOIN` 会**当场退化成 `INNER JOIN`**：

```
LEFT JOIN：先保留 notice 所有行，能配上 notice_read 就配上，配不上留 NULL
           → 我读过的配上、没读过的留 NULL → "没读过的"还在，is_read 是 0 ✅

写到 WHERE：SQL 先做完 LEFT JOIN（未读的那些 r.* 是 NULL），
           再用 WHERE r.user_id = 2 过滤 → NULL = 2 不成立 → 未读的全被删掉 ❌
           结果就是：列表里只剩我【已经读过】的通知，越读越少，红点也永远点不掉
```

症状极具迷惑性：**"我读过的通知都好好的，没读过的反而看不见了。"**

> 📌 **顺带修个老毛病**：`WHERE` 里 `n.content LIKE ...` 这种
> 「列名带表别名」的写法，在有 JOIN 的查询里**必须加**；只查一张表时可以省。

### 2. 🔴 `count` 和 `list` 的 where 条件必须**逐字一致**

**2.0 现有代码这里有个真 bug，别学它。** `UserController.GetUsers` 是这么写的：

```java
List<UserVo> userVos = userService.GetUsers(userSelectDto);  // 带筛选条件
Integer total = userService.GetUserCount();                  // ← 没带条件！SELECT COUNT(*) FROM sys_user
```

后果：管理员搜「张三」，列表只有 1 行，但页脚显示「共 3 条」，分页器也会多出两页空白页。

**正确做法**：把 `count` 和 `list` 的 `<where>` 抽成一段 `<sql>` 片段，两边 `<include>` 同一个：

```xml
<sql id="noticeWhere">
    <where>
        <if test="dto.status != null">AND n.status = #{dto.status}</if>
        <if test="dto.type   != null">AND n.type   = #{dto.type}</if>
        <if test="dto.onlyTop != null and dto.onlyTop == 1">AND n.is_top = 1</if>
        <if test="dto.keyword != null and dto.keyword != ''">
            AND (n.title LIKE CONCAT('%', #{dto.keyword}, '%')
                 OR n.content LIKE CONCAT('%', #{dto.keyword}, '%'))
        </if>
    </where>
</sql>

<!-- 总数：只查一张表，不需要 JOIN sys_user / notice_read -->
<select id="GetNoticeCount" resultType="java.lang.Integer">
    SELECT COUNT(*) FROM notice n
    <include refid="noticeWhere"/>
</select>
```

> 💡 **count 不需要 JOIN** —— 但 `<include>` 里引用了 `n.status`、`n.title`，
> 所以 `FROM notice n` 的别名 `n` **必须留着**，否则 SQL 报「未知列 n.status」。
> 这也是为什么 count 里写 `FROM notice n` 而不是 `FROM notice`。

### 3. 普通读者必须被**强制**成 `status = 1`

```java
// NoticeServiceImpl.GetNotices / GetNoticeCount 的第一行
if (!loginUser.isAdmin()) {
    dto.setStatus(1);   // ★ 不是"默认值"，是【覆盖】：前端传 0 也给你改成 1
}
```

不加这一行的后果：普通读者访问 `/api/notices?status=0`，
就能看到管理员**已经撤下来**的通知。虽然通知一般不是机密，
但"前端不给我传"从来不是安全措施，**后端不认这个参数**才是。

### 4. 详情接口的三道判断，顺序不能乱

```java
public NoticeDetailVo GetNoticeById(Long id, LoginUser loginUser) {
    // ① 先查，不存在直接抛
    Notice notice = noticeMapper.GetNoticeEntityById(id);
    if (notice == null) {
        throw new BusinessException("通知不存在");
    }

    // ② 已下架的通知：管理员能看（要编辑），普通读者当"不存在"
    if (notice.getStatus() == 0 && !loginUser.isAdmin()) {
        throw new BusinessException("通知不存在或已下架");
    }

    // ③ 只有普通读者才记已读，且【必须幂等】
    if (!loginUser.isAdmin()) {
        noticeMapper.InsertRead(id, loginUser.getId());   // 内部是 INSERT IGNORE
    }

    return noticeMapper.GetNoticeById(id, loginUser.getId());
}
```

> ⚠️ 第 ③ 步放在第 ② 步之后 —— 反过来的话，
> 一篇不存在的通知也会先给你插一条已读记录（外键没建，数据库不会拦你，脏数据就这么进去了）。

### 5. 列表**不要**返回 `content` 全文

一页 10 条通知，每条正文按 500 字算，一回就是 5000 字 —— 而这个列表页**一个字都不显示**（只显示标题）。
用 `LEFT(content, 60)` 给个摘要足够了。

这不是性能问题（课程项目的数据量小到看不出来），是**接口设计问题**：
详情接口存在的意义就是"需要全文的时候再去拿"。
如果列表已经把全文给了，详情接口就没有存在的必要了 —— 那才是真正的设计失误。

### 6. 新增时，"谁发的、什么时候发的"由后端定死

```java
Notice notice = new Notice();
notice.setTitle(dto.getTitle());
notice.setContent(dto.getContent());
notice.setType(dto.getType());
notice.setIsTop(dto.getIsTop() == null ? 0 : dto.getIsTop());
notice.setStatus(dto.getStatus() == null ? 1 : dto.getStatus());
// ★ 这两行是重点：绝对不能用 dto 里的值
notice.setPublisherId(loginUser.getId());
notice.setPublishTime(LocalDateTime.now());
```

`publishTime` 也可以干脆不设，让数据库的 `DEFAULT CURRENT_TIMESTAMP` 填 —— 两种都行，
**但不能让它来自请求体**。

### 7. 删除要走事务，并且**顺手把已读记录一起删**

见接口 7 的说明。这是本模块唯一需要 `@Transactional` 的地方。
