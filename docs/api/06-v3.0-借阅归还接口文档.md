## 一、这个模块解决什么问题

到这里系统才算真的像个图书馆：**书能被借走、能还回来、能被追讨**。

好消息：**`book` 表一行都不用改** —— 1.0 建表时就留好了 `available_num`（在馆可借册数），
当时的注释写的是"给借阅功能预留"。

| 已有字段 | 本模块怎么用 |
|---|---|
| `book.total_num` | 馆藏总册数（不变） |
| `book.available_num` | **在馆可借册数**：借出 `-1`，归还 / 撤销 `+1` |

### ★★ 本模块的设计原则：谁在实物旁边，谁才能改变库存

这条原则决定了每个接口的权限，值得单独讲清楚。

| 动作 | 谁操作 | 为什么 |
|---|---|---|
| **还书** | **仅管理员** | 用户在家点一下"已归还"，`available_num` 就 +1，而书还在他手上。更严重的是：记录立刻变成"已归还"，**系统里再也查不出这本书在谁那儿** —— 追责凭证被销毁，而且不可逆。 |
| **借书** | 用户可自助 | 同样会产生"假事实"（点了借书却没来取，书被虚拟占着），但**凭证还在**（记录是"借出中"，借阅人明确），而且**可撤销**。 |
| **撤销借阅** | 仅管理员 | 给"线上借了不来取"一个出口：书回库存，记录置为"已取消"。 |
| **续借** | 用户可自助 | 不涉及实物，只改应还日期，且已有"只能续 1 次 + 逾期不能续"的限制，风险为零。 |

一句话：**还书销毁凭证 → 必须管理员；借书凭证尚存 → 可以自助，但要能撤销。**

### 已确认的产品决策

| 决策 | 结果 |
|---|---|
| 借阅模式 | ✅ 用户**自助借书**，立即借出（不需要审批） |
| **还书方式** | ✅ **用户不能自助还书**，必须由管理员确认（线下还书 → 管理员确认） |
| **归还日期** | ✅ 管理员确认时**可以填实际归还日期**，默认今天 |
| **撤销借阅** | ✅ 管理员可以撤销"线上借了没来取"的记录 |
| 续借 | ✅ 保留给用户自助（1 次，+30 天） |

### 规则常量（都在后端，改一行即生效）

| 规则 | 默认值 | 改哪里 |
|---|---|---|
| 借期 | **30 天** | `BorrowServiceImpl.BORROW_DAYS = 30` |
| 续借 | **1 次**，每次 **+30 天** | `MAX_RENEW = 1` / `RENEW_DAYS = 30` |
| 每人同时可借 | **5 本** | `MAX_BORROW = 5` |
| 逾期 | 只标记、**不罚款**（课程项目没有支付环节） | —— |

## 二、状态机（三态）

| `status` | 含义 | `available_num` | `return_time` | 谁能造成 |
|---|---|---|---|---|
| **1** | 借出中 | 已扣 | `NULL` | 用户自助借书 |
| **2** | **已归还** | 已回 | **有值**（管理员填的实际归还日期） | **仅管理员确认** |
| **3** | **已取消** | 已回 | `NULL`（书从未离馆，谈不上"归还时间"） | **仅管理员撤销** |

**几个连带定义：**

| 概念 | 定义 |
|---|---|
| 在借数量 | `status = 1` 的条数 |
| 逾期 | `status = 1 AND due_time < NOW()` |
| 「这人能再借这本书吗」 | 同一本书还有 `status = 1` 的记录 → 不能 |
| 累计借阅次数 | `status IN (1, 2)` —— **不含已取消**（没借成，不算借过） |

> **物理删除的边界**：管理员可以删掉**非借出中**（`status = 2` / `3`）的记录 ——
> 这是一个**备用通道**，只用于清理测试数据或订正误操作（接口 8）。
> **借出中的记录删不掉**：删了它，`available_num` 会永远少一本，
> 而"这本书在谁手上"的凭证也没了。详见接口 8。

> ⚠️ **不给"已取消"做物理删除，是刻意的。** 撤销如果直接 `DELETE` 记录，
> 就等于"凭证被销毁" —— 和自助还书是同一个错误，只是换了个入口，
> 而且用户会发现记录凭空消失。

| 3 | 我的借阅统计 | `GET` | `/borrows/my/summary` | ✅ | ❌ | ⭐ |

| 7 | **撤销借阅** | `PATCH` | `/borrows/{id}/cancel` | ✅ | ✅ **仅管理员** | ⭐⭐ |
| 8 | **删除借阅记录**（备用通道） | `DELETE` | `/borrows/{id}` | ✅ | ✅ **仅管理员** | ⭐⭐ |

**另外有两处"改动"不在接口清单里，但必须做**（见第七节）：

| 改动 | 文件 | 为什么 |
|---|---|---|
| 🔴 删书前检查有没有未归还的借阅 | `BookServiceImpl` | 1.0 就写下的欠账 |
| 🔴 注销 / 删用户前检查有没有未归还的图书 | `UserServiceImpl` | 2.2 文档里标了"3.0 重新评估" |

> 借阅记录是**账本**，默认只增不删。接口 8 那个删除是**备用通道**（清理测试数据、订正误操作），
> 而且**只允许删非借出中的记录** —— 详见接口 8。

### 接口 1 · 借书

| 项 | 值 |
|---|---|
| 请求方法 | `POST` |
| 后端路径 | `/borrows` |
| 前端请求 | `/api/borrows` |
| 需要登录 | ✅ |
| 需要管理员 | ❌（读者自己借） |

#### 前端发过来的数据

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `bookId` | Integer | ✅ | 要借的图书 id |

```json
{ "bookId": 3 }
```

> ⚠️ **请求体里【没有】`userId` / `borrowTime` / `dueTime` / `status`：**
> 谁借的由 token 决定（收了 `userId` 就能替别人借书，把别人的额度占满）；
> 借出时间用数据库 `NOW()`；应还时间由后端算 `borrowTime + 30 天`；新记录必然是"借出中"。

#### 你希望我返回的数据

```json
{ "code": 1, "msg": "借阅成功", "data": null }
```

`data` 返回 `null` 就行。想让页面直接提示"请于 11-11 前归还"，让 Service 把算好的
`dueTime` 返回、`data` 传 `{ dueTime: "..." }` 也可以 —— 前端两种都能接。

#### 错误返回（HTTP 200 + `code:0`）

| 场景 | `msg` |
|---|---|
| `bookId` 为空 | `请选择要借阅的图书` |
| 图书不存在 | `图书不存在` |
| 图书已下架 | `该图书已下架，暂不可借阅` |
| 同一人已借这本还没还 | `你已借阅该书且尚未归还` |
| 在借数量到上限 | `最多同时借阅 5 本，请先归还部分图书` |
| **这本书可借数为 0** | `该图书暂无可借库存` |

### 接口 3 · 我的借阅统计

| 项 | 值 |
|---|---|
| 请求方法 | `GET` |
| 后端路径 | `/borrows/my/summary` |
| 前端请求 | `/api/borrows/my/summary` |
| 需要登录 | ✅ |
| 需要管理员 | ❌ |

#### 前端发过来的数据

**什么都没有**（"我是谁"由 token 决定）。

#### 你希望我返回的数据

```json
{
  "code": 1,
  "msg": "success",
  "data": { "borrowingCount": 2, "overdueCount": 1, "totalCount": 9 }
}
```

| 字段 | 含义 | SQL |
|---|---|---|
| `borrowingCount` | 当前在借几本 | `COUNT(*) WHERE user_id=? AND status=1` |
| `overdueCount` | 其中已逾期几本 | `... AND status=1 AND due_time < NOW()` |
| `totalCount` | 累计借阅过几本 | `... AND status IN (1, 2)` ← **不含已取消** |

> 这个接口是**页面要求倒逼出来的**：「我的借阅」页头要显示「在借 2 · 逾期 1 · 累计 9」。
> 让前端按当前页的 10 条算，**跨页就错了**。三条 count 一次查完，别让前端自己数。

### 接口 4 · 确认归还（**仅管理员**）★

| 项 | 值 |
|---|---|
| 请求方法 | `PATCH` |
| 后端路径 | `/borrows/{id}/return` |
| 前端请求 | `/api/borrows/7/return?returnTime=2026-10-15` |
| 需要登录 | ✅ |
| 需要管理员 | ✅ **`@RequireAdmin`** |
| 调用方 | **只有「借阅管理」页面（管理员）会调它** |

#### ★★ 为什么用户不能自己还书

用户在家点一下"已归还"：`available_num` 立刻 +1、`return_time` 被写上、记录变成"已归还"。
而书**还在他手上** —— 结果是：

1. 别人来借，管理员去架上找 → 没有；`available_num` 是假的。
2. 更严重的是：记录已经写着"已归还"，**系统里再也查不出这本书在谁那儿**。
   这不是操作失误，是**设计上把追责凭证交给了最没有动机保管它的一方**，而且不可逆。

管理员操作时，他手里**确实拿到了那本书** —— 事实和记录在同一个人手上，凭证链完整。

#### 前端发过来的数据

| 位置 | 名称 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| 路径 | `id` | Long | ✅ | 借阅记录 id（**不是图书 id**） |
| query | `returnTime` | String | ❌ | **实际归还日期**，格式 `yyyy-MM-dd`；不传按"现在" |

```
PATCH /api/borrows/7/return                        ← 今天就还的，不传
PATCH /api/borrows/7/return?returnTime=2026-10-15  ← 昨天还的，今天才录入
```

> ⚠️ **为什么路径里是借阅 id，而不是 `?bookId=3`？**
> 同一个人可能**借了同一本书两次**（还了再借）。按 `bookId` 还书就分不清还的是哪一次 ——
> 记录、库存、时间全对不上。**借阅记录的主键才是这件事的唯一标识。**

> ★★ **`returnTime` 为什么必须能填？**
> 书是昨天还的、管理员今天才录入 —— 如果强行写"今天"，昨天正好是应还日的话，
> **读者会被无辜算成逾期**。而且这个日期直接决定 `overdueDays`：
>
> ```
> 管理员填 2026-10-15，应还 2026-10-15  → 按期归还，overdueDays = 0
> 管理员不填（默认今天 10-18）          → 逾期 3 天，读者被冤枉
> ```
>
> **前端要在表单上把这句话写给管理员看**，因为它影响的是读者的信用记录。

#### 你希望我返回的数据

```json
{ "code": 1, "msg": "归还成功", "data": null }
```

#### 错误返回

| 场景 | `msg` |
|---|---|
| id 不存在 | `借阅记录不存在` |
| **已经还过了** | `该借阅记录已归还，请勿重复操作` |
| **这条已被撤销** | `该借阅已被取消，无需归还` |
| 归还日期晚于今天 | `归还日期不能晚于今天` |
| 归还日期早于借出日期 | `归还日期不能早于借出日期` |
| `returnTime` 格式不对 | `归还日期格式不正确，应为 yyyy-MM-dd` |

> **`returnTime` 用 `@RequestParam(required = false) String` 接，别直接声明成 `LocalDate`。**
> 格式不对时 Spring 会抛 `MethodArgumentTypeMismatchException`，
> 被全局处理器兜成 500「服务器异常」，前端根本看不懂。
> 自己接成 String 再 `LocalDate.parse(...)` 包一层 try/catch，才能给出上面那句友好的提示。

### 接口 5 · 续借（本人或管理员）

| 项 | 值 |
|---|---|
| 请求方法 | `PATCH` |
| 后端路径 | `/borrows/{id}/renew` |
| 前端请求 | `/api/borrows/7/renew` |
| 需要登录 | ✅ |
| 需要管理员 | ❌（**权限规则：本人或管理员**） |

> **续借为什么保留给用户？** 它不涉及实物，只改应还日期，而且已有
> "只能续 1 次 + 逾期不能续"的硬限制，风险为零。
> 但要判断"这条记录是不是我的" —— 这是本模块**唯一还需要归属判断**的接口
> （还书和撤销都已经是管理员专属了）。

#### 前端发过来的数据

只有路径参数 `id`。**没有请求体。**

> 续借多少天、能续几次，**全是后端常量**。
> 前端绝不能传 `renewDays` —— 传了就是"读者自己给自己定借期"。

#### 你希望我返回的数据

```json
{ "code": 1, "msg": "续借成功", "data": null }
```

想让提示语带日期，Service 顺手返回新的 `dueTime` 即可（`data` 传 `{ dueTime }`）。

#### 错误返回

| 场景 | `msg` |
|---|---|
| id 不存在 | `借阅记录不存在` |
| 不是自己的记录（且不是管理员） | `无权操作他人的借阅记录` |
| 已经归还了 | `该借阅已归还，无需续借` |
| **已被撤销** | `该借阅已取消，无需续借` |
| 续借次数用完 | `每本图书只能续借 1 次` |
| **已经逾期** | `图书已逾期，请先归还后再重新借阅` |

> **为什么逾期就不让续借了？** 续借是给"还没看完但守规矩的人"的便利。
> 已经逾期还允许续借，等于用续借来抹掉逾期记录 —— 那逾期提示就永远没用。

### 接口 6 · 全部借阅记录（管理员）

| 项 | 值 |

### 接口 7 · 撤销借阅（**仅管理员**）★新增

| 项 | 值 |
|---|---|
| 请求方法 | `PATCH` |
| 后端路径 | `/borrows/{id}/cancel` |
| 前端请求 | `/api/borrows/7/cancel` |
| 需要登录 | ✅ |
| 需要管理员 | ✅ **`@RequireAdmin`** |

#### 这个接口解决什么

用户线上自助借书，占了库存，**但一直不来取**：

```
8-01  zhangsan 线上点了"借阅"《深入理解计算机系统》
      → available_num 2 → 1，记录"借出中"
8-05  他没来取书。别人想借这本书 → 显示"无可借库存" → 借不到
8-10  管理员盘点发现：书明明在架上，却显示被借走了
      → 点「撤销借阅」→ 书回库存（available_num 1 → 2），记录置为"已取消"
```

**为什么不让管理员直接用「确认归还」代替？** 库存结果确实一样（都是 +1），但账本会错：
记录会写着"已归还"和一个归还时间，而实际上**这本书从未离开过图书馆**。
盘点、统计"多少人真的借过书"时就会对不上。**两个动作，两种事实，就该是两条状态。**

#### ★ 撤销【不删记录】

`status = 3`，记录保留。撤销如果直接 `DELETE`，就等于"凭证被销毁" ——
和自助还书是同一个错误，只是换了个入口，而且用户会发现记录凭空消失。

#### 前端发过来的数据

只有路径参数 `id`。**没有请求体**（不需要"撤销原因"，课程项目用不上）。

#### 你希望我返回的数据

```json
{ "code": 1, "msg": "已撤销该笔借阅", "data": null }
```

#### 错误返回

| 场景 | `msg` |
|---|---|
| id 不存在 | `借阅记录不存在` |
| **已经归还了** | `该借阅已归还，不能撤销` |
| **已经撤销过了** | `该借阅已被取消，请勿重复操作` |

> 🔴 **必须挡住"已归还的不能撤销"**：撤销和归还都对库存 `+1`。
> 如果一条已归还的记录又被撤销，库存会被**加两次** —— 凭空多出一本书，
> 而 `available_num` 一旦超过 `total_num`，就再也回不来了。
> 好在第五节要点 3 那个原子 UPDATE 本身就带 `status = 1` 这个门。

### 接口 8 · 删除借阅记录（**仅管理员**，备用通道）★新增

| 项 | 值 |
|---|---|
| 请求方法 | `DELETE` |
| 后端路径 | `/borrows/{id}` |
| 前端请求 | `/api/borrows/7` |
| 需要登录 | ✅ |
| 需要管理员 | ✅ **`@RequireAdmin`** |

#### 它是干什么用的

**备用通道**，只用于两件事：

1. 清理联调时产生的**测试数据**
2. 订正明显的**误操作**（比如点错借阅产生的垃圾记录）

**不要用它代替「确认归还」或「撤销借阅」** —— 那两个动作会如实记录事实，这个只是抹掉痕迹。
它存在，是为了让你在遇到"实在需要清掉"的情况时有个出口，而不是逼你去手写 SQL。

#### ★★ 唯一的硬约束：借出中的记录删不掉

```
✅ status = 2（已归还）→ 可以删
✅ status = 3（已取消）→ 可以删
❌ status = 1（借出中）→ 拒绝
```

**为什么？** 借出中的记录是"这本书在谁手上"的**唯一凭证**：

- 删了它，`available_num` 会**永远少一本** —— 书在外面，却没有任何记录说明它去了哪
- 这本书从此在系统里"人间蒸发" —— **这正是"用户不能自助还书"要防的那个风险，
  只是换成了让管理员来触发**
- 而已归还 / 已取消的记录**库存早就回滚过了**，删它们不动库存、不破坏一致性

```
要删一条借出中的记录？分两步走：
   ① PATCH /borrows/{id}/cancel   →  书回库存，记录变"已取消"
   ② DELETE /borrows/{id}         →  再删掉记录
两步都是诚实的事实，不存在"绕过库存逻辑"的旁路。
```

#### 前端发过来的数据

只有路径参数 `id`。**没有请求体。**

> 本期**不做批量删除**。1.0 图书那个"批量删除"按钮因为后端一直没有
> `DELETE /books/batch` 而成了摆设 —— 这个坑没必要在借阅上再挖一遍。

#### 你希望我返回的数据

```json
{ "code": 1, "msg": "删除成功", "data": null }
```

#### 错误返回

| 场景 | `msg` |
|---|---|
| id 不存在 | `借阅记录不存在` |
| **记录还在借出中** | `借出中的记录不能删除，请先确认归还或撤销借阅` |

## 六、★ 后端实现要点（9 条，1~3 是本模块的灵魂）

### 1. 🔴🔴 扣库存必须是**一条原子 SQL**，不能"先查再改"

**❌ 有并发 bug 的写法：**

```java
Book book = bookMapper.GetBookById(bookId);
if (book.getAvailableNum() > 0) {                                   // ① 查
    bookMapper.UpdateAvailable(bookId, book.getAvailableNum() - 1); // ② 改
}
```

两个读者同时借最后一本：

```
时刻   线程 A                    线程 B                   available_num
 t1    查到 available_num = 1                             1
 t2                             查到 available_num = 1    1     ← B 看到的是同一个 1
 t3    写入 1-1 = 0                                       0
 t4                             写入 1-1 = 0              0     ← 同一本书借给了两个人
```

**库存只减了 1，却借出去 2 本。** 这就是经典的"检查后使用"竞态，
自己一个人测**永远测不出来**，答辩时老师一问并发就露馅。

**✅ 正确写法：把判断和扣减压进同一条 SQL，让数据库保证原子性。**

```xml
<update id="DecreaseAvailable">
    UPDATE book
    SET available_num = available_num - 1
    WHERE id = #{bookId}
      AND status = 1
      AND available_num > 0
</update>
```

```java
int rows = borrowMapper.DecreaseAvailable(bookId);
if (rows == 0) {
    throw new BusinessException("该图书暂无可借库存");
}
```

`UPDATE ... WHERE available_num > 0` 会在数据库层面加行锁：两个请求同时进来，
一个先改成 0，另一个的 `WHERE` 就不成立 → 影响 0 行 → 被挡下。

> 🔑 **记住这个判断方式**：`int rows = mapper.xxx()`，**`rows == 0` 就是"没抢到"**。
> 借书、还书、撤销、续借四处全靠它，比任何 `if` 判断都可靠。

### 2. 🔴 借书必须在一个事务里

```java
@Transactional
public void BorrowBook(BorrowCreateDto dto, LoginUser loginUser) { ... }
```

少了它会出现"库存扣了但没记录"或"有记录但库存没扣"。流程与顺序：

```java
if (dto.getBookId() == null) throw new BusinessException("请选择要借阅的图书");

// ① 图书存在且在架
Book book = bookMapper.GetBookById(dto.getBookId());
if (book == null) throw new BusinessException("图书不存在");
if (book.getStatus() != null && book.getStatus() == 0) throw new BusinessException("该图书已下架，暂不可借阅");

// ② 同一本书不能重复借（未还的情况下）
if (borrowMapper.CountBorrowingByUserAndBook(loginUser.getId(), dto.getBookId()) > 0)
    throw new BusinessException("你已借阅该书且尚未归还");

// ③ 在借总数上限
if (borrowMapper.CountBorrowingByUser(loginUser.getId()) >= MAX_BORROW)
    throw new BusinessException("最多同时借阅 " + MAX_BORROW + " 本，请先归还部分图书");

// ④ ★ 原子扣库存（抢不到就抛，事务回滚）
if (borrowMapper.DecreaseAvailable(dto.getBookId()) == 0)
    throw new BusinessException("该图书暂无可借库存");

// ⑤ 写借阅记录
borrowMapper.InsertBorrow(loginUser.getId(), dto.getBookId(),
                          LocalDateTime.now().plusDays(BORROW_DAYS));
```

> ⚠️ **② ③（业务规则）必须放在 ④（扣库存）前面。** 反过来的话，
> 一个已经借满 5 本的人来借第 6 本，会先扣掉库存再被规则挡下 ——
> 事务虽然会回滚，但**白白锁了一次库存行**，高并发下拖慢别人。

### 3. 🔴 还书与撤销：状态翻转用"带条件的 UPDATE"，库存操作紧跟其后

两个动作对库存的效果完全一样（`+1`），区别只在记录变成 2 还是 3。
所以它们共用同一个模式 —— **先用"带条件的 UPDATE"抢到"这件事没做过"的资格**：

```xml
<update id="ReturnBook">
    UPDATE borrow_record
    SET status = 2, return_time = #{returnTime}
    WHERE id = #{id} AND status = 1      <!-- ★ 只有"借出中"才允许被翻转 -->
</update>

<update id="CancelBorrow">
    UPDATE borrow_record
    SET status = 3
    WHERE id = #{id} AND status = 1      <!-- ★ 同一个门 -->
</update>
```

```java
// 确认归还
int rows = borrowMapper.ReturnBook(id, returnTime);
if (rows == 0) throw new BusinessException("该借阅记录已归还，请勿重复操作");
borrowMapper.IncreaseAvailable(record.getBookId());   // ★ 翻转成功之后才加库存

// 撤销借阅
int rows = borrowMapper.CancelBorrow(id);
if (rows == 0) throw new BusinessException("该借阅已被取消，请勿重复操作");
borrowMapper.IncreaseAvailable(record.getBookId());
```

**这一条 SQL 同时干了两件事**：改状态、并保证只改一次。第二次点"还书"时
`status` 已经是 2，`WHERE` 不成立 → 影响 0 行 → 报错，**库存绝对不会被加两次**。

> **为什么先翻转记录、后加库存？** 因为"记录翻转成功"才是**这件事做没做过的唯一权威判据**。
> 先加库存的话，重复请求会先把库存加上去，再在翻转记录时失败 —— 库存白涨一本。

再加一道保险（防止任何意外把库存刷超）：

```xml
<update id="IncreaseAvailable">
    UPDATE book
    SET available_num = available_num + 1
    WHERE id = #{bookId}
      AND available_num &lt; total_num      <!-- ★ 小于号必须写成 &lt; -->
</update>
```

> 🔴🔴 **MyBatis XML 里 `<` 是非法字符！**
> XML 解析器把 `<` 当成"标签开始"，直接写 `available_num < total_num` 会报
> `The content of elements must consist of well-formed character data or markup`。
>
> | 想写 | XML 里必须写成 | 或者 |
> |---|---|---|
> | `a < b` | `a &lt; b` | `<![CDATA[ a < b ]]>` |
> | `a > b` | `a > b`（**大于号不用转义**） | |
>
> 本模块到处都在比时间（`due_time < NOW()`）和比数量（`available_num < total_num`），
> **每个 `<` 都要转义** —— 漏一个就编译不过去，而且报错信息完全看不出是哪一行。

`IncreaseAvailable` 影响 0 行**不算失败**（书可能已被删，或库存本来就满了），
所以不抛异常 —— 幂等的门由 `ReturnBook` / `CancelBorrow` 守着就够了。

### 4. 续借：也要带条件，且从"原应还时间"往后加

```java
BorrowRecord record = GetOwnedRecord(id, loginUser);   // 见要点 5
if (record.getStatus() == 2) throw new BusinessException("该借阅已归还，无需续借");
if (record.getStatus() == 3) throw new BusinessException("该借阅已取消，无需续借");
if (record.getRenewCount() >= MAX_RENEW)
    throw new BusinessException("每本图书只能续借 " + MAX_RENEW + " 次");
if (record.getDueTime().isBefore(LocalDateTime.now()))
    throw new BusinessException("图书已逾期，请先归还后再重新借阅");

if (borrowMapper.RenewBook(id, RENEW_DAYS) == 0)
    throw new BusinessException("续借失败，请刷新后重试");
```

```xml
<update id="RenewBook">
    UPDATE borrow_record
    SET due_time    = DATE_ADD(due_time, INTERVAL #{renewDays} DAY),
        renew_count = renew_count + 1
    WHERE id = #{id}
      AND status = 1
      AND renew_count &lt; 1        <!-- ★ 再带上限，防"双击续借两次" -->
</update>
```

> 💡 **`due_time` 从"原应还时间"往后加，不是从今天加。**
> `DATE_ADD(due_time, ...)` ✅ ／ `DATE_ADD(NOW(), ...)` ❌
> 后者等于把用户前面拖的时间一笔勾销：10-01 借、11-11 到期，用户 11-10 续借 ——
> 正确结果是 12-11；写成从今天加就变成 12-10，白送一天，**越拖越划算**。

### 5. 越权判断现在只剩"续借"需要

```java
/** 校验这条借阅记录当前登录人能不能动：本人或管理员 */
private BorrowRecord GetOwnedRecord(Long id, LoginUser loginUser) {
    BorrowRecord record = borrowMapper.GetById(id);
    if (record == null) throw new BusinessException("借阅记录不存在");
    if (!loginUser.isAdmin() && !record.getUserId().equals(loginUser.getId())) {
        throw new BusinessException("无权操作他人的借阅记录");
    }
    return record;
}
```

- **续借** 调它 —— 用户只能续自己的，管理员可以代续。
- **还书 / 撤销** 不用它 —— 方法上有 `@RequireAdmin`，拦截器已经挡住了非管理员；
  方法体里只需要 `GetById` 判存在 + 判状态。

> ⚠️ **`record.getUserId().equals(loginUser.getId())` 必须用 `.equals()`，不能用 `==`。**
> 两个都是 `Integer`（对象），`==` 比的是引用地址，超过 `-128~127` 的缓存范围就不相等 ——
> 表现是"有时候能续、有时候说没权限"。顺带说，`Integer` 和基本类型 `int` 比较时 `==`
> 又会自动拆箱变得正确 —— **这种"有时对有时错"正是它危险的地方，统一用 `.equals()` 最省心。**

在 `BookServiceImpl` 的 `DeleteBook`（以及批量删除）**最前面**加：

### 8. `count` 和 `list` 的条件必须一致（和模块一同一个坑）

### 9. ★★ `overdueDays` 的口径必须和 SQL 的 `due_time < NOW()` 完全一致

**这条是实测时真的炸了的一条。** SQL 判断"逾期"（筛选、统计、排序都用它）是
`status = 1 AND due_time < NOW()`，所以 Java 算 `overdueDays` 也必须是**同一个口径**：

| `status` | 和谁比 | `overdueDays` |
|---|---|---|
| 1 借出中 | `LocalDateTime.now()` | 没到期 → `0`；到期了 → **不满一天也计 `1`** |
| 2 已归还 | `return_time`（**不是今天**） | 同上 |
| 3 已取消 | —— | `0` |

```java
long days;
if (vo.getStatus() == 1) {
    days = ChronoUnit.DAYS.between(vo.getDueTime(), LocalDateTime.now());
} else if (vo.getStatus() == 2 && vo.getReturnTime() != null) {
    days = ChronoUnit.DAYS.between(vo.getDueTime(), vo.getReturnTime());
} else {
    days = 0;
}
vo.setOverdueDays(days > 0 ? (int) days : 0);

// 只有"借出中 + 没逾期 + 还没续借过"才能续借
vo.setCanRenew(vo.getStatus() == 1 && vo.getOverdueDays() == 0 && vo.getRenewCount() < 1 ? 1 : 0);
```

> 🔴🔴 **`return days > 0 ? days : 1` 里的那个 `1` 不能省。** 如果把左式写成
> `ChronoUnit.DAYS.between(dueTime.toLocalDate(), end.toLocalDate())` 直接返回，
> 应还时间是**今天 22:22**、请求时**今天 22:31** 的记录会算出 `0`，于是：
>
> | 来源 | 口径 | 结论 |
> |---|---|---|
> | `GetMySummary.overdue_count` | SQL `due_time < NOW()` | **算逾期** |
> | `?overdue=1` 筛选 | SQL `due_time < NOW()` | **筛得出来** |
> | `overdueDays` | 日历天差 | **0（不算逾期）** |
>
> 用户看到的就是：**这条记录出现在「已逾期」筛选里，却不标红、不显示天数、`canRenew` 还是 1**
> —— 也就是"明明逾期了却什么都不提示"。**这条规则在实测中被这条测试数据抓到过，别改回去。**
>
> **续借接口的逾期判断也必须用同一个口径**（`dueTime.isBefore(LocalDateTime.now())`），
> 否则会出现"按钮亮着、点了却说逾期"。

> 🔴 **已归还的记录如果拿"今天"去减 `due_time`，会得出荒唐结果**：
> 一条 8 月按期归还的记录，到 12 月会显示"逾期 120 天"。
> 必须用 `return_time` —— 它记的是**历史事实**，不是"到现在为止"。

### 本文件的规则变更记录

| 变更 | 原设计 | 现在 | 原因 |
|---|---|---|---|
| **还书权限** | 本人或管理员 | **仅管理员** | 用户自助还书会**销毁"书在谁手上"的凭证**，且不可逆 —— 库存虚增、追责无据 |
| **归还日期** | 系统时间 | **管理员可填，默认今天** | 书昨天还的、今天才录入，否则读者被无辜算成逾期 |
| **取消借阅** | 无 | **新增接口 7（仅管理员）** | 给"线上借了不来取"一个出口；不删记录，置 `status=3` |
| **状态机** | 1借出中 / 2已归还 | **1借出中 / 2已归还 / 3已取消** | 上一条的必然结果 |
| **续借** | 本人或管理员 | 不变（**保留给用户**） | 不涉及实物、只改日期、有硬限制，风险为零 |
| **`overdueDays`** | 一律用"今天"算 | **已归还的用 `return_time` 算** | 否则 8 月归还的记录到 12 月会显示"逾期 120 天" |
| **删除记录** | 不提供（借阅记录只增不删） | **新增接口 8（仅管理员，备用通道）**，但**借出中的记录删不掉** | 需要一个清理测试数据 / 订正误操作的出口；同时不能让删除成为绕过库存逻辑的旁路 |

### 3.0 结束后的状态

- 系统具备完整主流程：查书 → 借书 → 到馆归还 → 管理员确认 → 通知
- 借阅记录**只增不删**，`book.available_num` 与记录保持强一致（有自检 SQL 兜底）
- 三笔历史欠账全部结清：**删书的孤儿数据**、**注销的孤儿数据**、**库存并发**
