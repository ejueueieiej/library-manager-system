## 〇、先说清楚要做成什么样

### 0.1 功能拆解

路线图原文：*实现网页阅读功能，用户可以自己上传 txt 文件进行阅读，同时为部分书目开启阅读功能。*

拆成两半：

| 半 | 内容 | 谁能操作 |
|---|---|---|
| **A. 书籍在线阅读** | 管理员给某本书上传正文 txt → 打开"可阅读"开关 → 任何登录用户都能读 | 上传/开关：管理员<br>阅读：所有登录用户 |
| **B. 用户上传 txt** | 用户上传自己的 txt，只有他自己能读 | 本人 |

两半**共用同一个阅读器**，区别只在数据从哪张表来。

### 0.2 整个功能的骨架

理解这张图，后面每一步就都知道自己在干什么：

```
【A 书籍】
 管理员 ──上传txt──▶ book_content 表（正文纯文本）
 管理员 ──开关────▶ book.readable = 1
                              │
                              ▼
 读者 ──GET meta──▶ 后端：查书 → 判 readable → 取正文 → 正则切章 → 返回目录（不含正文）
 读者 ──GET chapter/{i}──▶ 后端：取正文 → 切章 → 只截第 i 章 → 返回

【B 用户文件】
 用户 ──上传txt──▶ reader_file 表（user_id 记着归属）
 用户 ──GET file/meta / file/chapter/{i}──▶ 同上，只是校验"是不是你自己的"

【公共】
 任何人 ──PUT progress──▶ reader_progress 表（一个用户对一个目标只有一条）
```

**三个关键设计决定**（后面会反复提到）：

1. **正文单独一张表**，不放 `book` 里 —— 因为 `book` 的查询是列表页高频操作，LONGTEXT 会白白拖慢
2. **章节不落库，每次现切** —— 正文变了不用同步，少一张表少一类 bug
3. **一次只返回一章** —— 100 万字塞进 DOM 会直接卡死

### 0.3 接口总表（14 个）

| # | 方法 | 路径 | 权限 | 作用 |
|---|---|---|---|---|

## 一、第 1 步：建表

### 1.1 为什么正文要单独一张表

先想一下现在的代码：`BookMapper.xml` 里

```xml
<select id="GetAllBooks" resultType="Book">
    SELECT b.*, c.name AS category_name
    FROM book b LEFT JOIN book_category c ...
```

`SELECT b.*` 会把 `book` 表**所有列**都取出来。如果正文（`LONGTEXT`）放在 `book` 里：

- 图书列表每页 10 行 → 一次查询要拉 10 × 2MB = 20MB
- 而这 20MB 里有 99.9% 是页面根本不显示的正文

**所以：正文单独放 `book_content`，主键就是 `book_id`（一对一）。**
列表页永远查不到它，想读正文必须显式去查。

> 这叫「冷热分离」的简化版 —— 高频小数据和低频大字段分开放。

### 1.2 逐字段说明

#### `book` 加一列

```sql
ALTER TABLE book
    ADD COLUMN readable TINYINT(1) NOT NULL DEFAULT 0
    COMMENT '1=开启在线阅读，只有管理员能改' AFTER status;
```

| 细节 | 为什么 |
|---|---|
| `TINYINT(1)` 而不是 `BOOLEAN` | MySQL 里 `BOOLEAN` 只是 `TINYINT(1)` 的别名，写哪个都行，但这个项目的其他开关（`status`）都是 `INT`，保持一致 |
| `NOT NULL DEFAULT 0` | 老数据自动变成"未开启"，不用补数据。**如果没有 DEFAULT，加 NOT NULL 列会失败** |
| `AFTER status` | 只是让列的顺序好看，不影响功能 |
| 不加索引 | 我们不按 `readable` 查（是读出来之后在 Java 里判断），不需要 |

#### `book_content`

```sql
CREATE TABLE book_content
(
    book_id     INT      NOT NULL COMMENT '主键即 book.id',
    content     LONGTEXT NOT NULL COMMENT '正文纯文本（换行已统一成 \n）',
    word_count  INT      NOT NULL DEFAULT 0 COMMENT '去掉空白后的字符数',
    encoding    VARCHAR(16) DEFAULT NULL COMMENT '检测出的编码，排错用',
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (book_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

| 字段 | 类型选型理由 |
|---|---|
| `book_id` | 用 `PRIMARY KEY` 而不是自增 id —— 一本书只有一份正文，`book_id` 天然唯一，省一个列 |
| `content` | `LONGTEXT` 上限 4GB；`TEXT` 只有 64KB，一本小说随便就超 |
| `word_count` | **存起来而不是每次算** —— 列表页要显示"86 万字"，每次扫 2MB 就为了数个数太浪费 |
| `encoding` | 出乱码时第一眼要看的东西，非常有用 |

#### `reader_file`

```sql
CREATE TABLE reader_file
(
    id            BIGINT       NOT NULL AUTO_INCREMENT,
    user_id       INT          NOT NULL,
    title         VARCHAR(200) NOT NULL COMMENT '默认取文件名（去扩展名）',
    content       LONGTEXT     NOT NULL,
    word_count    INT          NOT NULL DEFAULT 0,
    chapter_count INT          NOT NULL DEFAULT 0 COMMENT '切出几章，列表页要显示',
    encoding      VARCHAR(16)  DEFAULT NULL,
    create_time   DATETIME     DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    KEY idx_user (user_id, create_time)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

| 关键点 | 说明 |
|---|---|
| `id` 用自增 `BIGINT` | 这里没有天然的"业务主键"，只能用代理键 |
| `user_id` + 索引 | **所有查询都必须带 `user_id` 条件**，否则 A 能看到 B 的文件 |
| `title` | 用户上传的文件名不能直接当存储名（路径穿越风险），但可以当显示名 |
| **`chapter_count`** | ★ **必须存**。列表页要显示"42 章"，如果每次现切，翻一页就要把 10 个文件的正文（可能几十 MB）全部正则扫一遍 |

> **为什么 `book_content` 里没有 `chapter_count`，而这张表有？**
> 因为两者的使用场景不一样：
> - 书籍的 `meta` 接口**本来就要返回完整目录**，所以正文一定要切一次，顺便就拿到了章数，存了也是浪费
> - 文件的**列表接口只要章数、不要目录**，如果不存，就得为了一个数字把每个文件的正文全切一遍
>
> 这是"按使用场景决定要不要冗余"，不是"两个表要对称"。

#### `reader_progress`

```sql
CREATE TABLE reader_progress
(
    id            BIGINT        NOT NULL AUTO_INCREMENT,
    user_id       INT           NOT NULL,
    target_type   TINYINT       NOT NULL COMMENT '1=书籍 2=用户文件',
    target_id     BIGINT        NOT NULL,
    chapter_index INT           NOT NULL DEFAULT 0,
    chapter_title VARCHAR(200)  DEFAULT NULL,
    percent       DECIMAL(5, 2) NOT NULL DEFAULT 0 COMMENT '章节内滚动百分比 0~100',
    update_time   DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_progress (user_id, target_type, target_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

**`UNIQUE KEY uk_progress` 是这张表的灵魂。**

它保证"一个用户对一个阅读目标只有一条进度"。
有了它，写进度就能用一句 SQL 搞定（有则改、无则插）：

```sql
INSERT INTO reader_progress (...) VALUES (...)
ON DUPLICATE KEY UPDATE chapter_index = VALUES(chapter_index), ...
```

没有这个唯一索引，你就得先 `SELECT` 判断有没有、再决定 `INSERT` 还是 `UPDATE`
—— 那是两条 SQL，而且并发下会插出重复记录。

> `target_type` 为什么用数字不用字符串？`'book'` / `'file'` 也行，但数字占 1 字节、比较更快，
> 而且这个值只有后端自己用，前端看到的永远是 `/reader/book/...` 这样的路径。

## 二、第 2 步：打开上传开关（最容易漏的一步）

### 2.1 为什么必须改

Spring Boot 对上传文件有**默认限制**：

```yaml
spring.servlet.multipart.max-file-size     = 1MB     # 单个文件
spring.servlet.multipart.max-request-size  = 10MB    # 整个请求
```

**1MB 是什么概念？** 一本 30 万字的中文小说，UTF-8 下大约 **900KB**，勉强过线；
稍微长一点就直接 413（Payload Too Large）。

所以这一步不做，你上传时永远只会看到一个莫名其妙的 413 错误。

### 2.2 改哪里

`libaray_manager_system/src/main/resources/application.yml`，加在 `spring:` 下面：

```yaml
spring:
  datasource: ...
  data:
    redis: ...
  # 4.0 阅读：上传 txt 用
  servlet:
    multipart:
      max-file-size: 10MB
      max-request-size: 12MB
```

| 参数 | 说人话 |
|---|---|
| `max-file-size` | 一个文件最大 10MB（≈ 300 万汉字，够放整套《三体》） |
| `max-request-size` | 整个请求最大 12MB。它要比 `max-file-size` 大一点，因为请求里还有表单字段和边界字符 |

### 2.3 改完必须重启

`application.yml` **不支持热更新**。改完要在 IDEA 里重跑 `LibarayManagerApplication`，
否则新配置不生效 —— 这是新手最容易怀疑人生的一点："我明明改了为什么不生效"。

### 2.4 做完怎么验证

先随便造一个 2MB 的文件：

```powershell

(Get-Item D:\big-test.txt).Length / 1MB
```

## 三、第 3 步：编码检测（整个功能最坑的一块）

### 3.1 先扫盲：字符集和编码

- **字符集（Charset）**：一个"字符编号表"，规定"汉"对应哪个数字
- **编码（Encoding）**：把那个数字变成字节的规则

同一段中文，用不同编码存成字节，**字节完全不同**：

```
"第一章"
  UTF-8   → E7 AC AC E4 B8 80 E7 AB A0   （每个汉字 3 字节）
  GBK     → B5 DA D2 BB D5 C2             （每个汉字 2 字节）
```

**关键点：txt 文件本身不带"我是什么编码"的标记**（除非有 BOM）。
你拿一串字节，必须靠猜。

### 3.2 为什么这是国内 txt 的头号问题

Windows 中文版的记事本，**默认保存就是 GBK**（叫 ANSI）。
而你的 Java 代码、网页、数据库全是 UTF-8。

所以：
- 用 `new String(bytes)` 解码 → 用的是平台默认编码（JDK 18+ 是 UTF-8）
- 用 UTF-8 去解 GBK 字节 → **乱码**，而且**不可逆**（信息已经丢了）

### 3.3 BOM 是什么

有些编辑器会在文件**最开头**塞 2~3 个特殊字节，用来告诉别人"我是什么编码"：

| 编码 | BOM 字节 |
|---|---|
| UTF-8 | `EF BB BF` |
| UTF-16LE | `FF FE` |
| UTF-16BE | `FE FF` |

有 BOM 就不用猜了，直接按它说的解 —— 但**记得把 BOM 那几个字节切掉**，
否则正文第一个字符会是看不见的 `\uFEFF`。

### 3.4 检测策略：三步走

```
第 1 步：看开头有没有 BOM
        有 → 按 BOM 指定的编码解，切掉 BOM 字节，结束

第 2 步：能不能【严格】按 UTF-8 解？
        能 → 就是 UTF-8，结束

第 3 步：按 GB18030 解
        能 → 就是 GB18030，结束
        不能 → 报错，让用户另存为 UTF-8
```

**为什么第 2 步要强调"严格"？**

`new String(bytes, UTF_8)` 遇到非法字节时**不会报错**，而是悄悄替换成 `�`（U+FFFD）。
这样你永远不知道解码失败了。

正确做法是用 `CharsetDecoder` 并设置 `CodingErrorAction.REPORT`：
遇到非法字节**直接抛异常**，这样"能解出来"才等于"真的是 UTF-8"。

**为什么 GB18030 一个就够，不用判断 GBK / GB2312？**

因为 `GB2312 ⊂ GBK ⊂ GB18030`，**GB18030 是它们的超集**。
GBK 能解的字节，GB18030 一定也能解。所以直接用最大的那个，不用细分。

### 3.5 完整代码

新建 `utils/TextDecodeUtil.java`（注意包里是 **`utils`** 复数，跟 `JwtUtil` / `CacheUtil` 放一起）：

```java
package org.libaray_manager_system.utils;

import org.libaray_manager_system.exception.BusinessException;
import java.nio.ByteBuffer;
import java.nio.charset.*;
import java.util.Arrays;

public class TextDecodeUtil {

    /** 解析结果：正文 + 最终用的编码名 */
    public record Decoded(String text, String charset) {}

    public static Decoded decode(byte[] bytes) {
        if (bytes == null || bytes.length == 0) {
            throw new BusinessException("文件内容为空");
        }

        // ---- 第 1 步：BOM ----
        if (bytes.length >= 3 && (bytes[0] & 0xFF) == 0xEF
                && (bytes[1] & 0xFF) == 0xBB && (bytes[2] & 0xFF) == 0xBF) {
            return new Decoded(new String(bytes, 3, bytes.length - 3, StandardCharsets.UTF_8), "UTF-8");
        }
        if (bytes.length >= 2 && (bytes[0] & 0xFF) == 0xFF && (bytes[1] & 0xFF) == 0xFE) {
            return new Decoded(new String(bytes, 2, bytes.length - 2, StandardCharsets.UTF_16LE), "UTF-16LE");
        }
        if (bytes.length >= 2 && (bytes[0] & 0xFF) == 0xFE && (bytes[1] & 0xFF) == 0xFF) {
            return new Decoded(new String(bytes, 2, bytes.length - 2, StandardCharsets.UTF_16BE), "UTF-16BE");
        }

        // ---- 第 2 步：严格 UTF-8 ----
        String utf8 = tryDecode(bytes, StandardCharsets.UTF_8);
        if (utf8 != null) return new Decoded(utf8, "UTF-8");

        // ---- 第 3 步：GB18030 ----
        String gb = tryDecode(bytes, Charset.forName("GB18030"));
        if (gb != null) return new Decoded(gb, "GB18030");

        throw new BusinessException("无法识别文件编码，请另存为 UTF-8 后重新上传");
    }

    private static String tryDecode(byte[] bytes, Charset charset) {
        CharsetDecoder decoder = charset.newDecoder()
                .onMalformedInput(CodingErrorAction.REPORT)
                .onUnmappableCharacter(CodingErrorAction.REPORT);
        try {
            return decoder.decode(ByteBuffer.wrap(bytes)).toString();
        } catch (CharacterCodingException e) {
            return null;   // 解不出来，交给下一种编码
        }
    }
}
```

**逐行解释几个容易懵的地方：**

| 代码 | 为什么这么写 |
|---|---|
| `(bytes[0] & 0xFF) == 0xEF` | Java 的 `byte` 是有符号的（-128~127），`0xEF` 会被认成负数。`& 0xFF` 把它转成 0~255 的正数再比较 |
| `new String(bytes, 3, len - 3, UTF_8)` | 从第 4 个字节开始（跳过 3 字节 BOM），长度也减 3 |
| `record Decoded(...)` | Java 16+ 的语法，一个不可变的小数据载体。比写一个只有两个字段的类干净 |
| `CharsetDecoder` + `REPORT` | 见 3.4 的解释，这是"严格解码"的关键 |

### 3.6 做完怎么验证

写个临时 `main` 跑一下（或者用 JUnit，但项目现在没有测试框架，先 `main` 最快）：

```java
public static void main(String[] args) {
    String cn = "第一章 潜入\n他推开那扇门。\n";

    // 模拟 GBK 文件
    TextDecodeUtil.Decoded d1 = TextDecodeUtil.decode(cn.getBytes("GB18030"));
    System.out.println(d1.charset() + " -> " + d1.text().equals(cn));

    // 模拟 UTF-8 文件
    TextDecodeUtil.Decoded d2 = TextDecodeUtil.decode(cn.getBytes("UTF-8"));
    System.out.println(d2.charset() + " -> " + d2.text().equals(cn));
}
```

期望输出：

```
GB18030 -> true
UTF-8 -> true
```

**两个都 true 才算过。** 如果 GB18030 那条输出 `UTF-8 -> false`，说明 GBK 字节被误判成 UTF-8 了 —— 这时要回过头检查 `REPORT` 有没有设上。

## 四、第 4 步：章节切分

### 4.1 为什么必须切

一本 100 万字的小说，如果一次性发给前端：

| 问题 | 后果 |
|---|---|
| JSON 体积 | 约 3MB（UTF-8 中文 3 字节/字 + 转义）→ 首屏白屏好几秒 |
| DOM 节点 | 100 万字符放进一个 `<p>` → 浏览器的排版引擎直接卡死 |
| 进度定位 | "读到第 37 章"无从谈起 |

切成章之后，一次只加载一章（通常 3000~2 万字），上面三个问题全没了。

### 4.2 章节标题长什么样

国内 txt 的章节标题是个"民间标准"，常见的：

```
第一章 潜入              第1章 潜入
第十二回 高潮            第 12 节
序章 / 楔子 / 引子       尾声 / 后记 / 番外
Chapter 1                 Chapter 12: The End
```

### 4.3 正则逐段拆解

```java
private static final Pattern CHAPTER = Pattern.compile(
        "(?m)^[ \\t　]*(" +
                "第[0-9０-９零一二三四五六七八九十百千万〇两]+[章节回卷篇集]" +
                "|Chapter\\s+\\d+" +
                "|序章|楔子|引子|尾声|后记|番外" +
                ")[^\\n]{0,40}$");
```

一块一块看：

| 片段 | 含义 | 为什么 |
|---|---|---|
| `(?m)` | **多行模式** | 让 `^` 和 `$` 匹配"每行的开头/结尾"，而不是整个字符串的开头/结尾。**没有它，`^` 只认全文第一个字符，一章都匹配不到** |
| `^` | 行首 | **最关键的一个符号**。正文里出现"他翻到第三章的时候睡着了"，如果不锚行首，这里会被切成新章节 |
| `[ \t　]*` | 行首允许空白 | txt 里章节标题常带缩进（半角空格 / 制表符 / **全角空格 `　`**）。全角空格是 U+3000，肉眼看不出来，但它是合法字符，不写就会漏匹配 |
| `第...[\u7ae0\u8282...]` | 第X章/节/回/卷/篇/集 | 覆盖中文小说的常见量词 |
| `[0-9０-９零一二三四五六七八九十百千万〇两]+` | 数字部分 | 阿拉伯数字 + **全角数字** + 中文数字。`〇` 和 `两` 是老写法（"第〇章""第两百章"） |
| `Chapter\s+\d+` | 英文小说 | `\s+` 容忍 "Chapter  1" 中间多个空格 |
| `序章\|楔子\|...` | 特殊章节 | 这些没有"第X章"格式 |
| `[^\n]{0,40}$` | 标题后的部分 | 标题最多 40 字。**上限很重要**：不限制的话，一行很长的正文被开头几个字匹配上，整段都会被当成标题吃掉 |
| `$` | 行尾 | 和 `^` 配对，配合 `(?m)` |

### 4.4 切分算法

思路：**先找出所有"标题行"的位置，相邻两个标题之间的内容就是这一章的正文。**

```
原文：
  书名：深海之门          ← 第一个标题之前，归入「前言」
  作者：某某
  第一章 潜入             ← 标题 1，start=……
  他推开那扇门……           ← 属于第 1 章
  第二章 回声             ← 标题 2
  水声从深处传来……         ← 属于第 2 章
```

边界定义：

```java
record Chapter(String title, int contentStart, int end) {}
```

| 字段 | 含义 |
|---|---|
| `title` | 标题文字（给目录用） |
| `contentStart` | 正文起点 = **标题行的换行之后**（不含标题本身，否则页面会标题显示两遍） |
| `end` | 正文终点 = 下一个标题的起点（或全文末尾） |

### 4.5 完整代码

新建 `utils/ChapterSplitUtil.java`：

```java
package org.libaray_manager_system.utils;

import java.util.ArrayList;
import java.util.List;
import java.util.regex.Matcher;
import java.util.regex.Pattern;

public class ChapterSplitUtil {

    public record Chapter(String title, int contentStart, int end) {}

    private static final Pattern CHAPTER = Pattern.compile(
            "(?m)^[ \\t　]*(" +
                    "第[0-9０-９零一二三四五六七八九十百千万〇两]+[章节回卷篇集]" +
                    "|Chapter\\s+\\d+" +
                    "|序章|楔子|引子|尾声|后记|番外" +
                    ")[^\\n]{0,40}$");

    public static List<Chapter> split(String text) {
        List<Chapter> list = new ArrayList<>();
        if (text == null || text.isEmpty()) return list;

        List<int[]> marks = new ArrayList<>();
        List<String> titles = new ArrayList<>();
        Matcher m = CHAPTER.matcher(text);
        while (m.find()) {
            marks.add(new int[]{m.start(), m.end()});
            titles.add(m.group().trim());
        }

        // 兜底：一个章节标记都没有 → 整篇当一章，绝不报错
        if (marks.isEmpty()) {
            list.add(new Chapter("全文", 0, text.length()));
            return list;
        }

        // 第一个标题前的内容 → 前言
        if (marks.get(0)[0] > 0) {
            String head = text.substring(0, marks.get(0)[0]).trim();
            if (!head.isEmpty()) {
                list.add(new Chapter("前言", 0, marks.get(0)[0]));
            }
        }

        for (int i = 0; i < marks.size(); i++) {
            int titleEnd = marks.get(i)[1];
            int contentStart = titleEnd < text.length() ? titleEnd + 1 : titleEnd;  // 跳过换行
            int end = (i + 1 < marks.size()) ? marks.get(i + 1)[0] : text.length();
            list.add(new Chapter(titles.get(i), contentStart, end));
        }
        return list;
    }
}
```

**为什么 `contentStart = titleEnd + 1`？**

`(?m)$` 匹配的是"换行符之前"的位置，所以 `m.end()` 指向标题文字的末尾、**还没跨过 `\n`**。
正文从下一行开始，就是 `+1`。

> 前提是文本里的换行已经统一成 `\n`。Windows 的 txt 是 `\r\n`，要在上传时统一（见第 7 步）。

### 4.6 做完怎么验证

```java
public static void main(String[] args) {
    String text = "第一章 潜入\n他推开门。\n他翻到第三章的时候睡着了。\n第二章 回声\n水声传来。\n";
    List<ChapterSplitUtil.Chapter> list = ChapterSplitUtil.split(text);

    System.out.println("章节数：" + list.size());                 // 期望 2
    list.forEach(c -> System.out.println("  " + c.title()));     // 期望：第一章 潜入 / 第二章 回声
}
```

1. 章节数 = 2（不是 3）→ 说明"他翻到第三章"没被误判
2. 标题里没有 `\r` → 换行统一了
3. 把 `(?m)` 删掉再跑一次会变成 1 章 → 说明 `(?m)` 真的在起作用（推荐做一次，加深印象）

## 五、第 5 步：实体 / DTO / VO

### 5.1 三个概念别混

| 类型 | 干什么 | 谁用 |
|---|---|---|
| **Entity（实体）** | 和数据库表**一一对应** | Mapper 查出来、塞进去 |
| **DTO**（Data Transfer Object） | 接收**前端传来**的数据 | Controller 的参数 |
| **VO**（View Object） | 返回给**前端看**的数据 | Controller 的返回值 |

为什么不能全用一个类？因为三者字段常常不一样：

- `book_content` 表有 `content`（2MB），但目录接口**绝不能**返回它 → 所以要有 `ReaderMetaVo`
- 前端上传不需要传 `word_count`（后端自己算）→ 所以不需要 `BookContentDto`

### 5.2 先记住这条规则：数据库列 → Java 类型

写错类型的根源是"没记住对照关系"。先把这张表刻进脑子，后面 9 个类就是套用：

| MySQL 列类型 | Java 类型 | 说明 |
|---|---|---|
| `INT` | **`Integer`** | 项目里 `book.id`、`sysUser.id`、`LoginUser.id` 全是它 |
| `BIGINT` | **`Long`** | `notice.id`、`borrow_record.id`、`reader_file.id`、`reader_progress.id` |
| `TINYINT` | **`Integer`** | 别用 `Byte`，容易和 MyBatis 的类型处理器打架 |
| `DECIMAL(5,2)` | **`BigDecimal`** | 百分比、金额都用它，**别用 Double**（二进制浮点存不准 0.1） |
| `VARCHAR` / `LONGTEXT` | **`String`** | |
| `DATETIME` | **`LocalDateTime`** | |
| `DATE` | **`LocalDate`** | 例：`book.publish_date` |
| 0/1 语义的开关（`readable`） | **`Integer`** | 见下面的补充说明 |

**两条容易忽略的补充**：

1. **数据库的 0/1 开关，Java 用 `Integer` 接，判断时再比 1**
   ```java
   if (!Integer.valueOf(1).equals(book.getReadable())) { ... }
   ```
   为什么不用 `boolean` 字段？`TINYINT(1)` 的实际取值范围是 -128~127，万一有人存了 `2`，
   用 `boolean` 接会抛类型转换异常；用 `Integer` 接最稳。

2. **"算出来的结论"用 `Boolean`，"数据库里的值"用 `Integer`**
   `ReaderMetaVo.readable` 是 `Boolean` —— 它不是某张表的列，而是后端算出来的
   （开关开了 **且** 有正文 → true）。这类字段用 `Boolean`，语义更直白。

| `hasContent` | **`Boolean`** | **正文到底传没传** —— 和 `readable` 无关，管理端靠它区分"没正文"和"没开启" | ★ 不是数据库列 |
| `denyReason` | `String` | **不能读的原因** —— 直接甩给用户看，前端不用自己编文案 | `null` 或 `"这本书还没有开启在线阅读"` |

> 开关关掉时 `readable` 是 `false`，但你分不清到底是"没上传正文"还是"上传了但没开启"。

### 5.4 两个必踩的类型坑

#### 坑 1：把 `Integer` 直接塞进要 `Long` 的地方 → 编译不过

```java
// ❌ 编译错误：incompatible types: Integer cannot be converted to Long
progress.setTargetId(bookId);          // bookId 是 Integer，setTargetId 参数是 Long

// ✅ 显式转
progress.setTargetId(bookId.longValue());
```

Java 的自动装箱**只在"同一个类型"之间生效**（`int` ↔ `Integer`），
`Integer` 和 `Long` 之间**没有任何自动转换**。所以每次看到这个报错，就去找那个漏掉的 `.longValue()`。

Mapper 参数同理：

```java
// Mapper 里 targetId 声明的是 Long
ReaderProgress Get(@Param("userId") Integer userId,
                   @Param("targetType") Integer targetType,
                   @Param("targetId") Long targetId);

// 调用时也要转
progressMapper.Get(loginUser.getId(), 1, bookId.longValue());
```

#### 坑 2：`target_id` 如果写成 `Integer`，将来一定出事

`reader_progress` 是一张"两用"的表：

- `target_type = 1` 时，`target_id` 装的是 **`book.id`（INT）**
- `target_type = 2` 时，`target_id` 装的是 **`reader_file.id`（BIGINT）**

一个字段要同时装 INT 和 BIGINT，**只能按大的来** → 建表用 BIGINT、Java 用 `Long`。

如果偷懒写成 `Integer`：
- 现在能跑（书 id 都很小）
- 但 `reader_file.id` 超过 21 亿就溢出
- 而且 MyBatis 往 `Long` 字段塞 `Integer` 会直接报错

**记法：`target_id` 是 `Long`，把 `bookId` 传进去时要 `.longValue()`。**

### 6.2 `BookContentMapper`（新建 · 3 个方法）

`mapper/BookContentMapper.java`：

```java
package org.libaray_manager_system.mapper;

import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Param;
import org.libaray_manager_system.pojo.entity.BookContent;

@Mapper
public interface BookContentMapper {
    BookContent GetByBookId(@Param("bookId") Integer bookId);
    int Save(BookContent content);
    void DeleteByBookId(@Param("bookId") Integer bookId);
}
```

`resources/mapper/BookContentMapper.xml`：

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="org.libaray_manager_system.mapper.BookContentMapper">

    <select id="GetByBookId" resultType="BookContent">
        SELECT book_id, content, word_count, encoding, create_time, update_time
        FROM book_content
        WHERE book_id = #{bookId}
    </select>

    <insert id="Save">
        INSERT INTO book_content (book_id, content, word_count, encoding)
        VALUES (#{bookId}, #{content}, #{wordCount}, #{encoding})
        ON DUPLICATE KEY UPDATE content    = VALUES(content),
                                word_count = VALUES(word_count),
                                encoding   = VALUES(encoding)
    </insert>

    <delete id="DeleteByBookId">
        DELETE FROM book_content WHERE book_id = #{bookId}
    </delete>

</mapper>
```

| 点 | 为什么 |
|---|---|
| `@Mapper` | 让 MyBatis 生成实现类并交给 Spring。**必须是 `interface`**，写成 `class` 会被静默跳过（启动报找不到 bean） |
| `@Param` | 有多个参数、或参数名会丢时必须写。单参数其实能省，但写上更稳 |
| 方法名首字母大写 | 项目现有风格（`GetBookById`、`GetAllBooks`），跟着走 |
| `namespace` 必须 = 接口全限定名 | 这是 XML 和接口对上号的唯一方式，**错一个字母就 `Invalid bound statement`** |
| `resultType="BookContent"` | 配了 `type-aliases-package: ...pojo.entity`，可以只写短类名 |
| `#{bookId}` | `#{}` 是**预编译占位符**（`?`），防 SQL 注入。`${}` 是字符串拼接，**别用** |
| `ON DUPLICATE KEY UPDATE` | 撞主键就改成 UPDATE，一条 SQL 同时管"新增"和"替换" |

**`VALUES(content)` 是什么意思？**
MySQL 方言：指"INSERT 里那一列准备插入的值"。所以 `content = VALUES(content)` 就是"新值覆盖旧值"。

> MySQL 8.0.20 之后官方推荐别名写法（`AS new ... SET content = new.content`），
> 但 `VALUES()` 仍然能用且更简单，学习阶段用它就好。

**`int Save(...)` 为什么返回 int？** 返回受影响的行数。
- 新增 → 1
- `ON DUPLICATE KEY UPDATE` 命中并更新 → **2**（MySQL 的约定）
- 值完全没变 → 0

不看返回值也能跑，但知道这个数可以判断"到底插了还是改了"。

### 6.3 `ReaderProgressMapper`（新建 · 3 个方法）

`mapper/ReaderProgressMapper.java`：

```java
@Mapper
public interface ReaderProgressMapper {

    /** 取某个用户对某个目标的进度 */
    ReaderProgress Get(@Param("userId") Integer userId,
                       @Param("targetType") Integer targetType,
                       @Param("targetId") Long targetId);

    /** 有则改、无则插（靠 UNIQUE KEY 触发） */
    int Save(ReaderProgress progress);

    /** 正文被删时，连带清掉所有人对它的进度 */
    void DeleteByTarget(@Param("targetType") Integer targetType,
                        @Param("targetId") Long targetId);
}
```

`resources/mapper/ReaderProgressMapper.xml`：

```xml
<mapper namespace="org.libaray_manager_system.mapper.ReaderProgressMapper">

    <select id="Get" resultType="ReaderProgress">
        SELECT id, user_id, target_type, target_id, chapter_index, chapter_title, percent, update_time
        FROM reader_progress
        WHERE user_id = #{userId}
          AND target_type = #{targetType}
          AND target_id = #{targetId}
    </select>

    <insert id="Save">
        INSERT INTO reader_progress (user_id, target_type, target_id, chapter_index, chapter_title, percent)
        VALUES (#{userId}, #{targetType}, #{targetId}, #{chapterIndex}, #{chapterTitle}, #{percent})
        ON DUPLICATE KEY UPDATE chapter_index = VALUES(chapter_index),
                                chapter_title = VALUES(chapter_title),
                                percent       = VALUES(percent)
    </insert>

    <delete id="DeleteByTarget">
        DELETE FROM reader_progress WHERE target_type = #{targetType} AND target_id = #{targetId}
    </delete>

</mapper>
```

**这里"撞"的是哪个键？** 不是主键 `id`（自增，永远不冲突），而是
`UNIQUE KEY uk_progress (user_id, target_type, target_id)`。

所以同一用户对同一目标重复写进度，永远不会多出一行 —— 这正是第 1 步建唯一索引的意义。

> **`DeleteByTarget` 为什么不带 `user_id`？**
> 它是"正文被删了，顺手把所有人的进度都清掉"，本来就该跨用户。
> 和 `Get`/`Save` 那种"只动自己"的语义完全不同 —— **看方法名就知道该不该带 userId**。

`mapper/ReaderFileMapper.java`：

```java
@Mapper
public interface ReaderFileMapper {

    int Save(ReaderFile file);

    /** 我的文件列表（★ 不带正文，分页） */

                                @Param("startIndex") Integer startIndex);

    Integer GetMyFileCount(@Param("dto") ReaderFileSelectDto dto,
                           @Param("userId") Integer userId);

    /** 删除（带归属） */
    void DeleteByIdAndUser(@Param("id") Long id, @Param("userId") Integer userId);
}
```

`resources/mapper/ReaderFileMapper.xml`：

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="org.libaray_manager_system.mapper.ReaderFileMapper">

    <!-- useGeneratedKeys + keyProperty：插入后把自增 id 写回 file.id，
         前端要拿这个 id 立刻跳到阅读页 -->
    <insert id="Save" useGeneratedKeys="true" keyProperty="id">
        INSERT INTO reader_file (user_id, title, content, word_count, chapter_count, encoding)
        VALUES (#{userId}, #{title}, #{content}, #{wordCount}, #{chapterCount}, #{encoding})
    </insert>

    <select id="GetByIdAndUser" resultType="ReaderFile">
        SELECT id, user_id, title, content, word_count, chapter_count, encoding, create_time
        FROM reader_file
        WHERE id = #{id} AND user_id = #{userId}
    </select>

    <!-- ★ 列表故意不查 content：一页 10 个文件，可能几十 MB 正文，列表一条都用不上 -->
    <select id="GetMyFiles" resultType="ReaderFile">
        SELECT id, user_id, title, word_count, chapter_count, encoding, create_time
        FROM reader_file
        WHERE user_id = #{userId}
        <if test="dto.title != null and dto.title != ''">
            AND title LIKE CONCAT('%', #{dto.title}, '%')
        </if>
        ORDER BY create_time DESC
        LIMIT #{startIndex}, #{dto.pageSize}
    </select>

    <select id="GetMyFileCount" resultType="java.lang.Integer">
        SELECT COUNT(*)
        FROM reader_file
        WHERE user_id = #{userId}
        <if test="dto.title != null and dto.title != ''">
            AND title LIKE CONCAT('%', #{dto.title}, '%')
        </if>
    </select>

    <delete id="DeleteByIdAndUser">
        DELETE FROM reader_file WHERE id = #{id} AND user_id = #{userId}
    </delete>

</mapper>
```

| 点 | 为什么 |
|---|---|
| `useGeneratedKeys="true" keyProperty="id"` | 数据库生成的自增 id 回填到 `file.getId()`，Service 才能拿它返回给前端 |
| `GetByIdAndUser` 带 `user_id` | 路径里的 `{id}` 是前端传的，可以随便改。不带 `user_id` = 改个数字就能读别人的文件 |
| **`GetMyFiles` 不查 `content`** | ★ 列表只要标题/字数/章数。查了 `LONGTEXT` 等于翻一页拖几十 MB |
| `LIMIT #{startIndex}, #{dto.pageSize}` | MySQL 的分页语法：`LIMIT 偏移量, 条数`，偏移量从 0 开始 |
| `<if test="...">` | 动态 SQL：`title` 空的时候这一句整段不拼进 SQL |
| `ORDER BY create_time DESC` | 最新上传的排前面 |
| `resultType="java.lang.Integer"` | `COUNT(*)` 用全限定名，避免别名解析歧义 |

#### ★ 一个 3.0 踩过的坑：`Count` 和 `List` 的 WHERE 必须完全一致

`GetMyFileCount` 和 `GetMyFiles` 的 `<if>` 条件、`WHERE` 子句**必须逐字一致**。
不然会出现"列表里 3 条，分页器显示总共 100 条，能翻到空页"。

> 3.0 写借阅列表时真踩过：`GetAllBorrowCount` 少写了 `LEFT JOIN`，
> 结果条件里用到 `u.username` 时直接报 **`Unknown column 'u.username' in 'where clause'`** ——
> 这种错**编译期完全看不出来**，只有调接口才炸。

#### 为什么不需要单独的"轻量查询"？

你可能会想："`GetFileInfo` 只要标题和字数，是不是要再写一个不带 content 的方法？"
不用 —— `GetFileInfo` 要返回 `chapterCount`，而列表之外的那几个接口（meta / chapter / info）
本来就要用正文，直接用 `GetByIdAndUser` 把整行查回来最简单。

**只有"列表"这一个场景明确不需要正文**，所以只有 `GetMyFiles` 单独一个不查 `content` 的 SQL。

### 6.5 `BookMapper`：要加的那一个方法

这是唯一需要**改已有文件**的地方。

`mapper/BookMapper.java` 里加一行：

```java
    /** 4.0：只改"是否开启在线阅读"这一个字段 */
    int UpdateReadable(@Param("id") Integer id, @Param("readable") Integer readable);
```

`resources/mapper/BookMapper.xml` 里加一条：

```xml
    <update id="UpdateReadable">
        UPDATE book SET readable = #{readable} WHERE id = #{id}
    </update>
```

**为什么不复用现有的 `UpdateBook`？**

`BookMapper.UpdateBook` 的签名是一堆显式参数（ISBN、书名、价格、总册数、可借数…），
为了改一个 `readable` 去凑那十几个参数，很容易把别的字段改成 `null` 或 0 —— **风险远大于收益**。

**为什么返回 `int`？** 用受影响行数判断书存不存在：

```java
int rows = bookMapper.UpdateReadable(bookId, readable);
if (rows == 0) {
    throw new BusinessException("图书不存在");   // 没有这一行，UPDATE 影响 0 行
}
```

> 这是一个很好用的模式：**UPDATE / DELETE 返回的 int 就是"有没有命中"**，
> 比先 `SELECT` 再 `UPDATE` 少一次查询，而且没有并发窗口。
>
> ⚠️ 但注意：MySQL 里"值没变"时受影响行数是 **0**（不是 1）。
> 所以如果用户把开关从 1 再点成 1，`rows` 会是 0 —— 会被误判成"图书不存在"。
> 稳妥写法是先查一次书，或者用 `useAffectedRows=true` 让 MySQL 统计"匹配行"而不是"实际改动行"。

### 6.6 四个 Mapper 的共同要点

| 要点 | 说明 |
|---|---|
| 接口 + XML **必须配对** | 接口在 `java/.../mapper/`，XML 在 `resources/mapper/`，`namespace` = 接口全限定名 |
| 用 `#{}`，不用 `${}` | `#{}` 预编译防注入；`${}` 是拼字符串 |
| 短类名靠 `type-aliases-package` | `resultType="ReaderFile"` 能识别，是因为 yml 里配了 `pojo.entity` 包 |
| 驼峰自动映射 | `chapter_count` → `chapterCount`，靠 `map-underscore-to-camel-case: true`，**不用手写 `@Results`** |
| 多参数一定加 `@Param` | 否则 XML 里只能用 `arg0`/`param1`，改个名就崩 |
| 大字段不要出现在列表 SQL 里 | `content`/`intro` 这类 `LONGTEXT`，列表查询里显式列字段名，别 `SELECT *` |

## 七、第 7 步：Service

### 7.1 文件怎么分、接口有哪些方法

#### 建几个文件？

**两个**，和项目里其他模块完全一致：

```
src/main/java/org/libaray_manager_system/
├── service/
│   └── ReaderService.java          ← 接口：只写方法签名，不写实现
└── service/Impl/
    └── ReaderServiceImpl.java      ← 实现：@Service + @Transactional 在这里
```

| 为什么拆成"接口 + 实现" | 说明 |
|---|---|
| 对齐项目现有风格 | `BookService`/`BookServiceImpl`、`BorrowService`/`BorrowServiceImpl` 全是这个结构 |
| Controller 只依赖接口 | `@Autowired private ReaderService readerService;` —— Controller 完全不知道实现类叫什么 |
| 以后想加缓存、换实现 | 换个实现类即可，Controller 一行都不用改 |

> ⚠️ 实现类放在 `service/Impl/`（**大写 I**）。包名是 `org.libaray_manager_system.service.impl`。
> Windows 的文件系统不区分大小写，写成 `impl` 也能编译通过，但**部署到 Linux 会直接找不到类**。

#### 实现类要注入哪几个 Mapper？

```java
@Service
public class ReaderServiceImpl implements ReaderService {

    @Autowired private BookMapper bookMapper;                 // 拿 readable 开关 + 书名
    @Autowired private BookContentMapper bookContentMapper;   // 书籍正文
    @Autowired private ReaderFileMapper readerFileMapper;     // 用户上传的 txt
    @Autowired private ReaderProgressMapper progressMapper;   // 阅读进度
}
```

四个 Mapper 的分工：

| Mapper | 管哪张表 | 在哪些方法里用 |
|---|---|---|
| `BookMapper` | `book` | 判书存不存在、拿 `readable`、拿书名、改 `readable` |
| `BookContentMapper` | `book_content` | 上传/删除/读取书籍正文 |
| `ReaderFileMapper` | `reader_file` | 用户文件的上传/列表/删除/读取 |
| `ReaderProgressMapper` | `reader_progress` | 存进度、取上次读到哪 |

> **已经有 `BookMapper` 了，为什么还要新建 3 个？**
> 一个 Mapper 对应一张主表，是 MyBatis 的常规做法。
> 把 `book_content` 的 SQL 塞进 `BookMapper` 也能跑，但那个文件会越来越长，
> 而且"改正文"和"改图书信息"本来就是两件事。

#### 接口里的 13 个方法

13 个方法对 13 个接口，一一对应：

| # | 方法签名 | 对应接口 | 谁能调 |
|---|---|---|---|
| 1 | `void SetBookReadable(Integer bookId, Integer readable)` | `PUT /books/{id}/readable` | 管理员 |
| 2 | `void UploadBookContent(Integer bookId, MultipartFile file)` | `POST /reader/book/{id}/content` | 管理员 |
| 3 | `void DeleteBookContent(Integer bookId)` | `DELETE /reader/book/{id}/content` | 管理员 |
| 4 | `ReaderMetaVo GetBookMeta(Integer bookId, LoginUser loginUser)` | `GET /reader/book/{id}/meta` | 登录 |
| 5 | `ReaderChapterVo GetBookChapter(Integer bookId, Integer index)` | `GET /reader/book/{id}/chapter/{index}` | 登录 |
| 6 | `void SaveBookProgress(Integer bookId, ReaderProgressDto dto, LoginUser loginUser)` | `PUT /reader/book/{id}/progress` | 登录 |
| 7 | `ReaderFileVo UploadFile(MultipartFile file, String title, LoginUser loginUser)` | `POST /reader/file` | 登录 |
| 8 | `readerFilePageResult GetMyFiles(ReaderFileSelectDto dto, LoginUser loginUser)` | `GET /reader/file` | 登录 |
| 9 | `ReaderFileVo GetFileInfo(Long fileId, LoginUser loginUser)` | `GET /reader/file/{id}` | 登录 |

**四处值得注意的差别：**

1. **返回 `void` 的六个方法**（1、2、3、6、12、13）—— 它们只改数据，
   Controller 那边统一返回 `new Result().success("xxx成功", null)`，不需要 data
2. **`GetBookChapter` 没有 `LoginUser` 参数**（第 5 行）—— 书籍正文只要开关开着，谁都能读，
   不需要知道是谁在读。而文件那半（10、11、12、13）**必须**带 `loginUser`，因为要校验"是不是你的"
3. **`UploadFile` 返回 `ReaderFileVo`** —— 上传成功后前端要立刻跳到阅读页，
   得拿到新文件的 `id`；而 `UploadBookContent` 返回 `void`，因为书的 id 早就在路径里了
4. **`SetBookReadable` 也放在这个 Service**（第 1 行）—— 它改的是 `book` 表，照理可以放进 `BookService`。
   放在这里是为了让 4.0 的代码全部集中在**一个 Service + 一个 Controller** 里，
   你调试时不用在两个模块之间跳。代价是 `ReaderServiceImpl` 要 `@Autowired BookMapper` —— 这个取舍我接受。

#### 私有方法（不对外，但很关键）

| 私有方法 | 干什么 | 谁在调 |
|---|---|---|
| `String GetReadableText(Integer bookId)` | 校验书籍可读性 + 取回正文 | 4、5 |
| `ReaderFile GetOwnFile(Long fileId, LoginUser loginUser)` | 校验"这文件是不是你的" + 取回 | 9、10、11、12、13 |
| `List<ChapterItemVo> SplitChapters(String text)` | 切章并转成目录 VO | 4、10（两个 meta）+ **7**（文件上传要算章数存库） |
| `Integer CountWords(String text)` | 去掉空白后的字数 | 2、7（两个上传） |
| `Integer StartIndex(ReaderFileSelectDto dto)` | 算 `(pageNum-1) * pageSize` | 8（分页） |

★ **`SplitChapters` 和 `CountWords` 是两条路共用的。**
书籍和你上传的 txt，切章规则、字数规则完全一样 —— 这种"纯文本处理"不要在 Service 里写两遍，
一处改了两处生效，才不会出现"馆藏书能切章、自己的文件切不出来"这种莫名其妙的不一致。

#### 为什么两块要放在同一个 Service 里？

另一种做法是拆成 `BookReaderService` 和 `FileReaderService` 两个接口。这里选合并，原因：

| 理由 | 说明 |
|---|---|
| 共享 3 个私有方法 | 拆开就得提取公共工具类，或者让两个 Service 互相调用 |
| 对应同一个 Controller | `ReaderController` 只有一个，依赖一个 Service 比依赖两个清爽 |
| 业务上是同一件事 | "在线阅读"就是一件事，只是内容来源有两种 |

**判断标准**：如果两个功能连"怎么读"的逻辑都不一样，就该拆；
这里数据源不同、但阅读逻辑完全同一套，所以合并更划算。

### 7.2 可读性校验：三层，顺序不能乱

> ⚠️ **先明确一件事：这段代码只管「书籍正文」，不管「用户上传的 txt」。**
> 这是两条**完全分开**的路。用户文件那条在 7.6，**它根本不碰 `bookMapper`**。

```java
private String GetReadableText(Integer bookId) {
    // ① 书存在吗
    Book book = bookMapper.GetBookById(bookId);
    if (book == null) throw new BusinessException("图书不存在");

    // ② 开关开了吗
    if (!Integer.valueOf(1).equals(book.getReadable())) {
        throw new BusinessException("这本书还没有开启在线阅读");
    }

    // ③ 正文上传了吗
    BookContent bc = bookContentMapper.GetByBookId(bookId);
    if (bc == null || bc.getContent() == null || bc.getContent().isBlank()) {
        throw new BusinessException("这本书的正文还没上传");
    }
    return bc.getContent();
}
```

#### 为什么第 ① 步非查 `bookMapper` 不可？

**不是为了"限制谁能读"**，而是这一查同时拿到了三样东西：

| 拿到什么 | 少了会怎样 |
|---|---|
| **这本书到底存不存在** | 前端瞎传一个 `bookId=99999`，下一行 `book.getReadable()` 直接 **NPE 空指针** → 接口 500 |
| **`readable` 开关的值** | 没有它就不知道管理员到底开没开这本书的电子版 |
| **书名 `book.getName()`** | 目录接口要返回 `title`，不查书表就没名字（`book_content` 表里只有正文，没有书名） |

所以这一行不是"多余的校验"，是**必须的取数**。

#### 那"我自己上传的书不在书单里"怎么办？

**这是关键点：用户上传的 txt 永远不会进 `book` 表。**

两个表装的是两种完全不同的东西：

| | `book`（图书表） | `reader_file`（用户文件表） |
|---|---|---|
| 谁维护 | **管理员**（图书管理页面增删改） | **用户自己**（我的书库页面上传） |
| 代表什么 | 图书馆的**馆藏** —— 有 ISBN、作者、出版社、库存 | 用户**私人的 txt** —— 只有标题和正文 |
| 会出现在图书列表吗 | 会 | **不会**，它只出现在"我的书库" |
| 要借阅吗 | 要 | 不要，自己传的自己随时读 |
| 正文存在哪 | `book_content`（外键 = `book.id`） | `reader_file`（自带 `user_id`） |

所以你的担心场景是这样的：

```
用户上传 三体.txt
  → 存进 reader_file 表（user_id = 当前用户，id = 12）
  → 图书列表里【查不到】它  ← 这是对的，它不是馆藏
  → 但用户能读它：/reader/file/12  ← 走的是文件那条路，不查 book 表
```

**两条读路径的对照：**

| 你想读 | 前端请求 | 后端查哪些表 | "能不能读"取决于 |
|---|---|---|---|
| 图书列表里某本书的电子版 | `/reader/book/{bookId}/...` | `book` + `book_content` | `book.readable = 1` 且有正文 |
| 自己上传的 txt | `/reader/file/{fileId}/...` | **只查 `reader_file`** | **是不是你自己的**（`user_id` 对上） |

> **如果你希望用户上传的 txt 也能出现在图书列表里**（也就是"用户投稿，管理员审核后转成馆藏"），
> 那是另一个功能：要先建 `book` 记录、再上传正文，还要审核流程。4.0 不做这件事。

#### 顺序为什么重要？

如果先判 ③ 再判 ②，用户会看到"正文还没上传"—— 可实际上这本书压根没开启阅读，
那条提示就误导人了。**从外到内依次校验，报错才准确。**

### 7.3 上传正文的完整流程

```java
@Transactional
public void UploadBookContent(Integer bookId, MultipartFile file) {
    // 1. 文件本身合法吗
    if (file == null || file.isEmpty()) throw new BusinessException("请选择要上传的 txt 文件");
    String original = file.getOriginalFilename();
    if (original == null || !original.toLowerCase().endsWith(".txt")) {
        throw new BusinessException("只支持 .txt 文件");
    }
    if (file.getSize() > 10L * 1024 * 1024) throw new BusinessException("文件不能超过 10MB");

    // 2. 书存在吗
    if (bookMapper.GetBookById(bookId) == null) throw new BusinessException("图书不存在");

    // 3. 拿字节 → 检测编码 → 统一换行
    byte[] bytes;
    try {
        bytes = file.getBytes();
    } catch (IOException e) {
        throw new BusinessException("读取上传文件失败");
    }
    TextDecodeUtil.Decoded decoded = TextDecodeUtil.decode(bytes);
    String text = decoded.text().replace("\r\n", "\n").replace('\r', '\n');
    if (text.isBlank()) throw new BusinessException("文件内容为空");

    // 4. 存
    BookContent content = new BookContent();
    content.setBookId(bookId);
    content.setContent(text);
    content.setWordCount(CountWords(text));
    content.setEncoding(decoded.charset());
    bookContentMapper.Save(content);
}
```

**为什么第 3 步的换行统一不能省？**

Windows 的 txt 每行结尾是 `\r\n`（两个字符）。如果不统一：

| 影响 | 后果 |
|---|---|
| 章节正则 | `[^\n]{0,40}$` 会把行尾的 `\r` 也算进标题 → 标题里带着看不见的字符 |
| `contentStart + 1` | 只跳过了 `\n`，`\r` 留在了正文开头 |
| 字数统计 | 多算了每个换行的 `\r` |

统一成 `\n` 之后，上面三个问题一起消失。

**为什么用 `file.getBytes()` 而不是 `file.getInputStream()`？**

因为编码检测需要**完整字节**才能判断（UTF-8 的判定要看所有字节）。
2~10MB 一次性读进内存完全可以接受，流式处理反而让检测变复杂。

### 7.4 章节为什么每次现切，不落库

这是我和方案里最初想法不同的地方，值得说清楚：

| 做法 | 好处 | 坏处 |
|---|---|---|
| **章节落库**（`chapter` 表或 JSON 列） | 每次请求省一次正则扫描 | 正文一换就要删旧章节、插新章节；两处不同步就出错 |
| **每次现切**（推荐） | 正文是唯一真相，永不不同步；少一张表 | 每次请求多一次正则（2MB 约几十毫秒） |

对这个规模（几十本书、一次一个人读）来说，**几十毫秒换掉一整类不一致 bug 是赚的**。

而且真到了要优化的时候，加一层缓存（项目里已经有 `CacheUtil`）比维护章节表简单得多。

```java
public void SaveProgress(Integer bookId, ReaderProgressDto dto, LoginUser loginUser) {
    if (dto == null || dto.getChapterIndex() == null || dto.getChapterIndex() < 0) {
```

### 7.6 用户上传的文件：另一条完全不同的路

**为什么不能共用 7.2 那个方法？** 因为"能不能读"的规则根本不一样：

| | 书籍正文 | 用户上传的 txt |
|---|---|---|
| 数据在哪 | `book_content`（挂在 `book` 上） | `reader_file`（自带 `user_id`） |
| 要管理员开开关吗 | **要**（`book.readable`） | **不要** —— 自己传的自己当然能读 |
| "能不能读"看什么 | 开关 = 1 **且** 有正文 | **是不是你自己的**（`user_id` 对上） |
| 要查 `bookMapper` 吗 | 要（拿开关 + 书名） | **完全不查** |

所以文件这条路的校验只有一步 —— 把 `bookMapper` 换成"归属校验"：

```java
/** 取用户自己的文件：核心就是 SQL 里带上 user_id */
private ReaderFile GetOwnFile(Long fileId, LoginUser loginUser) {
    ReaderFile file = readerFileMapper.GetByIdAndUser(fileId, loginUser.getId());
    if (file == null) {
        // 故意不区分"不存在"和"不是你的"（原因见下）
        throw new BusinessException("文件不存在");
    }
    return file;
}
```

对应 Mapper：

```java
ReaderFile GetByIdAndUser(@Param("id") Long id, @Param("userId") Integer userId);
```

```xml
<select id="GetByIdAndUser" resultType="ReaderFile">
    SELECT id, user_id, title, content, word_count, encoding, create_time
    FROM reader_file
    WHERE id = #{id} AND user_id = #{userId}
</select>
```

#### ★ `AND user_id = #{userId}` 是这条 SQL 唯一的防线

少了它，前端只要把 `/reader/file/12` 里的 `12` 改成 `13`，就能读到别人的文件 ——
这叫 **IDOR（不安全直接对象引用）**，是 Web 里最常见的越权漏洞。

而 `userId` **只能从 `loginUser` 里取**（也就是 token 解出来的），绝不能用前端传的。

```java
// ❌ 这样写等于没校验：前端传什么就用什么
public ReaderFile GetFile(Long id, Integer userId) { ... }

// ✅ userId 来自 token
public ReaderFile GetFile(Long id, LoginUser loginUser) {
    return GetOwnFile(id, loginUser);
}
```

#### "文件不存在"为什么故意写得含糊？

如果报错区分成「文件不存在」和「无权访问」，攻击者就能靠两种不同的报错，
一个个试出**哪些 id 是真实存在的**（先探测，再想办法）。

统一返回"文件不存在"最安全，正常用户也感觉不到损失 —— 他本来就不该看到别人的文件。

#### 两个 Service 方法的完整对照

```java
// ===== 书籍：要查 book（拿开关和书名）=====
@Override
public ReaderMetaVo GetBookMeta(Integer bookId, LoginUser loginUser) {
    Book book = bookMapper.GetBookById(bookId);
    if (book == null) throw new BusinessException("图书不存在");
    // …判 readable、判有正文、切章节、查进度
}

// ===== 文件：只查 reader_file（认人，不认开关）=====
@Override
public ReaderMetaVo GetFileMeta(Long fileId, LoginUser loginUser) {
    ReaderFile file = GetOwnFile(fileId, loginUser);     // ← 唯一的校验
    List<ChapterSplitUtil.Chapter> chapters = ChapterSplitUtil.split(file.getContent());
    // …切章节、查进度
}
```

看到了吗：**文件那条路里，`bookMapper` 一次都没出现。**
你说"我自己上传的书书单里没有读不了"—— 那个场景走的是下面这个方法，它压根不关心书单。

## 八、第 8 步：Controller

### 8.1 注解逐个解释

```java
@RestController
public class ReaderController {

    @Autowired
    private ReaderService readerService;

    // 目录 + 可读性（不含正文）
    @GetMapping("/reader/book/{bookId}/meta")
    public Result GetBookMeta(@PathVariable Integer bookId,
                              @RequestAttribute("loginUser") LoginUser loginUser) {
        return new Result().success(readerService.GetBookMeta(bookId, loginUser));
    }
}
```

| 注解 | 作用 |
|---|---|
| `@RestController` | = `@Controller` + `@ResponseBody`，返回值自动转成 JSON |
| `@GetMapping` | 只接受 GET。用错方法会得到 405 |
| `@PathVariable` | 把路径里的 `{bookId}` 绑到参数上。`/reader/book/12/meta` → `bookId = 12` |
| `@RequestAttribute("loginUser")` | 从 request 作用域取对象。这个 `loginUser` 是 **`AuthInterceptor` 解析 token 后塞进去的** —— 不是前端传的 |
| `Result` | 项目统一的返回包装：`{code, msg, data}`，`code=1` 成功 |

**`@PatchMapping` / `@PutMapping` 怎么选？**

| 方法 | 语义 | 本项目用法 |
|---|---|---|
| GET | 查，不改数据 | 所有查询 |
| POST | 新建 | 上传（新建正文） |
| PUT | **整体替换 / 幂等设置** | 设置 `readable`、保存进度 |
| PATCH | **局部修改** | 归还、续借、撤销（`/borrows/{id}/return`） |
| DELETE | 删除 | 删除正文 / 文件 |

### 8.2 文件上传的写法（和普通接口不一样）

```java
@RequireAdmin
@PostMapping("/reader/book/{bookId}/content")
public Result UploadContent(@PathVariable Integer bookId,
                            @RequestParam("file") MultipartFile file) {
    readerService.UploadBookContent(bookId, file);
    return new Result().success("正文已上传", null);
}
```

| 点 | 说明 |
|---|---|
| 参数类型是 `MultipartFile` | 不能用 `@RequestBody`，也不能用 `String` |
| `@RequestParam("file")` | 名字必须和前端 `FormData.append('file', ...)` 的一致。**对不上会报 400 "Required part 'file' is not present"** |
| 没有 `consumes` | Spring 会自动从 multipart 请求里绑，不用写 |
| 前端必须发 `multipart/form-data` | 用 `FormData` 发，**不要**手动设置 `Content-Type`（浏览器要自己加 `boundary`） |

### 8.3 `@RequireAdmin` 是怎么生效的

```java
@RequireAdmin
@PostMapping("/reader/book/{bookId}/content")
```

这个注解是项目自定义的，配合 `AuthInterceptor` 工作：

1. 请求进来 → `AuthInterceptor.preHandle` 解析 token，把 `LoginUser` 放进 request
2. 检查目标方法上有没有 `@RequireAdmin`、当前用户是不是 `ADMIN`
3. 不是 → 返回 **403**（注意：不是 401。**401 = 你是谁我不知道；403 = 我知道你是谁，但你不能干这个**）

普通用户点上传 → 前端会收到 403 → `request.js` 弹出"没有操作权限" ✓

### 8.4 路由冲突要注意

`/reader/book/{bookId}/meta` 和 `/reader/book/{bookId}/chapter/{index}` 都是模板路径，不冲突。

但如果你以后加一个 `/reader/book/stats` 这种**字面路径**，要注意：
Spring 6 的 `PathPattern` 里**字面段优先级高于模板段**，所以 `/reader/book/stats` 会优先命中字面路径，不会当成 `bookId="stats"`。

> 反例：`/books/{id}` 会把 `DELETE /books/batch` 当成 `id="batch"` 然后类型转换失败 → 500。
> 这就是 3.0 里"批量删除"踩过的坑。

## 九、第 9 步：接口详细规格

### 9.1 `PUT /books/{id}/readable` —— 开关在线阅读

**权限**：管理员

**请求头**

```
Authorization: Bearer <token>
Content-Type: application/json
```

**路径参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | Integer | 是 | 图书 id |

**请求体**

```json
{ "readable": 1 }
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `readable` | Integer | 是 | `1` 开启 / `0` 关闭 |

**成功返回**

```json
{ "code": 1, "msg": "操作成功", "data": null }
```

**失败情况**

| 情况 | HTTP | code | msg |
|---|---|---|---|
| 图书不存在 | 200 | 0 | 图书不存在 |
| `readable` 不是 0/1 | 200 | 0 | 开关值不合法 |
| 非管理员 | 403 | — | 没有操作权限 |

---

### 9.2 `POST /reader/book/{bookId}/content` —— 上传书籍正文

**权限**：管理员

**请求头**

```
Authorization: Bearer <token>
Content-Type: multipart/form-data; boundary=...
```

> ⚠️ `boundary` 由浏览器自动生成，**前端不要手写这个头**，交给 `FormData`。

**表单字段**

| 字段名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `file` | File | 是 | `.txt` 文件，≤10MB |

**成功返回**

```json
{ "code": 1, "msg": "正文已上传", "data": null }
```

**失败情况**

| 情况 | HTTP | msg |
|---|---|---|
| 没传文件 | 200 | 请选择要上传的 txt 文件 |
| 不是 .txt | 200 | 只支持 .txt 文件 |
| 超过 10MB | 200 | 文件不能超过 10MB |
| 超过 Spring 上限 | **413** | （默认错误页，见第 2 步） |
| 编码识别不出 | 200 | 无法识别文件编码，请另存为 UTF-8 后重新上传 |
| 内容是空的 | 200 | 文件内容为空 |
| 非管理员 | 403 | 没有操作权限 |

---

### 9.3 `DELETE /reader/book/{bookId}/content` —— 删除书籍正文

**权限**：管理员

**副作用**：同时删除所有人对这本书的阅读进度（正文都没了，进度没意义）。

**成功返回**

```json
{ "code": 1, "msg": "正文已删除", "data": null }
```

---

### 9.4 `GET /reader/book/{bookId}/meta` —— 书籍目录

**权限**：登录用户

**成功返回（能读）**

```json
{
  "code": 1,
  "msg": "操作成功",
  "data": {
    "title": "深海之门",
    "readable": true,
    "hasContent": true,
    "denyReason": null,
    "chapterCount": 3,
    "wordCount": 57,
    "encoding": "GB18030",
    "lastChapter": 1,
    "chapters": [
      { "index": 0, "title": "第一章 潜入", "wordCount": 21 },
      { "index": 1, "title": "第二章 回声", "wordCount": 18 },
      { "index": 2, "title": "第三章 灯灭", "wordCount": 18 }
    ]
  }
}
```

**成功返回（不能读）** —— 注意 HTTP 仍是 200，`code` 仍是 1

```json
{
  "code": 1,
  "msg": "操作成功",
  "data": {
    "title": "深海之门",
    "readable": false,
    "hasContent": true,
    "denyReason": "这本书还没有开启在线阅读",
    "chapterCount": 3,
    "wordCount": 57,
    "chapters": [],
    "lastChapter": 0,
    "encoding": "GB18030"
  }
}
```

**为什么"不能读"不返回错误？**

因为"这本书没开启阅读"是**正常的业务状态**，不是错误。
前端拿到 `readable=false` 后显示一句提示就行，不需要走异常分支。

> 对比：「图书不存在」（id 是瞎填的）才是异常 → `code=0`。

**字段说明**：见 5.3

---

### 9.5 `GET /reader/book/{bookId}/chapter/{index}` —— 单章正文

**路径参数**

| 参数 | 类型 | 说明 |
|---|---|---|
| `bookId` | Integer | 图书 id |
| `index` | Integer | 章节序号，**从 0 开始** |

**成功返回**

```json
{
  "code": 1,
  "data": {
    "index": 1,
    "title": "第二章 回声",
    "content": "水声从很深的地方传来。\n他停下脚步。\n",
    "prevIndex": 0,
    "nextIndex": 2
  }
}
```

| 字段 | 说明 |
|---|---|
| `index` | 当前章序号（0 起） |
| `title` | 章节标题 |
| `content` | **不含标题行的正文**，段落之间是 `\n` |
| `prevIndex` | 上一章序号，**第一章为 `null`** |
| `nextIndex` | 下一章序号，**最后一章为 `null`** |

**失败情况**

| 情况 | msg |
|---|---|
| 章节序号越界 | 章节不存在 |
| 书没开启阅读 | 这本书还没有开启在线阅读 |
| 正文没上传 | 这本书的正文还没上传 |

### 9.6 `PUT /reader/book/{bookId}/progress` —— 保存进度

**请求体**

```json
{ "chapterIndex": 37, "chapterTitle": "第三十八章 灯灭", "percent": 42.5 }
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `chapterIndex` | Integer | 是 | 章节序号，≥0 |
| `chapterTitle` | String | 否 | 存下来方便以后显示"上次读到 xxx" |
| `percent` | BigDecimal | 否 | 章节内滚动百分比 0~100，不传按 0 |

**成功返回**

```json
{ "code": 1, "msg": "进度已保存", "data": null }
```

### 9.7 用户文件相关的 7 个接口

套路和上面完全一样，只多一条铁律：**每条 SQL 都必须带 `user_id`**。

| 接口 | 和书籍版的差别 |
|---|---|
| `POST /reader/file` | 多一个 `title` 字段（可空，空则用文件名） |
| `GET /reader/file?pageNum&pageSize` | 返回分页，只查自己的 |
| `DELETE /reader/file/{id}` | 只能删自己的，否则 404 |
| `GET /reader/file/{id}/meta` | 同书籍版，但 `readable` 恒为 `true`（自己的文件总能读） |
| `GET /reader/file/{id}/chapter/{index}` | 同 |
| `PUT /reader/file/{id}/progress` | `target_type = 2` |
| `GET /reader/file/{id}` | 返回 `{id, title, wordCount, chapterCount, createTime}` |

**上传我的 txt**（`POST /reader/file`）请求：

```
Content-Type: multipart/form-data
file:  <File>    必填
title: <String>  可空
```

**我的文件列表**返回：

```json
{
  "code": 1,
  "data": {
    "total": 3,
    "list": [
      { "id": 12, "title": "三体", "wordCount": 210034, "chapterCount": 42,
        "createTime": "2026-11-04T20:15:00" }
    ]
  }
}
```

## 十、联调自测（用 curl 走一遍）

### 10.1 拿 token

```powershell
$login = Invoke-RestMethod -Uri 'http://localhost:8081/auth/login' -Method Post `
    -ContentType 'application/json' -Body '{"username":"admin","password":"123456"}'
$token = $login.data.token
```

### 10.2 开启一本书的阅读

```powershell
Invoke-RestMethod -Uri 'http://localhost:8081/books/1/readable' -Method Put `
    -Headers @{ Authorization = "Bearer $token" } `
    -ContentType 'application/json' -Body '{"readable":1}'
```

### 10.3 上传正文（关键：`-F` 才是 multipart）

```powershell
# ★ 用 curl.exe，不要用 Invoke-RestMethod —— 后者拼 multipart 很麻烦
curl.exe -s -X POST "http://localhost:8081/reader/book/1/content" `
    -H "Authorization: Bearer $token" `
    -F "file=@D:\test.txt"
```

### 10.4 看目录、读第一章

```powershell
$h = @{ Authorization = "Bearer $token" }
Invoke-RestMethod -Uri 'http://localhost:8081/reader/book/1/meta' -Headers $h |
    ConvertTo-Json -Depth 4

Invoke-RestMethod -Uri 'http://localhost:8081/reader/book/1/chapter/0' -Headers $h |
    ConvertTo-Json -Depth 4
```

### 10.5 常见报错对照表

| 现象 | 原因 | 怎么修 |
|---|---|---|
| 413 | 超过 Spring 上限 | 第 2 步的 yml 没生效 / 没重启 |
| 400 `Required part 'file' is not present` | 表单字段名不是 `file` | 前端 `FormData.append('file', f)` |
| 415 Unsupported Media Type | 手动设了 `Content-Type: application/json` | 别设，让浏览器自己加 boundary |
| 500 `Invalid bound statement (not found)` | XML 的 `namespace` 或 `id` 写错 | 逐个字母核对 |
| 500 `Unknown column 'xxx'` | 实体字段没有对应列 / 列名拼错 | 对照第 1 步的表结构 |
| 正文全是 `���` | 编码检测没生效，或前端 `readAsText` 先解码了 | 见第 3 步 + 下面第 11 节第 2 条 |
| 章节只有 1 章叫「全文」 | 正则没匹配上 | 去掉 `(?m)` 试、检查 `^` 和全角空格 |
| 403 | 用普通用户调了管理员接口 | 换 admin 的 token |

## 十一、八个坑（按踩到概率排序）

| # | 坑 | 后果 | 处理 |
|---|---|---|---|
| 1 | Spring 默认 `max-file-size=1MB` | 稍大的 txt 直接 413 | 第 2 步 |
| 2 | 前端 `FileReader.readAsText()` 后再发 JSON | **GBK 文件在浏览器就乱码了，后端救不回** | 必须 `FormData` 传原始字节 |
| 3 | 章节正则不锚 `(?m)^` | 正文里"他翻到第三章"被切成章节 | 锚行首 + `{0,40}` |
| 4 | 书列表 `SELECT *` 带出正文 | 列表页每次拖几十 MB | 正文单独建表 |
| 5 | 前端用 `v-html` 渲染正文 | **XSS**（txt 里可以有 `<script>`） | 插值 + `white-space: pre-wrap` |
| 6 | 一次渲染整本 | 100 万字 DOM 卡死 | 按章拉取 |
| 7 | 章节偏移用字节算 | 中文被切半成乱码 | 全程用 `String.indexOf` / `substring` 的字符偏移 |
| 8 | 私有资源查询不带 `user_id` | 改个 id 就能看别人的文件 | SQL 里必须带归属条件 |

## 十二、前端会怎么调（给你联调时对照）

| 页面 | 调哪些接口 |
|---|---|
| 图书详情抽屉（所有用户） | `GET /reader/book/{id}/meta` → `readable=true` 才显示「在线阅读」按钮 |
| **阅读页** `/read/book/:id` | `meta` 拿目录 → `chapter/{i}` 拿正文 → `PUT progress` 存进度 |
| 图书列表「电子书」（管理员） | `PUT /books/{id}/readable`、`POST/DELETE /reader/book/{id}/content` |
| 我的 txt 页 `/my-files` | `GET /reader/file`、`POST /reader/file`、`DELETE /reader/file/{id}` |
| **阅读页** `/read/file/:id` | 和书籍版同一套，路径换成 `file` |

前端调用的约定（和现有模块一致）：

- 一律走 `utils/request.js`，`baseURL` 是 `/api`
- 成功时拦截器已经把 `data` 解包好了，业务代码拿到的就是 `data` 本身
- 失败时拦截器已经弹过提示，业务代码 `catch` 里通常什么都不用写
- 上传要传 `FormData`，**并且把超时调大**（默认 10 秒，10MB 文件可能不够）
