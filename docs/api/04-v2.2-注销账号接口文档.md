## 一、这个功能是什么

让**任何已登录的用户**（含管理员）在「个人中心」里**注销自己的账号**。

和已有的两个功能要分清：

| 功能 | 接口 | 谁操作 | 删谁 | 能不能恢复 |
|---|---|---|---|---|
| 退出登录 | `POST /auth/logout` | 任何人 | 不删，只清本地 token | —— |
| **管理员删用户** | `DELETE /users/{id}` | 管理员 | **别人** | ❌ 不能 |
| **注销自己**（本文档） | `DELETE /auth/account` | 任何人 | **自己** | ❌ 不能 |
| 禁用账号 | `PATCH /users/{id}/status` | 管理员 | 别人 | ✅ **能**（改回 1 就恢复） |

> 💡 **「注销」和「禁用」的区别要在产品上想清楚**：
> - 想**暂时不用** → 应该用「退出登录」或让管理员「禁用」
> - 想**彻底删号** → 才是「注销」
>
> 前端页面已经把这段话写给用户看了，避免他们误操作。

## 三、接口详情

### 1. 注销自己的账号

| 项 | 值 |
|---|---|
| 请求方法 | `DELETE` |
| 后端路径 | `/auth/account` |
| 前端请求 | `/api/auth/account` |
| 需要登录 | ✅ |
| 需要管理员 | ❌ **不需要**（普通读者也能注销自己） |

#### ★★ 最重要的一条：路径里【没有 id】

```
✅ DELETE /auth/account          ← 注销的是谁，由 token 决定
❌ DELETE /users/{id}            ← 千万不要！这是水平越权漏洞
❌ DELETE /auth/account?userId=1 ← 同样错误
```

**为什么这么强调**：注销是不可逆的破坏性操作。如果身份来自请求参数，
任何人都能把 URL 里的数字一改，去删掉别人的账号 —— 这比"改别人密码"严重得多。

**它是怎么知道"我是谁"的**：
`AuthInterceptor` 已经解析 token、查库、把 `LoginUser` 塞进 request 了，
Controller 用 `@RequestAttribute("loginUser")` 取出来即可 —— **不需要任何 id 参数**。

#### 请求体

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `password` | String | ✅ | **当前账号的登录密码**，用于二次确认 |

```json
{ "password": "123456" }
```

> **为什么要传密码？**
> 注销不可逆。如果只凭 token 就删，任何"拿到你未锁屏电脑的人"、
> 或者"XSS 偷到 token 的人"都能一键把号删了。
> 要求现场输入密码，等于强制一次"证明是你本人"。
>
> 注意：这里传的是**明文的当前密码**（走 HTTPS），后端用
> `BCrypt.checkpw(明文, 库里的哈希)` 校验 —— 和改密码接口一个套路。

#### 返回

**成功**（HTTP 200）：

```json
{ "code": 1, "msg": "账号已注销", "data": null }
```

#### 错误返回（都是 HTTP 200 + `code:0`，沿用 v2.0 的约定）

| 场景 | msg |
|---|---|
| 密码为空 | `请输入密码以确认注销` |
| 密码错误 | `密码不正确` |
| **是系统里最后一个管理员** | `系统至少需要保留一个管理员，不能注销最后一个管理员账号` |

#### 注销之后会发生什么

| 对象 | 结果 |
|---|---|
| 数据库里的 `sys_user` 那一行 | **被删除** |
| 用户手上的 token（还没过期的那张） | **立刻失效** |
| 前端本地 localStorage | 已清空，跳回登录页 |

> 💡 **"注销后旧 token 立刻失效"是怎么做到的？**
> 靠的是 `AuthInterceptor` 里那句"回库核对"：
> ```java
> sysUser sysuser = loginMapper.GetByUsername(JwtUtil.getUsername(claims));
> if (sysuser == null || ...) return reject(response, 401, "账号不存在或已被禁用");
> ```
> 用户被删了 → `GetByUsername` 返回 `null` → **401**。
> 所以**不需要**做 token 黑名单 —— v2.0 那个设计的价值在这里体现出来了 ✅

## 四、★ 后端实现要点（4 条，第 2 条最容易出事）

### 1. `WebConfig` **不要改！**（和注册接口正好相反）

```java
// WebConfig.java —— 保持原样，【不要】把 /auth/account 加进去
registry.addInterceptor(authInterceptor)
        .addPathPatterns("/**")
        .excludePathPatterns("/auth/login", "/auth/register");
        //                  ↑ 只有这两个是公开的，/auth/account 必须登录才能访问
```

> ⚠️ **别搞混了**：v2.1 的 `/auth/register` 要**加**进白名单（因为注册的人还没账号），
> v2.2 的 `/auth/account` 要**留在**拦截范围内（因为注销的人必须有账号）。
> 手一滑把 `/auth/account` 也放行了，就变成"不用登录就能注销" —— 那谁都删得掉任何人
> （因为 token 没有了，你的 service 就只能靠别的参数认人 → 直接掉进越权陷阱）。

### 2. 🔴 必须挡住「最后一个管理员」

这是本接口**唯一真正危险的边界**：

```
数据库现状：admin(ADMIN) + zhangsan(USER) + lisi(USER)

如果 admin 注销了自己：
   → 系统里【一个管理员都没有了】
   → 谁也进不去「用户管理」
   → 想新建管理员？没权限。想恢复 admin？没账号。
   → 🔒 系统永久锁死，只能手写 SQL 救
```

**所以必须加这道判断**：

```java
// 如果要注销的人是 ADMIN，先数一下还有几个管理员
if ("ADMIN".equals(loginUser.getRole())) {
    // ⚠️ 用 count > 1 判断，别写成 == 0
    if (userMapper.CountAdmin() <= 1) {
        throw new BusinessException("系统至少需要保留一个管理员，不能注销最后一个管理员账号");
    }
}
```

`UserMapper` 里加一个：

```xml
<!-- 统计管理员数量 -->
<select id="CountAdmin" resultType="int">
    SELECT COUNT(*) FROM sys_user WHERE role = 'ADMIN'
</select>
```

### 3. 密码二次确认

```java
sysUser user = userMapper.GetUserById(loginUser.getId());
if (dto.getPassword() == null || dto.getPassword().isEmpty()) {
    throw new BusinessException("请输入密码以确认注销");
}
if (!BCrypt.checkpw(dto.getPassword(), user.getPassword())) {
    throw new BusinessException("密码不正确");
}
```

> ⚠️ 注意顺序：**先校验密码，再判断"最后一个管理员"**。
> 反过来会让攻击者不用密码就能探测"系统里还剩几个管理员"。

Hmm，实际上这两个顺序都行，但"先验密码"更合理（先证明身份，再走业务规则）。让我在文档里写明。

### 4. 物理删除（和现有保持一致）

```xml
<delete id="DeleteById">
    DELETE FROM sys_user WHERE id = #{id}
</delete>
```

> **为什么选物理删除而不是"标记删除"？**
> 1. 和 `DELETE /users/{id}` 的现有语义保持一致；
> 2. `sys_user` 表上有 `UNIQUE KEY uk_user_username` —— 如果只是把 `status` 改成 0，
>    **那个用户名会被永久占用**，用户以后想用同名重新注册会撞"用户名已存在"，很困惑；
> 3. 课程项目阶段没有合规审计需求。
>
> ⚠️ **但 3.0 加了借阅记录之后，这个选择要重新评估**：
> 删用户会让他的借阅历史变成孤儿数据（外键指向不存在的用户）。
> 到时候要么改成逻辑删除 + 唯一索引加时间戳，要么加"有未归还图书不能注销"的判断。
> （v2.0 文档第 11 节已经提过同一个问题）

## 五、后端需要新增/改动的文件（清单）

| 文件 | 动作 | 说明 |
|---|---|---|
| `pojo/dto/CancelAccountDto.java` | 🆕 | 只有一个字段 `password` |
| `controller/Impl/LoginControllerImpl.java` | 🔧 | 加一个 `CancelAccount` 方法（不必新建 Controller） |
| `service/LoginService.java` + `Impl` | 🔧 | 加 `CancelAccount(LoginUser, CancelAccountDto)` |
| `mapper/UserMapper.java` + `.xml` | 🔧 | 加 `CountAdmin()` 和 `DeleteById(id)` |
| `config/WebConfig.java` | ❌ **不用改** | ★ 千万别把 `/auth/account` 加进白名单 |

### Controller 参考实现

```java
/**
 * 注销自己的账号
 *
 * ⚠️ 看这个签名：路径是 /auth/account（没有 {id}），参数里也没有 userId ——
 *    注销的是谁【完全由 token 决定】，前端改不了。
 */
@DeleteMapping("/auth/account")
public Result CancelAccount(@RequestBody CancelAccountDto dto,
                            @RequestAttribute("loginUser") LoginUser loginUser) {
    loginService.CancelAccount(loginUser, dto);
    return new Result().success("账号已注销", null);
}
```

> 💡 如果要走 `POST /auth/account/cancel`（见下方"请求体兼容性"），
> 把 `@DeleteMapping` 换成 `@PostMapping`、路径加 `/cancel` 即可。

### 「请求体兼容性」说明

本接口用 `DELETE` + JSON body。这在 **HTTP 规范里允许**、Spring Boot + Tomcat + nginx 也都支持。

但历史上有个别**老代理 / 老 CDN 会丢掉 `DELETE` 请求的 body**（因为它们只按 method 处理，不转发 body）。
如果你联调时发现后端收到的 `password` 是 `null`（提示"请输入密码以确认注销"，但前端明明传了），
**就是撞上这个了** —— 解决办法：

| | 路径 | 前端改动 |
|---|---|---|
| 现在 | `DELETE /auth/account` | —— |
| 备选 | `POST /auth/account/cancel` | [auth.js](../../library-web/src/api/auth.js) 里 `request.delete` 改成 `request.post`，路径加 `/cancel` |

**一行的事**，不用慌。

## 六、前端已完成的改动（你不用再写）

| 文件 | 改动 |

**前端调用契约**（[api/auth.js](../../library-web/src/api/auth.js)）：

```js
export function deleteAccount(data) {
  return request.delete('/auth/account', { data })   // data = { password }
}
```

**前端的交互流程**：

```
个人中心 → 底部「注销账号」卡片
   ↓ 点「注销我的账号」
弹窗：注销后「admin」会被永久删除，无法恢复…请输入登录密码确认
   ↓ 输入密码 → 点「确认注销」
DELETE /api/auth/account  { password: "..." }
   ↓ 成功
清空 localStorage 的 token + user → 跳回 /login
```

**前端做的一个关键动作**：成功后**主动调 `store.clear()`**，而不是只 `router.replace('/login')`。
因为路由守卫看到 localStorage 里还有 token，会认为你已登录，拿着这个刚被删掉的账号去调
`/auth/me` → 401 → 再弹一次"登录已过期"。主动清掉就不会多闪那一下。

现在点「注销我的账号」→ 输入密码 → 确认 → 会收到：

```json
{ "code": 0, "msg": "接口不存在，请检查请求路径", "data": null }
```

**预期内**，后端实现后自然消失，前端一行都不用改。

## 七、联调自测清单

**基础流程**
- [ ] 用 zhangsan 登录，个人中心点注销，输对密码 → `账号已注销`，跳回登录页
- [ ] 查数据库，`sys_user` 里 zhangsan 那一行**真的没了**
- [ ] 再用 zhangsan / 原密码登录 → `用户名或密码错误`（账号已不存在）
- [ ] 注销后前端 localStorage 里 `library_token` 和 `library_user` **都被清掉了**

**密码二次确认**
- [ ] 密码输错 → `密码不正确`，账号**没被删**
- [ ] 密码留空 → 弹窗直接不让提交（前端 `inputValidator` 拦下）
- [ ] 绕过前端直接打接口，body 传 `{}` → `请输入密码以确认注销`

**★ 最后管理员保护（最容易漏测）**
- [ ] 系统只有 `admin` 一个管理员时，用 admin 注销自己 → `系统至少需要保留一个管理员，不能注销最后一个管理员账号`
- [ ] 再新建一个管理员（比如 `admin2`），然后用 `admin` 注销 → **成功**
- [ ] 然后再用 `admin2` 注销 → **被拦下**（因为 `admin2` 成了最后一个管理员）

**★ 越权测试（必做）**
- [ ] 用 zhangsan 的 token 调 `DELETE /auth/account`，body 里**故意加** `"id": 1` 或 `"userId": 1`
      → **只有 zhangsan 被删，admin 安然无恙**（因为 id 参数被忽略）
- [ ] 不带 `Authorization` 头调 → **401**（不是 200，说明白名单没被误改）
- [ ] 用已经注销掉的账号的**旧 token**（2 小时内）调 `GET /auth/me` → **401 账号不存在或已被禁用**

**前端**
- [ ] 普通读者（USER）能看到「注销账号」卡片（不需要管理员权限）
- [ ] 管理员也能看到
- [ ] 弹窗点「我再想想」→ 什么都不发生
- [ ] 点「确认注销」时按钮显示 loading，防止连点两次

## 八、和 v2.0「不能删除自己的账号」的关系（别搞混）

v2.0 的 `DELETE /users/{id}`（管理员删用户）里有这条规则：

> **⚠️ 必须挡住**：`不能删除自己的账号`。

**这条规则要保留，不要因为有了新接口就删掉。** 两者不冲突：

| 场景 | 规则 | 为什么 |
|---|---|---|
| 管理员在「用户管理」列表里点删除 | **禁止删自己** | 那是**顺手**的操作，容易点错。挡住是防误操作 |
| 用户在「个人中心」点注销 | **允许** | 那是**明确**的意图（还输了密码）。该给用户自决权 |

> 一句话：**列表里的删除按钮是"手滑区"，个人中心的注销按钮是"深思熟虑区"。**
> 同一件事，在不同入口下用不同的严格度，是合理的。
